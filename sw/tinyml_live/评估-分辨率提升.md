# 分辨率评估：从 960×1080 提到 ≥720p

时间：2026-10-23 ｜ 结论：**技术上可行，且比现状更省带宽；卡点在 sensor 输出模式**

---

## 1. 现状（已核实）

顶层 `ti60f225_oob_top.v:622` 的帧缓冲例化：

```verilog
frame_buffer #(
  .I_VID_WIDTH   (32),
  .O_VID_WIDTH   (16),
  .START_ADDR    (32'h1000000),
  .MAX_VID_WIDTH (960),      ← 水平只有 960
  .MAX_VID_HIGHT (1080),
  .O_FRAME_WIDTH (960),
  .O_FRAME_HEIGHT(1080)
)
```

而 `frame_buffer` / `ddr_buffer` / `bank_switch` 的**模块默认值都是 1920**。
**只有顶层把它设成了 960。**

显示侧是 `HACT = 1920`、OSD `H_ACTIVE=1920,V_ACTIVE=1080`，实测 60 fps。

### 赛题对照

| 项 | 要求 | 现状 | 判定 |
|---|---|---|---|
| 垂直 | ≥720 | 1080 | ✅ |
| 水平 | 720p = **1280** | **960** | ❌ |
| 总像素 | — | 104 万（比 720p 的 92 万还多） | — |
| 帧率 | ≥30 | 59.7–60.3（实测） | ✅ |

**水平 960 < 1280，按字面要求不达标。**

## 2. 好消息：改分辨率是「只改参数」

```verilog
// rtl/frame_buffer_V4/bank_switch.v:32
localparam FRAME_LEN = MAX_VID_WIDTH*MAX_VID_HIGHT*VID_DATA_WIDTH/8 + 32'h200;
```

验证：`960*1080*4 + 512 = 4,147,712 = 0x3F4A00` —— 与工程中的帧长度**完全一致**。

⇒ bank 步长、三个 bank 的起始地址**全部由这两个参数推导**，
改 `MAX_VID_WIDTH/MAX_VID_HIGHT` 后**自动重算**，不需要手工改常量。

**需要改的地方**：

| 位置 | 改动 |
|---|---|
| `ti60f225_oob_top.v` 帧缓冲例化 | 4 个参数（`MAX_VID_WIDTH`、`MAX_VID_HIGHT`、`O_FRAME_WIDTH`、`O_FRAME_HEIGHT`） |
| `main_live*.cc` 固件 | 3 个常量（`FB_W`、`FB_H`、`FB_FRAME_LEN`） |
| 若改为 720p，OSD 文字/热力图坐标 | 若 `HACT` 也随之改，需重定位 |

## 3. 带宽与内存测算

DDR3：`sdram_clk` 周期 2.500 ns → 400 MHz × DDR × 16 bit = **1.6 GB/s 理论**

每帧缓冲：写入一次 + 显示读取一次，均按 60 fps。

| 分辨率 | 每 bank 每帧 | 写入 | 读取 | **合计** | 占 1.6 GB/s | 3 bank 总量 | 结束地址 |
|---|---|---|---|---|---|---|---|
| **960×1080（现状）** | 4.15 MB | 249 MB/s | 249 MB/s | **498 MB/s** | 31% | 12.44 MB | `0x01BDDE00` |
| **1280×720** | 3.69 MB | 221 MB/s | 221 MB/s | **442 MB/s** | **28%** | 11.06 MB | `0x01B0C000` |
| 1920×1080 | 8.29 MB | 498 MB/s | 498 MB/s | 995 MB/s | 62% | 24.88 MB | `0x028B4A00` |

### 结论

- **1280×720 比现状更省**：带宽 ↓11%，内存 ↓11%。**没有任何代价。**
- **1920×1080 翻倍**：占 62% 带宽，在 3 主口仲裁下余量偏紧，且帧缓冲跨过 `0x02000000`。
- 三个方案的帧缓冲都在 256 MB DDR 内，不与固件（`0x1000`）、模型（`0x00100000`）冲突。

## 4. 已实测：画面是水平重复的，实际只有约 960 列

把 MAX_VID_WIDTH / O_FRAME_WIDTH 改成 1920 并重编位流（p7_1920.bit，负 slack 0），
上用 SoC 采样整帧并做左右半幅对比：

| 指标 | 数值 |
|---|---|
| 左半（源 x 0..960）均值 | 102.8 |
| 右半（源 x 960..1920）均值 | 102.4 |
| 平均绝对差 | 18.00 |
| 差值 ≤3 的像素对 | 32.8% |
| **左右相关系数** | **0.921** |

**0.921 的相关系数说明左右两半是同一幅画面。**
把帧缓冲加宽到 1920 并不会得到 1920 列的真实采集，只是把 960 列的画面重复了一遍。

⇒ **真正的采集宽度是 960 列**，瓶颈在 sensor 输出模式/CSI 流水线，
不是帧缓冲参数。

复现工具：check_halves.py（采一帧、比较左右半幅、输出相关系数）

## 4b. 原始推测（已被上面的实测取代）

**这一条我无法从代码确定，需要实测或查 sensor 手册。**

- ROM 里 `0x0160~0x016b`（输出尺寸/裁剪）**全部是注释掉的**，
  说明当前用的是 sensor 默认模式，没有显式设定
- 但注释里记录过 `x_end − x_start = 1920`、`y_end − y_start = 1080`
- 顶层 `cvo_axi_v2`、`axi_streamin` 的 `FRAME_COUNT = 1*1920*1080` 也暗示按 1080p 设计

**两种可能**：

| 可能 | 含义 | 改法 |
|---|---|---|
| A. sensor 输出 1920×1080，帧缓冲只存 960 | 中间有 2:1 水平抽点 | 找到抽点处去掉，或把帧缓冲设回 1920 |
| B. sensor 输出就是 960×1080 | sensor 配置成了裁剪/合并模式 | 改 sensor 模式寄存器到 720p 或 1080p |

**怎么判定（最快）**：把 `MAX_VID_WIDTH` 改成 1920 重编一版，烧上去看画面是否变成完整 1920 宽。
- 画面正常 ⇒ 本来是 A，直接改参数即可
- 画面撕裂/错位 ⇒ 是 B，需要改 sensor 模式

## 5. 建议路线

### 首选：1280×720

| 优点 | 说明 |
|---|---|
| 严格满足 ≥720p | 1280 ≥ 1280 |
| 带宽反而下降 | 442 vs 498 MB/s |
| 内存下降 | 11.06 vs 12.44 MB |
| 16:9 与显示匹配 | 现在 960×1080 是 8:9，被拉宽到 16:9 显示 |

**代价**：需要把 sensor 配到 720p 模式（或从 1080p 裁剪出 720p 中央区域）。

### 次选：1920×1080

带宽 995 MB/s（62%），可行但余量小；帧缓冲 24.88 MB。

### 不建议：保持 960×1080

水平不达标，且是唯一"像素效率低"的方案（比 720p 多 11% 带宽却只有 75% 的有效画面宽度）。

## 6. 风险与工作量评估

| 步骤 | 工作量 | 风险 |
|---|---|---|
| 改顶层 4 个参数 + 重编位流 | ~10 分钟 | 低 |
| 固件改 3 个常量 | ~5 分钟 | 低 |
| 判定 sensor 输出模式（§4 的实验） | ~20 分钟 | 低 |
| 若需改 sensor 模式 | 半天–1 天 | **中**：sensor 寄存器手册、CSI 时序、PLL 可能都要跟着调 |
| OSD 坐标重定位（若 HACT 变） | 1 小时 | 低 |

**最坏情况**：sensor 模式改动导致出图失败，需要回退到 960×1080。
所以**建议先在分支上做实验位流，别动已验证的 p6_exp.bit**。
