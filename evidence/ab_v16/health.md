# v16 阶段 A：板子健康检查（实测结果）

**执行时间**：2026-10-23 ｜ 位流 `v7_MERGE11.bit`（SHA256 核对通过）｜ 固件 `tinyml_pdti8_v16_base.bin`（CRC32 `901478D6`）

**结论**：✅ 固件起得来、管线正常，**可以进入阶段 B**；但发现 **画面偏亮（b0m=185）导致空场 100% 误报**，以及 **传感器无读数** 两个问题。

## 2. 检查项逐条结果

|---|---|---|---|
| a | 画面是否正常输出 | ⚠️ **管线正常，但无法目视确认** | 96×96 dump 有内容、每帧 `MMT_OSD` 连续输出、图像结构合理；HDMI 画面需人眼确认（本机无法截屏） |

### b) 关于 `MMT_CAM_VTS` 的格式 bug

```
MMT_CAM_VTS ok=1 vts=0x04x rom_vts=0 fallback=1
```

`main_live16.cc:530` 用的是 `MicroPrintf(... vts=0x%04x ...)`，而 **MicroPrintf 不支持宽度修饰符**，
于是 `%04x` 被拆成字面量输出，真实数值丢失。同一原因使该行无法直接读 VTS。

**真实 VTS 可从 `MMT_LP` 行得到**（每帧都有）：`vts=0x000005dc` = **1500**，且 `vts_ok=1`。
它落在合法区间 `[0x0400, 0x0A00]` 内，说明**相机寄存器读通路可用、VTS 合法**。

> 建议：把 530 行的 `%04x` 改成 `%x`（MicroPrintf 支持），行 683/780 同理。

### c) 传感器状态

- SHT30：`sht=0 rh=0`，119 帧全部为 0 → **无温湿度读数**
- MLX90640：`ir_upd` 从 0 递增到 6（固件在周期性发起刷新），但 `irhot=0`、`body=0` → **无有效红外读数**

按任务书要求：**只报告，不擅自改线**。可能原因：I2C 未接/接触不良/上拉缺失/器件未上电。
OSD 上的 `SNS=` 字段应为 `ER`。

## 4. 自动曝光（AE）变体的取舍

任务书条件：「`MMT_CAM` 行显示读写通路可用，且启动 VTS ∈ [0x0400, 0x0a00]」。

- `MMT_CAM` 详细行**本次不存在**——因为它只在 `AUTOEXP_ON` 或 `LP_CAMFPS_ON` 打开时才打印，
  而 base 固件两者都是 0（设计如此，不是故障）。
- 但 `MMT_CAM_VTS ok=1` + `MMT_LP vts=0x5dc vts_ok=1` 已经证明**读通路可用且 VTS 合法**。

**决策：判定条件满足，编译并追加 AE 变体。** 理由：`MMT_CAM` 的缺失是宏配置导致，而非通路故障；
继续等待它出现会让 AE 测试永远无法执行。

## 5. 决策记录

1. **AE 变体照做**（见 §4），命名 `tinyml_pdti8_v16_crop1_ae_dump.bin`，仅开 `AUTOEXP_ON=1`。
   注意 `AE_DIM_ENABLE=0`（默认）时 AE **只能变亮不能变暗**；当前场景已过亮（b0m=185），
   因此预计 `b0m` 无法进入 `[95,125]`。这一负结果本身就是要报告的信息。
2. **`IMG_DUMP_EVERY` 最终取 10**。实测本固件推理已占 485 ms（上限 2.06 fps），
   而一次 dump ≈ 19.6 KB ≈ 1.70 s 串口时间：
   N=1 → 0.46 fps、N=5 → 1.23 fps、N=10 → 1.53 fps、N=40 → 1.95 fps。
   **「≥2 fps」与「多出图」在本硬件上不可兼得**；取 N=10 以保证 35 s 内约有 5 张图供离线重放，
   同时帧率仍 >1.5 fps。若实测低于 1.5 fps 再升到 20。
3. **不因 b0m=185 中止**：固件与管线均正常，`b0m` 偏高正是本轮要对比解决的对象；
   按任务书，中止条件只针对「画面不正常或固件起不来」。
4. 未对传感器做任何接线改动。

## 7. 追加诊断：阶段 B 开始后固件上传失败（2026-10-24）

阶段 A 之后、阶段 B 之前，固件上传开始稳定失败：

| 尝试 | 镜像 | 大小 | 失败位置 |
|---|---|---|---|
| 1 | base_dump | 480,882 B | Block 1037（66 KB） |
| 2 | base_dump | 480,882 B | Block 966（61.8 KB） |
| 3（ACK 超时加宽到 6 s） | base_dump | 480,882 B | Block 914（58.5 KB） |
| 4（同上，重试） | base_dump | 480,882 B | Block 920（58.9 KB） |
| 5（原版 base，阶段 A 成功过） | base | 472,594 B | Block 1182（75.6 KB） |
| 6（块间加 3 ms 延时） | base | 472,594 B | Block 1161（74.3 KB） |

**截断镜像对照实验**（排除固件/加载器因素）：

| 镜像大小 | 结果 |
|---|---|
| 40 KB | ✅ `MMT_LOAD_PASS DDR_CRC` |
| 56 KB | ✅ `MMT_LOAD_PASS DDR_CRC` |
| ≥58 KB | ❌ 板子不再回 ACK（6 s 内一个字节都没有） |

**结论**：加载器、固件、串口主机侧均正常；**板子在写入约 56–64 KB 之后停止响应**。
镜像从 DDR `0x1000` 开始写，56 KB 对应 `0xF000` —— 故障区间起始于 `0xF000`~`0x10000` 附近。
与固件内容无关（阶段 A 用同一份 472 KB 固件曾一次性成功），属于**板子侧状态退化 / DDR 异常**。

**处理**：按任务书「板子无响应：停止并报告当前状态，不要反复重烧」，已停止后续烧录。
**需要断电重新上电（拔插 USB 或断电重启）以重新跑 DDR 校准**，然后从阶段 B 重新开始。

**已做的加固**（仅改本地副本，不动仓库）：

- `tools/load_and_run.py`：单块 ACK 超时 2 s → 6 s，容忍杂散字节；新增 `--block-gap` 可加块间延时。
- `capture_v16.py`：Efinity 的 `PYTHONHOME` 只传给烧录子进程与加载器子进程，不污染主进程；
  加载器改用 Efinity 自带的 python（它带 `pyserial`）。
