# 网口实测记录（2026-11-03 下午）

## 一、发送（TX）已打通并实测

主设计（SoC+相机+HDMI+MOT 全在）上板，PC 抓到：

```
PKT 1800  169.254.47.62:8080  len=64  MMT-RAW-TEST-0123456789abcdef...END
NIC: err=0
```

**根因**：`ge_raw_tx` 的 APB 写通路里，`wdata`/`wen` 是寄存一拍输出的，而写地址 `wptr`
在同一拍就自增了 ⇒ **整帧数据错位一个 32 位字**，FCS 自然不对，网卡按错误帧丢弃。
修法：加一级 `waddr_r`（与 wdata 同拍寄存的写地址）。修完立刻正常。

## 二、接收（RX）

- 同样的错位 bug 也存在于 `ge_raw_rx`（`waddr` 同拍自增），已按同样方式修好（`waddr_r`）；
- RX 状态寄存器语义也改成了 `bit31 = 有新帧, [10:0] = 字数`，固件按这个读；
- **还没完成端到端验证**：ARP/ping 仍不通，需要再上板一轮确认 RX 是否真的抓到帧。

## 三、板内 HTTP

协议栈/页面/PNG 全部在 PC 上自测通过（`net_sim`、`http_sim`、Pillow 校验），
固件也编译通过（357 KB）。**只差 RX**：浏览器发 GET → 板子要能收到并回包。

## 四、现场踩坑（下次直接照做）

1. **`tools/mot_service.ps1` 是看门狗**，会不停重启 `web_monitor` 抢占 COM15；
   刷固件前必须先杀掉看门狗，否则一直 `PermissionError: COM15`；
2. `flash_vendor_utf8.ps1` 的 `-Sha256` 必须是**完整 64 位**，传短哈希会被拒绝（"sha256 不匹配"）；
3. 板子有时卡在 `MMT_LOADER_READY`，重烧位流即可恢复（load_v30 上传前后要确认 LOAD_PASS）。
