## 2. Q2 第一个被折的信号：**视频输入侧全活，折叠起点在 `ddr_wr_buffer` 自己**

### 2.1 三个 CEG 扇出数字：我们和"写通路活着的"厂商工程**逐项相同**（**实测**）

`map.rpt` 的 **EFX_FF CE enables** 段（时钟使能信号及其控制的 FF 数）：

| 信号 | 我们（`out\mmt.map.rpt`） | 厂商（`ti60f225_oob_top.map.rpt`） | 是否一致 |
|---|---|---|---|
| `checker0/u_vid_rx_align/u_frame_info_det/w_frame_end` | `:413` → **24** | `:527` → **24** | ✅ 完全相同 |
| `checker0/u_vid_rx_align/u_frame_info_det/frame_end_r0` | `:755` → **3** | `:528` → **3** | ✅ 完全相同 |
| `checker0/u_vid_rx_align/u_frame_info_det/frame_end_r1` | `:1055` → **1** | `:529` → **1** | ✅ 完全相同 |

### 2.2 `frame_end_r1` 的"1"就是 `frame_stable` 的触发器 ⇒ **`frame_stable` 没被折**（**实测+推断**）

`rtl\frame_buffer\frame_info_det.v`：

```
:92      end else if( frame_end_r0 ) begin
:93          frame_len_d0 <= frame_end_r0;     // 24 位寄存器，CE = frame_end_r0
:94          frame_len_d1 <= frame_len_d0;
:95          frame_len_d2 <= frame_len_d1;
:99  always @( posedge clk or negedge rst_n )
:103     end else if( frame_end_r1 ) begin    // ★ frame_end_r1 的唯一用途：给 frame_stable 做 CE
:104         if( frame_len_d0 == frame_len_d1 && frame_len_d0 == frame_len_d2 )
:105             frame_stable <= 1'b1;
```

- `frame_end_r0` 扇出 **3** = `frame_len_d0/d1/d2` 三个 FF 的 CE —— 与 `:93-95` 完全对应 ✅
- `frame_end_r1` 扇出 **1** = `frame_stable` 一个 FF 的 CE —— 与 `:103` 完全对应 ✅

⇒ **`frame_stable` 的触发器在网表里存在、且被 `frame_end_r1` 使能。它没有被折。**
⇒ 也就是说：**`wr_start = frame_start & frame_stable`（`rtl\frame_buffer\frame_buffer.v:196`）的输入端在报告里是活的。**

### 2.3 方法论修正：「在 `map.rpt` 里搜不到」≠「被折」（**实测**）

Lead 与我都曾把"`frame_stable` / `frame_start` / `w_mipi_rx_de/hs/vs` 在 `map.rpt` 里完全搜不到"当成"已经被折"的证据。**这个推断不成立**，实测反证：

- 在**厂商那份写通路活着的报告里**，`frame_stable` **0 命中**、`frame_start` **0 命中**（`ti60f225_oob_top.map.rpt`）。
- 原因：`map.rpt` 只列 **CE/SR 表**（时钟使能/置复位信号）和 **Trimming Report**（被优化的信号）。`frame_stable`/`frame_start` 只驱动**D 端**（进 ser2par 的 `frame_stable` 输入、进 `wr_start` 的与门），**既不是 CE 也不是被折信号**，所以两张表都不会列它。
- 同理 `w_mipi_rx_de/hs/vs` 是**端口连接网**，不在两张表里出现是正常的。

**⇒ 判断"是否被折"必须看 `(optimized to 0)` / `(unreachable)` / `(merged to equivalence)` 这三个后缀，不能看"是否存在"。**

### 2.4 RTL 逐拍推导：`frame_stable` **必然**会在第 3 个 `frame_end_r1` 变成 1（**推断，但可逐步核对**）

`frame_len_d0/d1/d2` 的 CE 都是 `frame_end_r0`；`frame_len_d0 <= frame_end_r0`（1 位零扩展到 24 位）。
`frame_end_r0` 是 `w_frame_end` 的 1 拍脉冲（每帧一次）；`frame_end_r1` 是它延迟 1 拍。

| 第 N 帧的脉冲 | 脉冲那拍各寄存器值（前） | 脉冲沿之后（CE=1 才移位） | `frame_end_r1` 那拍的比较（`:104`） | `frame_stable` |
|---|---|---|---|---|
| 1 | (0,0,0) | (1,0,0) | `1==0` 假 | 0 |
| 2 | (1,0,0) | (1,1,0) | `1==1 真 && 1==0 假` | 0 |
| 3 | (1,1,0) | **(1,1,1)** | `1==1 && 1==1` **真** | **1** |
| ≥4 | (1,1,1) | (1,1,1) | 真 | **保持 1** |

（`frame_len_d0/d1/d2` 的 bit[1:23] 被优化为 0 是**正常的**，因为 `frame_len_d0 <= frame_end_r0` 只可能写进 bit[0]；比较退化成 3 个 1 位值的相等。bit[0] 活着，未出现在 trimming 列表里。）

⇒ **`frame_stable` 在语义上可达 1 并保持** ⇒ `wr_start` 不是常量 0 ⇒ **`state ≡ 0` 这个折叠结果在 RTL 语义上无法成立。**

### 2.5 结论：**第一处（也是唯一一处）被折的就是写 FSM 自己**（**实测**）

`out\mmt.map.rpt`（Sequential Elements/Signals Trimming Report）里，本项目 s0 写通道的全部折叠条目：

```
:3561  'fb_awvalid' (rtl\mmt\mmt_top.v:347) (optimized to 0)
:3562  'fb_wvalid'  (rtl\mmt\mmt_top.v:352) (optimized to 0)
:3563  'fb_wlast'   (rtl\mmt\mmt_top.v:351) (optimized to 0)
:3564  'checker0/u_ddr_buffer/ddr_wr_buffer_inst/state[1]' (rtl\frame_buffer\ddr_wr_buffer.v:316) (optimized to 0)
:3636  'checker0/u_ddr_buffer/ddr_wr_buffer_inst/state[0]' (rtl\frame_buffer\ddr_wr_buffer.v:316) (optimized to 0)
:3637  'checker0/u_ddr_buffer/ddr_wr_buffer_inst/burst_end_r' (rtl\frame_buffer\ddr_wr_buffer.v:446) (optimized to 0)
```
加上 `u_wr_fifo` 的 26 条端口裁剪（`out\mmt.map.rpt:1634-1659`，`RADDR tied off` / `RDATA disconnected`）。

**⇒ 折叠的边界非常干净：从 `ddr_wr_buffer` 的 `state` 往外，`awvalid/wvalid/wlast` 到顶层 `fb_*`，再往上是 `u_wr_fifo`。它的上游（`vid_rx_align` / `frame_info_det` / CSI RX 的接口）在报告里全部是活的。**

**三种可能，必须用实验分开（见 §3）**：
- **(P1)** 综合器**正确**地证明了 `wr_start ≡ 0` —— 但按 §2.4 这不可能，除非它把某个我读不到的常量（如 `frame_start ≡ 0`）算出来了；
- **(P2)** 综合器**过度优化**（把语义上可达的 FSM 削掉）—— 与"同 RTL、同 IP、同输入侧，只有工具版本/流程不同"的自洽性最高；
- **(P3)** 折叠的真实入口在**写缓冲/互联侧**（例如 `awready`/`wready` 被证明为常量），而不是 `wr_start`。

**⇒ 这就是 X1/X2/X3 要判定的东西。**

### 2.6 唯一的设计侧差异：SDC（**实测，已排查，大概率不是根因**）

我们把 `constr\ti60f225_oob.sdc` 与厂商 `ti60f225_oob.sdc` 做了**全文 diff**（厂商 339 行 / 我们 364 行），**实质差异只有 2 处**：

| # | 我们的 | 厂商的 | 说明 |
|---|---|---|---|
| 1 | `:26  ... -group {vid_clk_dvi2 hdmi_tx_slow_clk} ...` | `:26  ... -group {vid_clk_dvi2} ...` | task-1/CDC 分析的改动：把 `hdmi_tx_slow_clk` 并进 `vid_clk_dvi2` 所在的 `-exclusive` 组 |
| 2 | `:162-165 set_output_delay -clock core_clk ... {system_spi_0_io_sclk_write / _ss}` | `set_output_delay -clock i_soc_clk -reference_pin [...]` | 我们改用真实时钟 `core_clk`（原来那条是空操作） |

其余全部相同（含 `:21 create_clock -period 20.0000 i_mipi_rx_pclk`、`:25`、`:27` 的 `set_clock_groups`）。

- **判定**：这两条都**不触及** frame_buffer 写通路的时钟（`i_mipi_rx_pclk` ↔ `core_clk`）；`:26` 改的只是 `hdmi_tx_slow_clk` 的从属关系，而 `hdmi_tx_slow_clk` 不在 `checker0` 的任何端口上。
- **不能完全排除**：`set_clock_groups -exclusive` 在语义上是"这些时钟互斥、不会同时有效"。**推断**它不该删除逻辑，但"`-exclusive` 是否影响了 2026.1 的优化"属于**无法确认**；如果 X1/X2/X3 都指向"工具过度优化"，**建议 Lead 顺手做一次对照：把 `:26` 恢复成厂商原样（`-group {vid_clk_dvi2}`，去掉 `hdmi_tx_slow_clk`）跑一次 `efx_map`**，看写通路是否回来。这是一次 2 分钟、零功能代价的对照。
  ⚠️ 注意：回退 `:26` 会让 task-1 修好的 WNS 问题复发（`core_clk ↔ hdmi_tx_slow_clk` 假违规），**只能作为一次性诊断，不能作为最终状态**。

## 3. Q3 三个最小隔离实验（Lead 照做，每个只跑 `efx_map`，~2–3 分钟）

> 全部是**临时诊断改动**，验证后必须回滚。基线先记下：`Memory Blocks 222/256`（`out\mmt.place.rpt:339`）、`checker0` mem=15（`out\mmt.res.csv:118`）、`ddr_wr_buffer_inst` mem=**0**（`:126`）、`inst_efx_csi2_rx` mem=4（`:11`）。

### X1 —— 钉住 `wr_start`：判定"折的入口是不是 `wr_start`"

**改哪行**：`rtl\frame_buffer\frame_buffer.v:196`
```verilog
/*i*/.wr_start        (frame_start & frame_stable),   // 原
/*i*/.wr_start        (1'b1),                        // 改成
```

**预期（读 `out\mmt.res.csv` / `out\mmt.map.rpt`）**：

| 观测量 | 位置 | 若"折的入口是 wr_start"（工具行为正确） | 若"折与 wr_start 无关"（工具过度优化） |
|---|---|---|---|
| `ddr_wr_buffer_inst/state[0]` | trimming 报告（现 `:3636`） | 由 `optimized to 0` 变成 **`optimized to 1`**（或该条目消失、`state` 合并为常量 1） | **仍然是 `optimized to 0`** |
| `ddr_wr_buffer_inst/state[1]` | 现 `:3564` | 仍是 `optimized to 0`（FSM 停在 state 1） | 仍是 `optimized to 0` |
| `ddr_wr_buffer_inst` 的 XLR | `res.csv`（现 `:126`，77） | 明显上升（FSM 的 FF 不再被删） | 不变 |
| `u_wr_fifo` 的 mem | `res.csv` | **仍为 0**（FIFO 没有数据 → 读侧仍死，可接受） | 仍为 0 |
| 总 BRAM | `place.rpt` | 基本不变（222） | 不变 |

**它证明什么**：`state` 能否被"一个恒定有效的 `wr_start`"救活。
- 若 `state[0]` 变 1 ⇒ **折的入口确实是 `wr_start`（即视频输入侧被证明为常量）** ⇒ 下一步用 X3 定位是 CSI RX 还是更上游。
- 若 `state[0]` 仍为 0 ⇒ **即使 `wr_start` 恒 1，工具也把 FSM 折了** ⇒ **P2（工具过度优化）成立**，且**与视频输入侧无关**。
**它不证明什么**：不能说明真实运行时 `wr_start` 是否会脉冲；不能量化最终的 BRAM 回升。

### X2【最推荐】—— 同时钉住 `wr_start` 和 `wr_fifo_wren`：判定断点在输入侧还是写缓冲/互联侧，并量化 BRAM 回升

**改哪行**（在 X1 的基础上加一条）：
- `rtl\frame_buffer\frame_buffer.v:196` → `.wr_start(1'b1)`
- `rtl\frame_buffer\frame_buffer.v:203` → `.wr_fifo_wren(1'b1)`（原 `.wr_fifo_wren(wr_fifo_wren)`）

**预期**：FIFO 每拍被写 → `wr_fifo_rdusedw` 涨过 `ddr_awlen` → `wr_req=1` → `state`→2（需 `awready`，来自互联）→3 → `awvalid/wvalid` 拉起 → `wr_fifo_rden` 活 → **整条写通路活**。

| 观测量 | 位置 | 预期值 |
|---|---|---|
| `+u_wr_fifo:DC_FIFO(FIFO_DEPTH=1024)` | `out\mmt.res.csv` | **出现**该行，内存列 **13(13)**（对照 `ti60f225_oob.res.csv:128`） |
| `+ddr_wr_buffer_inst:ddr_wr_buffer(...)` 内存列 | `out\mmt.res.csv:126` | **0 → 13** |
| `+checker0:frame_buffer(...)` 内存列 | `out\mmt.res.csv:118` | **15 → 28** |
| `'fb_awvalid' / 'fb_wvalid' / 'fb_wlast'` | trimming 报告 | **三条都消失** |
| `ddr_wr_buffer_inst/u_wr_fifo` 的 `RADDR tied off`/`RDATA disconnected` | Memory Trimming（现 `:1634-1659`，26 行） | **全部消失**，只应剩良性 `WE[1] tied off` |
| `u_wr_fifo/FifoWrEn`、`u_wr_fifo/ReadEn` | CE 表 | **出现**，各约 23 FF（对照厂商 `:501-502`） |
| `Memory Blocks` | `out\mmt.place.rpt:339` | **222 → 约 235**（+13） |

**它证明什么**：
- **若如上表全部命中** ⇒ **写缓冲 + 写 FIFO + `axi_interconnect` s0 口这条链是健康的、能装能跑，且正好值 13 块 BRAM**；断点**在它上游**（`wr_start`/`fifo_wr_en` 被证明为常量）⇒ **根因在视频输入侧**。
- **若 `ddr_wr_buffer_inst` 的内存列仍为 0**（FIFO 仍被删）⇒ 断点**不在输入侧**，而在**写缓冲自身 / 互联 s0 口 / 工具**（即 P3 或 P2）⇒ 下一步查 `.awready/.wready` 是否被证明为常量、以及 s0 口在互联里的处理。
**它不证明什么**：不区分"是 CSI RX 输出被判死"还是"更上游从没活过"（那是 X3）；也不代表这可以作为最终实现（强制 `wr_fifo_wren=1'b1` 会写假数据）。

### X3 —— 用一个"一定会翻转"的假 VS/DE 旁路 CSI RX：判定"CSI RX 的输出是否被判死"

**改哪行**：`rtl\mmt\mmt_top.v:702-703` 的 checker0 端口，临时改接本地生成的翻转信号（**只做诊断，`.vin` 可保留或给常量**）：
```verilog
// 临时诊断：在 i_mipi_rx_pclk 域造一对必然翻转的 vs/de
reg [15:0] dbg_cnt = 16'd0;
always @(posedge i_mipi_rx_pclk) dbg_cnt <= dbg_cnt + 1'b1;
wire dbg_vs = (dbg_cnt == 16'd0);
wire dbg_de = (dbg_cnt[3:0] != 4'd0);
...
/*i*/.i_vs   (dbg_vs),      // 原 (w_mipi_rx_vs)
/*i*/.i_de   (dbg_de),      // 原 (w_mipi_rx_de & w_mipi_rx_hs)
```

**预期**：`w_frame_start`/`w_frame_end` 必然出现边沿 → `frame_start`/`frame_stable` 变活 → `wr_start` 出现上升沿 → `state`→1；`fifo_wr_en` 也会因 `frame_stable=1` 与 `de` 而活 → FIFO 被写 → 同 X2 的判据（`u_wr_fifo` 13 块、`ddr_wr_buffer_inst` 0→13）。

| 结果 | 说明 |
|---|---|
| **写通路回来**（判据同 X2） | ⇒ 根因是 **CSI RX 的四路视频输出在综合期被判成常量**（`w_mipi_rx_vs/de/hs` 或 `pixel_data_valid`）⇒ 下一步查 CSI RX 的 `vsync_vc0`/`pixel_data_valid`/`hsync_vc0` 为什么在**我们这条链**上被判死（注意：E2 已证明不是 IP 版本，所以要看**它周边**——例如 `pixel_data` 的消费者、`i_de & i_hs` 的组合、或 `pack` 参数） |
| **写通路仍死** | ⇒ 折与视频输入**无关** ⇒ 直接指向**写缓冲/互联侧或工具**（P2/P3） |

**它不证明什么**：这是把真实摄像头输入切断后人为造信号，**不代表真实运行会好**；只能在"回来/不回来"这个二值上作判据。

### 3.1 对 Lead 原建议 ③ 的更正

任务描述里的建议 ③ 是"**把 `frame_info_det` 的 `i_de/i_vs` 换成常量（看折叠是否消失）**"。
**这个方向是反的**：把输入钉成常量只会让折叠**更彻底**（`w_frame_start/w_frame_end` 立刻变成常量，`frame_stable` 也就恒 0），**不可能让折叠消失**，因此不具判别力。
**请用上面的 X3 替代**：造一对**会翻转**的信号（而不是常量），才能区分"输入被判死"与"折与输入无关"。

### 3.2 建议的执行顺序与回滚

1. 先 X1（只改 1 行）——2 分钟就得到"折的入口是不是 `wr_start`"这个二元答案。
2. 再 X2（2 行）——拿到 BRAM 回升量 + 断点在输入侧还是写缓冲侧。

## 4. Q4 "修好后 BRAM 涨多少"复核：**下限 +13，上限 +45（会超容量）**

### 4.1 确定的部分：+13 块（**实测 + 算术**）

- `u_wr_fifo = DC_FIFO(DATA_WIDTH=128, FIFO_DEPTH=1024)`：128×1024 = 131,072 bit；EFX_RAM10 单块 10,240 bit ⇒ `ceil(131072/10240) = 13` 块；**厂商实测恰好 13**（`ti60f225_oob.res.csv:128`）✅
- 连带：`checker0` 由 15 → **28**（厂商实测 28，`ti60f225_oob.res.csv:119`）
- ⇒ 全器件 **222 → 235**（235/256 = **91.8%**）。**task-12 的"约 13 块"复核成立。**

### 4.2 ⚠️ 但还有一个"隐藏的 32 块"可能一起回来（**推断，必须预警**）

按 §1.5 的因果反转：**CSI RX 现在只有 4 块 mem（`out\mmt.res.csv:11`），而厂商流程下同一个 IP 是 36 块（`ti60f225_oob.res.csv:11`）**。如果那 32 块的缺失**是写通路被折的后果**（输出没人用 → 像素侧 FIFO 被删），那么**一旦写通路修好，这 32 块也会回来**：

| 情形 | BRAM | 占 256 |
|---|---|---|
| 现在（写通路死） | 222 | 86.72% |
| 只回来写 FIFO（若 CSI RX 的 32 块确实与此无关） | **235** | 91.8% |
| 写 FIFO + CSI RX 像素侧都回来 | **267** | **104.3% ⇒ 装不下！** |

**⇒ 给 Lead 的两个警示**：
1. **验收判据里要同时看 `inst_efx_csi2_rx` 的 mem 列**（现 4）。它一旦明显上升（向 36 靠），说明"隐藏的 32 块"确实是被这个折叠压住的、并且**总量会顶穿 256**。
2. **在修写通路之前，先把 §4.2 的预算和 task-5 的削减方案（`docs\BRAM资源优化方案.md`）对齐**——很可能必须**同时**执行那边的 `OCRSize 32768→16384`（−16）等条目，才能让"写通路修好 + 像素 FIFO 回来"同时装得下。

> 诚实标注：36 这个数字来自**不可比的基线**（§1），所以"32 块会不会全回来"**无法确认**，只能用 X2/X3 的 `res.csv` 实测。但**风险足够大，必须提前预算**。
