## 0. 结论摘要

### 0.1 先认账：**X1/X3 双负直接否掉了我 task-13 的"输入侧"判断**

- X1（`.wr_start(1'b1)`）⇒ `state[1:0]` 仍 `optimized to 0`；
- X3（注入必然翻转的 `dbg_vs/dbg_de`）⇒ 仍全折，且 **BRAM 222→218、XLR 45541→43586**（这反而**证实**了我 task-13 §1.5 的"因果反转"：CSI RX 的存储是**跟着消费者一起被删的后果**）。
- ⇒ **折叠与视频输入无关，与 `wr_start` 也无关。**

### 0.2 本轮最硬的一条推理：**"钉 `fb_awready=1'b1`"这个实验在原理上不可能有效，建议不要跑**

`out\mmt.map.rpt` 里 `state[0]` 是 `optimized to 0`，意味着 **FSM 连 state 1 都没进过**。
而 `ddr_wr_buffer.v:413-416` 的 state 0→1 分支是：

```verilog
:413  case(state )
:414  2'd0 : begin
:415      if( sync_r2)          // ← 只依赖 sync_r2（由 start_sync/pos_sync 延迟而来）
:416          state <= 2'd1;
```

**`sync_r2` 的源头是 `wr_start`（经 `start_sync`/`pos_sync`/`sync_r0..r2`），与 `awready`/`wready` 毫无关系**（`awready` 只在 state 2→3 用，`wready` 只在 state 3 / `wlast` 用）。
⇒ 即使 `fb_awready` 恒 1，state 也只会停在 **1**（`state=2'b01`），不可能解释 `state[0] ≡ 0`。
⇒ **"ready 被判常量"这条假设解释不了观察到的现象**（它只能解释"卡在 state 1/2"，不能解释"卡在 state 0"）。

### 0.3 更硬的第二条：**X1 的结果与 RTL 语义直接矛盾**（**推断，可逐步核对**）

把 `.wr_start` 钉成 `1'b1` 后，`ddr_wr_buffer.v:119-140 + 402-442` 的行为是**可逐拍算出来的**：

| 拍 | `start_sync` | `pos_sync` | `sync_r0` | `sync_r2` | `state` |
|---|---|---|---|---|---|
| 复位 | 00 | 0 | 0 | 0 | 0 |
| E1 | 01 | 1 | 0 | 0 | 0 |
| E2 | 11 | 0 | 1 | 0 | **0（被 sync_r0 拉回）** |
| E3 | 11 | 0 | 0 | 0 | 0 |
| E4 | 11 | 0 | 0 | **1** | **1** |
| ≥E5 | 11 | 0 | 0 | 0 | **1（永远停在 1）** |

（`start_sync <= {start_sync[0], wr_start}`，`wr_start≡1` ⇒ 序列 00→01→11→11…；`pos_sync = (start_sync==2'b01)` 只 1 拍；`state` 除 state 0→1 外没有别的路径能离开 0，因为 `sync_r0` 只出现在 E2 那一拍。）

⇒ **`state` 必然变成常量 `2'b01`**，工具应当报 `state[1]` optimized to 0、**`state[0]` optimized to 1**。
**X1 实测两份都是 0** ⇒ 只有两种可能：
- **(甲) 写 FSM 的输出在工具眼里"不可观测"** —— 于是工具把 `state` 的取值当无关量、按惯例折叠成 0。这与 X1/X3 全部自洽；
- **(乙) 工具过度优化（bug）**。

**⇒ 本轮剩下的全部工作就是把 (甲) 和 (乙) 分开。** 这正是 §3 的 Y1。

### 0.4 新嫌疑排序（详见 §2）

### 1.2 S1 的机理（为什么"不可观测"能解释一切）

综合器的死逻辑消除是**从输出往回推**的。如果 `ddr_wr_buffer` 的 `awvalid/wvalid/wlast/wdata` 在**网表可观测性**意义上没有任何下游消费者（例如互联 s0 的写通道在内部没有被接通），那么：

1. `state` 只被 `awvalid/wvalid` 消费 ⇒ `state` 也变成不可观测 ⇒ 工具按惯例折叠为 0（**注意：这与"state 被证明恒 0"在报告上写法相同，都是 `optimized to 0`**）；
2. `u_wr_fifo` 的读侧（`RdEn` 来自 `awvalid/wvalid`）随之死掉 ⇒ RADDR tie off / RDATA disconnect（`mmt.map.rpt` 的 Memory Trimming，baseline 那轮在 `:1634-1659`，26 行）；
3. 顶层 `fb_wdata` 也随之不可观测 ⇒ 该 FIFO 的存储被删 ⇒ `ddr_wr_buffer_inst` mem = 0；
4. **而且这一切对 `wr_start`（X1）和视频输入（X3）完全不敏感** ✔✔

**⇒ 这是目前唯一能同时解释 X1 与 X3 的机制。**

从**资源**上看，互联的 s0 写通道**不像**被删（`out\mmt.res.csv`，baseline 那轮 `:48-57`）：

## 2. 新嫌疑排序与"怎么查"

### 2.1 S1：互联 s0 写通道不可观测（**最可能**）

**查法（在 `map.rpt` / `res.csv` 里，全部可机检）**：

1. **先分清"哪个 ready 是 s0 的"**：顶层网名是 `fb_awready` / `fb_wready` / `fb_bready`（由互联 `s_axi_awready[0]` 驱动，`mmt_top.v:796/804/809`）。
   ```powershell
   Select-String -Path D:\FPGA\mmt\out\mmt.map.rpt -Pattern "fb_awready|fb_wready|fb_bready"
   ```
   - 出现在 **EFX_FF CE enables** 段 ⇒ 有负载、活；
   - 出现在 trimming 段带 `(optimized to 0/1)` ⇒ 被判常量（此时"写通道拿不到 ready"成立）；
   - **两处都不出现** ⇒ 无负载/无驱动（最坏：互联没接上）。
   **注意**：如果写 FSM 已被折，`fb_awready` 会**因为没负载**而跟着消失 —— 这是**后果**，不能当原因，必须配合 Y1 才能定因果。
2. **看互联实例自己的资源**（baseline 那轮 `out\mmt.res.csv:48-57`）：`u_efx_axi_interconnect` = 668 XLR / RAMs 0，子节点 = arbiter(PORTS=6) + wrdata_skid(146b) + rddata_skid(136b)（见 §1.3 表）。**若某一路 skid buffer 或 arbiter 的 PORTS 数不对（例如 PORTS=4 而不是 6），就说明有通道被删** —— 当前是 6，正常。
3. **看互联内部的 per-port 信号**：`mmt_top.v` 里互联的 s 口名是 `s_axi_*`（向量），`m` 口名也是 `s_axi_*`（单口，见 `mmt_top.v:835-874` 的 m 口连接）——**名字撞车**，查 `map.rpt` 时务必带上下文（`m_axi_*` 是互联的**输入**端口名，顶层网名是 `s_axi_*`）。
4. **最强判据 = Y1**（§3.1）：直接看折叠是"跟着信号"还是"跟着位号"。

### 2.2 S2：`rst_n` 被判常量 0 —— **倾向排除（我给出反证）**

- 若 `ddr_wr_buffer` 的 `rst_n`（= `axi_clk_rst_n`，`rtl\frame_buffer\ddr_buffer.v:127`）恒 0，则其所有 FF 恒为复位值：`state≡0`、`awvalid/wvalid/wlast≡0`、`burst_end_r≡0` —— **能解释全部观察，且对 X1/X3 不敏感**。这是 S2 唯一比 S1 更简洁的地方。
- **反证**：同一个 `axi_clk_rst_n` 也接到读缓冲 `ddr_buffer.v:179` 的 `ddr_rd_buffer_inst.axi_clk_rst_n`，而 `rtl\frame_buffer\ddr_rd_buffer.v:79-101` 用 `always @(posedge axi_clk or negedge axi_clk_rst_n) if(!axi_clk_rst_n) ...` 复位它的 axi 域 FSM。实测 `checker0/u_ddr_buffer/ddr_rd_buffer_inst/u_rd_fifo/FifoWrEn` **在 CE 表里、控制 23 个 FF**（task-10 那轮 `mmt.map.rpt:418`）⇒ 该 FIFO 的**写使能是活的** ⇒ 它的 `WrEn = ddr_rd_valid` 是活的 ⇒ 读缓冲的 axi 域 FSM 活着 ⇒ **`axi_clk_rst_n` 不是常量 0** ⇒ S2 排除。
- **零改动复核法**（建议 Lead 顺带看一眼最新一轮）：
  ```powershell
  Select-String -Path D:\FPGA\mmt\out\mmt.map.rpt -Pattern "ddr_rd_buffer_inst/u_rd_fifo/FifoWrEn|ddr_rd_buffer_inst/state|ddr_rd_buffer_inst/burst_end_r"
  ```
  若读缓冲的同类信号**也没有**被折（`burst_end_r`/`state` 不在 trimming 里），而写缓冲的**全被折** ⇒ 两者共用同一个 `rst_n` + 同一个 `axi_clk`，**唯一的差别只剩"输出有没有消费者"** ⇒ **进一步指向 S1**。

### 2.3 S3：工具过度优化（**兜底**）

- 支持：同 RTL、同 IP、同输入侧；厂商 2025.2 的 build 里同一 FIFO 13 块 BRAM、CE 齐全（task-10 §2.3）。

### 3.1 Y1【首推 · 最决定性 · 改 2 行】交换 s0 与 s1 在拼接里的位置

**改哪两行**（`rtl\mmt\mmt_top.v`，当前行号 783 / 798）：

```verilog
// 原
.s_axi_awvalid  ({tml_awvalid,  soc_ddr_awvalid,  fb_awvalid  }),   // [2]=tml [1]=soc [0]=fb
.s_axi_wvalid   ({tml_wvalid,   soc_ddr_wvalid,   fb_wvalid   }),
// 诊断改成（只交换 s0<->s1 两个操作数，其余不动）
.s_axi_awvalid  ({tml_awvalid,  fb_awvalid,       soc_ddr_awvalid}),
.s_axi_wvalid   ({tml_wvalid,   fb_wvalid,        soc_ddr_wvalid }),
```

**为什么它决定性**：它把 `fb_awvalid` 从"互联第 0 位"挪到"互联第 1 位"。
- **若根因在互联的第 0 位**（那个口的通道没被消费）：折叠会**留在第 0 位** ⇒ 现在被折的变成 `soc_ddr_awvalid` / `soc_ddr_wvalid`，而 `fb_awvalid`/`fb_wvalid` 不再出现在 trimming 里。
- **若根因在写缓冲/RTL 侧**（`ddr_wr_buffer` 的输出本身被删）：折叠会**跟着信号走** ⇒ 仍然是 `fb_awvalid`/`fb_wvalid` 被折（`soc` 的一直活着）。

**预期读法**（`out\mmt.map.rpt` 的 trimming 段，baseline 那轮在 `:3561-3563`；X3 那轮在 `:3492` 附近）：

| 结果 | 含义 | 下一步 |
|---|---|---|
| `soc_ddr_awvalid`/`soc_ddr_wvalid` 变成 `(optimized to 0)`，`fb_*` 不再被折 | **根因在互联 s0 口**（S1 成立） | 查互联 IP 的 `S_ARRAY`/`ARB_MODE`/端口使能配置，考虑重新生成互联或换 `ARB_MODE` |
| `fb_awvalid`/`fb_wvalid` 仍被折 | **根因在写缓冲/RTL 侧**（S1 被否） | 转向 S3（工具），或做 Y2 |

**证明什么 / 不证明什么**：
- ✅ 证明"折叠是绑在位号还是绑在信号上"，从而把 **互联侧** 与 **写缓冲侧** 一刀切开。
- ❌ 不证明**具体**是互联的哪个内部机制；也不证明修好后的功能正确性（这只是一个只读报告的诊断，交换后 AXI 地址/数据是错配的，**绝不能上板**）。
- ⚠️ 附带影响：交换后 s0 的 AW 与 W 会落到不同口，AXI 语义被破坏 —— **只用于综合诊断**。若 Lead 想更保守，可**只交换 `.s_axi_awvalid` 一行**（观察 `fb_awvalid` 是否还被折），信息量略小但扰动最小。

### 3.3 不建议跑的实验（省 Lead 的时间）

| 实验 | 为什么不建议 |
|---|---|
| 把 `fb_awready` 钉 `1'b1` | **原理上无效**：`state[0]≡0` 说明连 state 1 都没到，而 state 0→1 不经过任何 AXI 握手（`ddr_wr_buffer.v:413-416`）。钉 ready 最多让 state 停在 1/2，不可能解释现象 |
| `checker0` 写通道直连 DDR3 | DDR3 控制器只有 **1 个 AXI 从口**（`mmt_top.v:1001/1024` 显示 `s_axi_awlock(s_axi_awlock[0])` 单口），s1/s2 还要用互联 ⇒ 必须拆互联或加 mux，**不是"最小改动"**，且会同时改变 s1/s2 的行为，结论不干净 |
| `.wr_busrt_len` 钉常量 | `burst_len` 只影响 `ddr_awlen`/地址步进（`ddr_wr_buffer.v:155-303`），不参与 state 0→1；且 X1 已证明"喂给 FSM 的输入不敏感"，同族实验价值低 |
| 再把 `i_de/i_vs` 钉常量 | 方向上只会让折叠更彻底（task-13 §3.1 已说明） |

## 4. BRAM 预算结论

### 4.1 三种情形（**实测 + 算术**）

| 情形 | BRAM | 占 256 | 依据 |
|---|---|---|---|
| 现状（写通路不在网表里，X3 那轮） | **218** | 85.2% | `mmt.place.rpt`（X3 轮）；baseline 那轮是 **222**（`:339`） |
| 写通路修好、只回写 FIFO | **235** | **91.8%** | +13（`u_wr_fifo` 128b×1024 = 13；厂商实测 13，`ti60f225_oob.res.csv:128`） |
| 写通路修好、**CSI RX 的像素侧 FIFO 一起回来** | **267** | **104.3%** | +13 +32（CSI RX 现 4 vs 厂商 36）⇒ **超容量，装不下** |

### 4.2 建议：**现在就上 task-5 的 R1+R2+R5（−26），不要等**

| 条目 | 改动 | 省 | 类型 |
|---|---|---|---|
| R1 | `rtl\mmt\mmt_top.v:665` `RD_FIFO_DEPTH 1024→512` | **−6** | 纯 RTL，零 IP 风险 |
| R2 | `ip\sapphire_soc\settings.json:80` `OCRSize 32768→16384` | **−16** | 重生成 SoC IP（固件只用 3089 B） |
| R5 | `ip\sapphire_soc\settings.json:70-71` `ICacheSize`/`DCacheSize 4096→2048` | **−4** | 重生成 SoC IP |
| | **合计** | **−26** | 目标基线 **196** |

**为什么现在就上**（三条理由，都独立成立）：
1. **与写通路是否修好无关** —— 这三条的收益是确定的，早做不浪费、也不会因为写通路问题而失效（其中 R1 恰好在读缓冲侧，是活的那条通路）；
2. **对三种情形都装得下**：196 → （+13）**209 = 81.6%** → （+45）**241 = 94.1%**；
3. **不上就装不下**：如果 CSI RX 那 32 块真跟着回来，222+45 = **267 > 256**，工程直接不收敛；而 241 虽然紧（94.1%）但可收敛，仍留 15 块余量。

**留作后手**（不要现在做）：`TINYML_CACHE ENABLE→DISABLE`（−22）—— 它能把预算再压到 219，但代价是**推理时权重全走 DDR、明显变慢**，应在"确认真的需要"时再动。

**⚠️ 顺序建议**：**先跑 Y1**（2 分钟，只动 `mmt_top.v` 两行）—— 它是唯一能立刻把根因劈成"互联侧 / 写缓冲侧"的实验；拿到 Y1 结果后再决定 R1+R2+R5 是一次上还是分批（R1 是纯 RTL 可以先做，R2/R5 要重生成 SoC IP、涉及固件，建议放同一批）。
