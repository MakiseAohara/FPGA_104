## 2. 逐项改动

### 2.1 任务3 ⑤ 低功耗场景管理

- **状态机**：`ACTIVE` ⇄ `IDLE`。连续 `LP_IDLE_FRAMES = 30` 个"静止帧"（`!motion && area < LP_AREA_TH=500`）进 IDLE；
  任一帧 `motion || area >= 500` **立即**回 ACTIVE（滞回，不累计）。
- **IDLE 动作**：① 不刷热力图（省 768 次 APB 写）② 主循环节流 ×2 ③ 不发起任何加速器命令。
- **可观测**：串口新增 `[LP] mode=… idle_f=… thr=… enter=… ctrl=…`；OSD 第 0 行尾追加 ` LP`。
- ⚠️ **诚实边界（重要）**：
  - **没有降低摄像头输出帧率** —— 那要改 `cam_i2c_ctrl` 的固定 ROM 表，超出范围
  - **没有实测功耗收益** —— 没有功率计，无法量化
  - 「关闭神经网络推理」目前是"不调用"（TinyML 本来就是 `DISABLE`）
  - **为什么不在 IDLE 关帧差（MMT_CTRL bit0）**：`mmt_frame_diff.v:165` 是 `frame_active <= enable && …`，
    关掉后 `frame_tgl` 不再翻转，而唤醒的唯一依据就是它 ⇒ **永远退不出 IDLE**。
    这是 Claude 独立核查时发现并推翻了我最初规格里的写法。
  - `[LP]` 的 `ctrl=` 是**固件影子值**，不是读回值 —— 已核实 `0x48` 只出现在 `mmt_soc_regs.v:482` 的**写** case 里，
    读多路器（`:361-416`）没有它 ⇒ 读 `MMT_CTRL` 恒为 0。

### 2.2 任务2「非授权时段」可变化输入（串口命令）

原状态：`sw\main.c` 把 `hour` 写死 0 ⇒ `in_auth_window` 恒真（`0 < 6`），无法演示"白天不报、夜里报"。

**为什么用串口而不是 KEY**：UART RX 通路**本来就通** —— `sw\uart.c:98-115` 已有 `uart_rx_ready()/uart_getc()`；
`rtl\mmt\mmt_top.v:189,1543` 与 `rtl\mmt\soc\mmt_soc_subsystem.v:400` 都已接线。
KEY1/KEY2 在 GPIOR_21/22 但当前设计未使用，要加得动 peri.xml + 顶层端口 + 同步器 + 消抖，代价高得多。

| 键 | 效果 |
|---|---|
| `d` / `D` | 白天：`hour=12` → 不在授权窗口 → **不报警** |
| `n` / `N` | 夜间：`hour=23` → 在授权窗口 → **可报警** |
| `0`–`9` | 直接设小时（试 6 / 22 边界） |
| `?` | 打印当前 hour / 阈值 / 图案状态 |

回显的窗口判定与 RTL **同构**（`mmt_fusion_vote.v:129-132` 的跨零点分支）：
`(hour >= auth_beg) || (hour < auth_end)`；默认 22-6 是跨零点分支。

⚠️ **UART RX 是否真的接到 FT4232 的 TX，未上板验证**（`i_uart_rxd` = GPIOL_02，`mmt.peri.xml`）。

### 2.3 任务1 预处理：异常值剔除 + 滑动平均

原状态：**时间戳对齐已实现**（`align_nearest()`），缺"异常值剔除"和"传感器滑动平均"。

- 通用 `pre_filter_t` + `pre_init()` / `pre_push()`（全定点，无浮点）
- **剔除**：新值与上次有效值之差 > 阈值 ⇒ 丢弃（不入窗、不动 last），计数
- **平均**：N=4 点环形窗滑动平均
- **单位不写死**：阈值由调用方传 —— SHT30 环境温 ×100 用 `500`(5.00℃)；MLX 最高温 ×10 用 `150`(15.0℃)
- **首次样本无条件接受**（否则建不起 baseline）
- **重同步**：连续 8 次被剔除 ⇒ 认定是真实阶跃，清窗重建基线（否则真实温跃会被永久丢弃）
- **遥测**：新增 `[PP] A raw=… flt=… rej=… B raw=… flt=… rej=… win=4 thrA=500(x100) thrB=150(x10)`

⚠️ 两个阈值都是**估的**，需要上板按 `[PP]` 里 `rej` 的增长标定。
⚠️ 更大的限制：MLX 的 `ir_compute_temps()` 仍是占位算法（文件内已标 TODO），
   在移植 Melexis 官方换算前，体温这一路的阈值**没有标定意义**。

### 2.4 ★ 测试图案命令（补上一个真缺口）

**发现**：交接的 checklist §2 要求做 M0（测试图案证明 写DDR→读DDR→显示），
但 `main.c` **从不调用 `MMT_TEST_PATTERN_SET`**，也没有任何从主机写 SoC 寄存器的通路
⇒ **M0 在当前固件上根本做不了**。（Claude 独立核查发现）

| 键 | 效果 |
|---|---|
| `t` | 开测试图案（mode 0 = 8 色彩条 + 移动方块） |
| `o` | 关，切回摄像头 |
| `p` | 循环：关→彩条→纯红→纯绿→纯蓝→关（顺便验证 R/B 有没有交叉） |

### 2.5 融合阈值现场调节

Claude 的演示数学：`vprob` 需 **≥193**（即帧差面积 ≈1930，约占降采样画面 10%）才够默认阈值 154。
挥手幅度不够会一直不报警。

| 键 | 效果 |
|---|---|
| `+` / `=` | 得分阈值 +8（Q8，上限 255） |
| `-` / `_` | 得分阈值 −8 |

### 2.6 ★ 两个"不依赖主机输入"的兜底

因为 UART RX 未验证，M0 又必须做，所以：

1. **开机先开测试图案**，跑 `BOOT_PATTERN_ITERS = 400` 个主循环周期（估 8~12 秒）后
   **自动切回摄像头**。⇒ 不插摄像头也能在 HDMI 上看到彩条+方块，同时 `[WR] AW/W`、`[AMAX] az=` 应有数可看。
   固定自动关闭（不受串口命令影响），保证可预测。
2. **若始终收不到任何串口字节**（`auto_demo` 仍为 1），每 `AUTO_SWITCH_FRAMES = 900` 个循环周期
   自动翻转 `hour` 12 ⇄ 23 ⇒ 串口 RX 不通时，"切夜间才报警"仍能演示。
   **一旦收到任何字节即永久交出控制权**。

## 4. 上板必验清单（按顺序）

1. `[BOOT] test pattern ON` 串口行是否出现 → 证明固件在跑
2. HDMI 是否出现**8 色彩条 + 移动方块**（≈10 秒）→ **M0 的画面证据**
3. 测试图案期间 `[WR] AW/W` 是否持续增长、`az=OK`
4. 之后是否出现 `[BOOT] test pattern OFF -> camera`，画面切走
5. 串口敲 `?` → 是否回 `[CMD] hour=…` ⇒ **UART RX 通了**
6. 敲 `n` / `d` → `AUTH` 位是否跟着变 ⇒ 非授权时段可控
7. `[PP]` 行是否出现、静态时 `rej` 是否不涨
8. `[LP]` 行是否出现；静置约 30 帧后 `mode` 是否变 `IDLE`，OSD 是否出现 ` LP`
9. 敲 `t` 再敲 `p` 循环，确认**红是红、蓝是蓝**（R/B 交叉修复的硬件验证）
