# 实测：2025.1 复现写通路折叠 + ice=0 修复验证（2026-10-18）

> 环境：**本机** Efinity **2025.1.110**（补丁 2025.1.110.5.9），工程取自 `F:\mmt\mmt`（复制到工作区，**未改动原件**）。
> 目的：在没有 FPGA 板子的情况下，用真实工具链回答三个一直靠推断的问题。
> 方法：`efx_map` 直调（2025.1 用 `--project-xml`/`--v`，**不接受 2026.1 的 `--prj`**；工程 XML 由 2026.1 写，2025.1 解析不了，故改用 `--v` 逐条喂源文件）。

## 1. 三组实验数据（Efinity 2025.1.110，同一工程、同一源文件集）

| 配置 | EFX_LUT4 | EFX_FF | SRL8 | RAM10 | DPRAM10 | **BRAM** | `fb_awvalid~FF` 的 `.D` |
|---|---|---|---|---|---|---|---|
| **A. ice=3（原始工程）** | 28,026 | 21,719 | 1,230 | 231 | 4 | **235** | `.D(1'b0)` ❌ **折叠** |
| **B. ice=0（原始工程）** | 48,963 | 28,232 | 440 | 231 | 4 | **235** | `.D(n1254)` ✅ 真实逻辑 |
| **C. ice=0 + 摘 TinyML（本补丁）** | **34,512** | **21,647** | 356 | **198** | 4 | **202** | `.D(n1254)` ✅ 真实逻辑 |

网表原文（A vs C）：

```verilog
// A: ice=3
EFX_FF \fb_awvalid~FF  (.D(1'b0), .CE(ceg_net5678), .CLK(core_clk), .SR(dbg_fb_sb2[31]), .Q(fb_awvalid))
EFX_FF \fb_wvalid~FF   (.D(1'b0), .CE(ceg_net6361), .CLK(core_clk), ...

// C: ice=0 + 摘 TinyML
EFX_FF \fb_awvalid~FF  (.D(\checker0/u_ddr_buffer/ddr_wr_buffer_inst/n1254 ), ...
EFX_FF \fb_wvalid~FF   (.D(\checker0/u_ddr_buffer/ddr_wr_buffer_inst/n1255 ), ...
```

**读法**：`.D(1'b0)` 意味着这个触发器**永远装不进 1** ⇒ `awvalid` 恒 0 ⇒ 一个 AXI 写都发不出去。
C 里 `.D` 指向真实组合网络 ⇒ 次态逻辑回来了。

## 2. 容量：为什么这次装得下

2026.1 上的已知数（你 10-16 的记录）：

| 项 | 值 |
|---|---|
| ice=3 整机 XLR | 45,017 |
| ice=0 整机 XLR | **60,833** ← 超器件 60,800，差 33，PnR 失败 |
| `u_tinyml_accel` XLR（hier_util） | 15,647 |

⇒ **ice=0 + 摘 TinyML ≈ 60,833 − 15,647 = 45,186 XLR**（余量约 15,600）。

这与本次 2025.1 的实测方向一致（LUT4 48,963 → 34,512，−14,451）。

**BRAM**：235 → **202**（−33，正好是 TinyML 那份），余量 54 块。
写 FIFO 修好后即使再 +13 块也只到 215，仍有余量。

> ⚠️ 跨版本数字不能逐位对齐（2025.1 的 LUT4 计数比 2026.1 高），但**方向和量级一致**，
> 且 2026.1 的 45,186 是用你自己的两个实测数相减得到的，可信度最高。

## 3. 一个被本次实测抓出来的真 bug（已在补丁里修掉）

第一版补丁在 2025.1 上报：

```
ERROR : mmt_top.v(1762): constant is not allowed here [VERI-1180]   × 9 行
```

**原因**：Efinity **不允许在模块例化的端口连接处直接写常量**。第一版写的是：

```verilog
.ci_cmd_ready (1'b0),      // ❌ VERI-1180
```

**修法**：先声明成 wire，端口连 wire 名：

```verilog
wire ci_cmd_ready_tie = 1'b0;          // 在 else 块里声明
...
.ci_cmd_ready (ci_cmd_ready_tie),      // ✅
```

修完后 C 组综合**退出码 0**。

> 这个 bug 如果没在本地工具链上跑过，会在你那台机器上白烧一次 6 分钟的综合。
> **这就是为什么值得在本机先跑一遍**。

## 4. 顺带推翻的一条旧结论

`docs/帧缓冲写通路根因-4.md` §3 把"换 Efinity 2025.2"列为**成功概率最高**的方案（依据是"同一份厂商工程在 2025.2 上综合是好的"）。

本次实测：**2025.1 同样把 `fb_awvalid` 折成 `.D(1'b0)`**。

⇒ 那个"厂商工程能过"的证据，不能外推到我们这个设计（三主口 AXI 互联 + SoC + TinyML 的规模/结构才是诱因）。
**⇒ 别再把"换版本"当主方案**，`infer-clk-enable=0` + 摘 TinyML 才是对症的。

## 5. 本次实验怎么复现（本机，供下次用）

```powershell
$efx='F:\Efinity'; $d='<工程副本>'
$env:EFINITY_HOME='F:/Efinity'; $env:EFXPT_HOME="$efx\pt"; $env:EFXIPM_HOME="$efx\ipm"
$env:PYTHONHOME='F:\python311'
$env:PATH="F:\python311;$efx\bin;$efx\scripts;"+$env:PATH

# 2025.1 不接受 --prj，工程 XML（2026.1 写的）也解析不了 ⇒ 用 --v 逐条喂源文件
# 源文件清单 = XML 里所有 <efx:design_file .../> + 3 个 ip_src_file
& "$efx\bin\efx_map.exe" --project mmt_cut --root mmt_top `
  --device Ti60F225 --family Titanium `
  --work-dir "$d\work_syn_cut" --output-dir "$d\out_cut" --I $d `
  --v <每个源文件> ... `
  --write-efx-verilog "$d\out_cut\mmt.gate.postsyn.v" `
  --infer-clk-enable 0
```

**耗时约 5 分钟/次**（比 2026.1 快）。判定看 `out_cut\mmt.gate.postsyn.v` 里
`EFX_FF \fb_awvalid~FF` 那一行的 `.D(...)`。
