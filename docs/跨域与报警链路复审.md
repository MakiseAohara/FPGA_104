## 2. 修复② 的功能等价性复审（逐行证据）

### 2.1 OSD 里 `alarm` 到底怎么用（不是纯组合，会进触发器）

`rtl\mmt\osd\mmt_osd_overlay.v`：

| 行 | 内容 | 含义 |
|---|---|---|
| `:92` | `input wire alarm;` | 端口声明 |
| `:157-158` | `wire in_border = (x_cnt < BORDER) \|\| (x_cnt >= H_ACTIVE-BORDER) \|\| (y_cnt < BORDER) \|\| (y_cnt >= V_ACTIVE-BORDER);` | 边框区域判定，源是**视频域**的 `x_cnt/y_cnt`（`:115-137`，`posedge vclk`） |
| `:160` | `wire show_border = alarm & in_border;` | **唯一一处组合使用 `alarm`** |
| `:213` | `s1_show_border <= show_border;` | **在 `vclk` 域打第 1 拍** |
| `:242` | `s2_show_border <= s1_show_border;` | 第 2 拍（4 级流水的一部分） |
| `:286-288` | `if (s2_show_border) o_r<=FF;o_g<=00;o_b<=00;` | 最终画红框 |

⇒ 修复前，`alarm` 端口接的是 **core 域**信号 `alg_alarm_s`，它被 `in_border`（视频域组合）与 `show_border` 混合后**送进视频域触发器的 D 端**（`:213`）。这**正是** `out\mmt.timing.rpt` 里 `core_clk → hdmi_tx_slow_clk` 那类失败路径的形状：一条跨域组合路径 + 视频域单级采样。修复后源与目标同域，问题消失。

### 2.2 `alg_alarm` 的产生逻辑与时钟域：**是视频域、是持续电平**

`rtl\mmt\algo\mmt_fusion_vote.v`：
```
138: always @(posedge clk or negedge rst_n) begin
139:     if (!rst_n) begin alarm <= 1'b0; ...
142:     end else begin
143:         alarm_valid <= 1'b0;
145:         alarm       <= (score >= {1'b0, score_thresh}) && in_auth_window;
146:         alarm_valid <= 1'b1;
```
- `:145` 是**每拍重新计算并寄存** ⇒ `alarm` 是**对条件成立的持续电平**（条件成立就一直是 1），**不是单周期脉冲**。因此视频域直接用它**不需要**额外滤波或展宽。
- 时钟：`mmt_top.v:1670` `u_algo .clk(hdmi_tx_slow_clk)` → `mmt_algo_subsystem.v:109-110` `mmt_fusion_vote u_fusion (.clk(clk) ...)` ⇒ `alarm` 确实住在 `hdmi_tx_slow_clk` 域；`mmt_top.v:1707` `.alarm(alg_alarm)`。
- 输出条件里的 `score` / `in_auth_window` 由 `sy_vision_prob / sy_body_max_t / sy_hour ...` 等**同步后的准静态量**驱动（`mmt_top.v:1677-1700`）⇒ `alarm` 的翻沿只发生在"配置/状态变了"时，量级是秒级，不会高速抖动。

**对照 `alg_alarm_s`**：`mmt_top.v:1725-1731`
```
1725: mmt_sync2 #(.WIDTH(4)) u_sy_fl (.clk_b(core_clk), ... .d_a({alg_alarm, alg_in_auth, alg_motion_done, alg_motion_flag}), .q_b(alg_flags_s));
1731: wire alg_alarm_s = alg_flags_s[3];
```
`mmt_sync2.v:30-40` 是"两级触发器的**第一级吃异步输入**、第二级输出"的标准同步器 ⇒ `alg_alarm_s` = `alg_alarm` 经 **2 拍 core_clk 延迟**后的 core 域副本（4 位按位同步，bit3 独立，不存在相干性问题）。

### 2.3 判定

1. **逻辑等价**：`alg_alarm_s` 就是 `alg_alarm` 延后 2 个 core 拍的副本，**不是另一个信号**。OSD 只是"从哪条路取这个报警"变了。
2. **可见行为差异（唯一一条）**：红框的出现/消失边沿提前 **2 个 core 拍 = 20 ns**（相当于 **2.8 个视频像素**，视频周期 7.143 ns）。红框厚 8 px、报警是帧级持续状态 ⇒ **不可见**，且不会"晚/早一帧"。
3. **修复前是负收益而非等价**：core 域电平被视频域单级触发器采样，`alg_alarm_s` 的翻沿与 `vclk` 无固定相位 ⇒ 采样点可能落在建立/保持窗口内，存在**亚稳态 → 红框边沿随机抖动一个像素甚至整拍**的概率；且该路径在约束上是 `0.001 ns`（不可满足）。修复②把这条不确定性**彻底删掉**。
4. **结论：修复② 正确、功能等价（差异 ≤20 ns 且不可见）、且严格优于修复前。**

### 2.4 附带发现（不影响判定，供 Lead 决定是否处理）

## 4. ★ 复核 SDC 第 37 行作用域：它**顺带切断了同源 2:1 的 `vid_clk_dvi2 ↔ hdmi_tx_slow_clk`**

这一条是本次复审最重要的发现，也是 task-4 第 3 项要求回答的问题。

### 4.1 工具语义（先摆依据，避免凭经验）

`D:\Efinity\2026.1\doc\topics\constraint-set-clock-groups.html` 原文：

> This command instructs the timing analyzer to **not analyze paths between one or more specified groups of clock domains in either direction**. …
> If you specify **only one clock group**, it cuts all paths to and from the specified clock domain(s) to all others.

`D:\Efinity\2026.1\doc\topics\tim-add-clock-set-clock-groups.html` 原文：

> If you later add an additional clock, clk5, and do not update the constraints, **the software assumes that clk5 is synchronous to all other clocks.**（多组写法）
> … each set_clock_groups constraint only specifies one group, which tells the software that the clocks in a given group are asynchronous to all others.（单组写法）

**按字面语义**：第 37 行只有 `{core_clk}` 和 `{hdmi_tx_slow_clk}` 两个组，`vid_clk_dvi2` 不在其中 ⇒ **理论上不该影响 `vid_clk_dvi2 ↔ hdmi_tx_slow_clk`**。Lead 在 `sdc:33-36` 注释里"故意不并进第 26 行大组"的意图，从文档语义看是站得住的。

### 4.2 实测证据：**现象与该语义不符**

时钟关系数量（Setup 与 Hold 两节、以及 `efx_pnr.log` 的表格，四处一致）：

| 版本 | 关系条数 | 含 `vid_clk_dvi2 ↔ hdmi_tx_slow_clk`？ | 含 `core_clk ↔ hdmi_tx_slow_clk`？ |
|---|---|---|---|
| 修复前（二手：`docs\时序与CDC问题分析.md:59-74`、`:182` 明写"Setup Clock Relationship 共 16 行"） | **16** | **有**，`:71` = 10 条，最差 **+3.741 ns**，约束 7.143（`:269` 引用 `timing.rpt:7523`；`:326` 再次确认） | 有（两个方向） |
| 修复后第 1 轮 19:24–19:27 | **13** | **无** | 无 |
| 修复后第 2 轮 19:39–19:41（当前） | **13** | **无** | 无 |

当前 13 条（`out\mmt.timing.rpt:61-73`）：
```
core_clk→core_clk 3.673 | core_clk→tx_cal_clk_90edge 1.143 | tx_cal_clk_90edge→core_clk 1.833
tx_cal_clk_90edge→tx_cal_clk_90edge 0.417 | tx_cal_clk_90edge→tx_cal_clk 1.158
```

- 这不是"正好不关键所以没打印"：同一张表里 `CLK_5M→CLK_5M` 的 slack 是 **+196.684 ns**（远远不关键）却照样打印 ⇒ **该表是按"被分析的关系"逐条打印的**，没有按关键度筛选。
- 像素通路的端点在整个报告里**一次都没出现**：`hdmi_tx_de` / `hdmi_tx_rdata` / `hdmi_tx_gdata` / `hdmi_tx_bdata` / `rgb_datax2` 在 `out\mmt.timing.rpt` 中的出现次数**都是 0**（`w_debayer` 也是 0），而 `vid_clk_dvi2` 出现 166 次全部落在 `vid_clk_dvi2 vs vid_clk_dvi2` 一节里（`:5372-5382` 最差路径是 `checker0/u_ddr_buffer/...` 内部路径）。
- 元数据也支持"关系被切"而不是"路径不存在"：`mmt_top.v:1063-1074` 用 `hdmi_tx_slow_clk` 采样 `rgb_datax2/rgb_vs/hs/de`，而 `rgb_datax2` 由 `debayer_top` 的 `in_pclk = vid_clk_dvi2`（`:1041`）域寄存器组合产生 —— `rtl\debayer\debayer_top_2to1.v:142-152`（`o_r/o_g/o_b` 出来即组合成 `rgb_datax2_o`），而这些寄存器在 `rtl\debayer\raw_to_rgb.v:146-216`（`always @(posedge i_pclk)`）里打拍、`:397-399` 直接 `assign` 到 `o_r/o_g/o_b` ⇒ **这条跨域路径在 RTL 里真实存在**，不可能"没有路径"。

### 4.3 判定与不确定度（如实写）

- **可确证的**：当前工程里 **`vid_clk_dvi2 ↔ hdmi_tx_slow_clk` 这条"同源 PLL、真实 2:1 的同步路径"已经不再被 STA 分析**（两轮独立重跑一致）。这正是 Lead 在 `sdc:33-36` 想避免的"误伤"。
- **无法确证的**：Efinity 内部为什么把它切掉。两种可能我都没有直接证据：
  - (a) 实现层面：Efinity 维护一张**全局时钟组表**，任何出现在某个 `-group` 里的时钟与**其它组**的时钟一律视为不相关；`hdmi_tx_slow_clk` 因第 37 行第一次进入该表，于是同时与 `core_clk`（本意）**和 `vid_clk_dvi2`**（第 26 行的组成员，副作用）成了不相关。这个模型能同时解释"修复前 16 条 / 修复后 13 条 / 第 26 行确实生效（`core_clk×vid_clk_dvi2` 一条路径都没有）"三件事，也能解释"`tx_cal_clk_90edge` 不在任何组里所以仍被分析"（`:62-65`）。
  - (b) 报告选择性地只打印了部分关系。
  - 二者都**无法用现有产物判定**，唯一干净的验证办法是 Lead 在 Efinity Tcl 控制台跑一次 `report_timing -from [get_clocks vid_clk_dvi2] -to [get_clocks hdmi_tx_slow_clk]`，或在重跑后看 `out\mmt.timing.rpt` 的 `Clock Relationship Summary` 是否重新出现该行。
- ⚠️ 注意：**不能**用 `out\mmt.cdc.rpt` 的"No Synchronizer warnings"来反驳本结论——该报告检查的是同步器结构，**不检查"关系是否被约束切断"**。

### 4.4 建议的修法（**仅建议，本次未改任何文件**）

**首选：把第 26 行与第 37 行合并成一条，并把同源的两个输出放进同一个组。**

```tcl
# 替换 constr\ti60f225_oob.sdc:26 与 :37 两处
set_clock_groups -asynchronous \
    -group {core_clk} \
    -group {vid_clk_dvi2 hdmi_tx_slow_clk} \
    -group {tx_cal_clk} \
    -group {CLK_5M} \
    -group {i_mipi_rx_pclk} \
    -group {sdram_clk} \
    -group {rx_cal_clk}
```

为什么这样写（对 4.3 的两种可能**都成立**）：
- `core_clk` 与 `{vid_clk_dvi2 hdmi_tx_slow_clk}` 不同组 ⇒ `core↔hdmi`、`core↔vid` 都被切断（修复①的意图保留）。
- `vid_clk_dvi2` 与 `hdmi_tx_slow_clk` **同组** ⇒ 它们之间仍是"相关时钟"，STA 继续按 2:1 做同步分析 ⇒ **同源 2:1 通路重新受检**。
- 其余 5 个时钟保持互斥；`tx_cal_clk_90edge` 不在任何组（与现状一致，它当前有 4 条关系且都通过，见 `out\mmt.timing.rpt:62-65`）。
- 合并成**一条**命令可以避免"多条命令之间怎么合并组"这种实现相关的不确定性。

**备选（改动最小，但依赖实现行为，需重跑验证）**：只把第 37 行改成
`set_clock_groups -asynchronous -group {core_clk} -group {vid_clk_dvi2 hdmi_tx_slow_clk}`
——它要求 Efinity 把 `vid_clk_dvi2` 的新组成员关系与第 26 行已有成员关系**合并**；若工具报错或行为不符，回退到首选方案。

**验收标准（重跑 `efx_map`+`efx_pnr` 后）**：
1. `out\mmt.timing.rpt` 的 Setup 表应为 **14 行**，其中**重新出现** `vid_clk_dvi2 vs hdmi_tx_slow_clk`（预期 +3.7 ns 量级），且**仍然没有** `core_clk` 与 `hdmi_tx_slow_clk` 的组合行；
2. 负 slack 仍为 0 条；`hdmi_tx_slow_clk vs hdmi_tx_slow_clk` 最差仍 ≈ +1.4 ns；
3. `out\mmt.cdc.rpt` 仍无告警。

### 4.5 为什么这条不能不管（风险）

被切断的路径不止一条，且都属"实际在跑的图像通路"：

| 位置 | 跨的域 | 说明 |
|---|---|---|
| `mmt_top.v:1063-1074` | `vid_clk_dvi2` → `hdmi_tx_slow_clk` | 48 位像素 `rgb_datax2` + `rgb_vs/hs/de` 直接进 `hdmi_tx_*` 寄存器，靠 `vid_cnt`（`:1065`）交替取高低 24 位。**这是 HDMI 画面能不能出图的关键通路** |
| `mmt_top.v:1248`（`.rst_p(~vid_rst_n)`） | `vid_clk_dvi2` → `hdmi_tx_slow_clk` | `dvi_encoder_m0` 是 `hdmi_tx_slow_clk` 域（`:1247`），复位信号却来自 `vid_rst_n = dly_cnt[26]`（`:1116-1126`，`vid_clk_dvi2` 域） |
| `mmt_top.v:674` | `vid_clk_dvi2` → `core_clk`/`i_mipi_rx_pclk`/`vid_clk_dvi2` | `checker0`(frame_buffer) 的 `rst_n` 是 vid 域信号，但该模块内含三个时钟域（`:673` axi_clk=core、`:676` i_clk=i_mipi_rx_pclk、`:681` o_clk=vid_clk_dvi2） |

这三条里，`frame_buffer` 那条其实**已被厂商正确处理**（它内部给了每个域一个 `rst_n_piple` 复位同步器，见 §6），前两条则完全依赖"两个时钟同源 2:1"这个前提。这个前提在当前 `mmt.peri.xml:340-341`（同一 USER_PLL、divider 40/20、`phase_setting=0`、不反相）下成立，但**一旦有人改 PLL divider/换 PLL/加 `-exclusive` 大组，就会静默地变成"没有 STA 保护的真跨域"**——这正是要把这条检查恢复的原因。

## 6. 复位跨域（独立小节，因为它是本次唯一的"新违规"）

- `mmt_top.v:472`：`w_arstn` 是**三个 PLL lock 引脚的组合与**（`i_pll_locked`、`pll_locked`、`user_pll_locked`，都是顶层输入，异步）。
- 它被当作**异步低有效复位**直接用在整个设计的两大域上：video 域 `mmt_top.v:1359`(`u_osd.vrst_n`)、`:1671`(`u_algo.rst_n`)、`:1309`、`:1655`、`:1740`；core 域 `:1426`(`u_soc`)、`:1586`(`u_sensors`)、`:1758`(`u_alarm`)、`mmt_top.v:876/890`(TinyML) 等。
- **问题**：异步**置位**没问题，问题在**释放沿**——它相对 `core_clk` 与 `hdmi_tx_slow_clk` 都是异步的，各域触发器可能在自己的时钟沿附近脱离复位 ⇒ recovery/removal 违例（表现为上电后个别寄存器进入未定义态，且在实验室很难复现）。
- **工具是否检查了？** 这三根引脚在 `constr\ti60f225_oob.sdc` 里没有 `create_clock`/`set_input_delay`；当前 `out\mmt.timing.rpt` 也搜不到任何与复位相关的路径 ⇒ 判定为 **"未被检查"**，而不是"检查通过"。
- **对比**：厂商 `frame_buffer` 用 `rtl\frame_buffer\rst_n_piple.v` 给每个时钟域各做一份复位同步（`frame_buffer.v:122-146`），这是正确范式。
- **建议（RTL 改动，交由 Lead，本次未改）**：为 `core_clk` 与 `hdmi_tx_slow_clk` 各加一个 2~3 级复位同步器（可直接复用 `rtl\frame_buffer\rst_n_piple.v`），再分发给各自域；或在 SDC 里给三根 lock 引脚补输入延迟约束，让 STA 至少检查一次。优先级低于 §4（不影响当前"时序全过"的结论，属上电可靠性）。
