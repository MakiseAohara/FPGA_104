## 二、两个"一度改错、已撤回"的判断（教训）

### 1. 我照抄厂商的 hs/vs 交叉 —— **错，已撤回**
厂商参考顶层 `ti60f225_oob_top.v:966-967` 把 `i_hs`/`i_vs` 交叉接进编码器。我照改了。
**被明文 `dvi_encoder.v` 推翻**（板卡资料包 `02_Ti60F225_hdmi_demo` 里有一份明文）：
```
:324  encode encb (            // 蓝通道
:329    .c0 (ram_hs_r[...]),   // i_hs → c0
:330    .c1 (ram_vs_r[...])    // i_vs → c1
```
TMDS 蓝通道 `{c1,c0}` = `{VSYNC,HSYNC}` ⇒ **端口名是字面意思**。
厂商 v1 的交叉是 bug：**同一 demo 的 v4/v5/v6 已改回直连**；`02_hdmi_demo`、`03_hdmi_tx_demo`、`09_hdmi2dsi` 也都是直连。
⇒ **我们原来的"不交叉"是对的。现在是 `.i_hs(osd_hs)` / `.i_vs(osd_vs)`。**

### 2. `video_format` 悬空 —— **真缺陷，修复保留**
`out\mmt.warn.log` 里 Efinity 自己报了 6 条 `VDB-1002 does not have a driver` + 1 条 `VERI-1330`（位宽 1 vs 2），
涉及 `video_format` / `audio_L` / `audio_R` / `audio_valid` / `audio_samp_freq` / `audio_samp_word_len`。
已在 `mmt_top.v` 显式驱动（`video_format = 2'b00` RGB，音频全 0）。厂商参考顶层同样悬空，属遗留缺陷。

## 三、★ 观测量可信度问题（今晚的"方法论教训"）

调试寄存器 **`0xE4`（走 `test_rdata`）读回的值不可信**，证据两条：
1. 它 `[31:24]` 放的**常量 `8'hA5` 读回来是 `0x00`** —— 常量被读成 0
2. `[11:8]` 的 `pos_sync` 计数**饱和到 15**，而 `[7:0]` 的 `sb_pos_sync` 粘滞位却是 **0** —— 两者同 `always` 块、同钟同复位，逻辑上不可能不一致

⇒ 已把 DDR 诊断**搬到 `0xE0`（走 `test_wdata`，实测可信：读到 `0x1F` 五位全对）**。

### 由此确立的纪律：**路标位**
**每换一版位流，调试寄存器的最高字节放一个不同的常量；串口读到它才谈得上分析其它位。**
- 上一版：`0xA5`
- **当前版：`0xA6`**

## 四、DDR 写通路（`AW=0`）—— 现状与下一步

### 已排到很窄的范围（全部用可信通道 `0xE0` 实测）

上一版 `dbg=0xA5AF901F`（多次采样）解码：

| 位 | 含义 | 实测 | 结论 |
|---|---|---|---|
| `[31:24]` | 路标 | `A5` | ✅ 通道可信 |
| `[23]` | `rst_n` | 1 | ✅ 复位已释放 |
| `[22:20]` | `axi_clk` 计数器 | 在变 | ✅ 时钟在跑 |
| `[19:16]` | `pos_sync` 计数 | **15（饱和）** | ✅ 触发发生了 |
| `[15:13]` | `rdusedw[10:8]` | **4 ⇒ 1024** | ✅ **写 FIFO 满** |
| `[12]` | `wr_req` | **1** | ✅ **请求成立** |
| `[11:10]` | `state` | **0（恒 0）** | ❌ **FSM 从未离开 state 0** |
| `[9]`/`[8]` | `awvalid`/`awready` | 0 / 0 | ⇒ 因为 state 没到 2 |

**⇒ 所有前置条件都满足（FIFO 满、`wr_req`=1、`pos_sync` 发生），FSM 就是不动。**

### 三个候选假设（未证实，正在用观测区分）

| # | 假设 | 判据 |
|---|---|---|
| **H1** | `sync_r1`/`sync_r2` 没有 `preserve`，**被工具删了或折成常量** | `sync_r2_cnt`=0 且 `sync_r0_cnt`>0 |
| **H2** | `state` 被常量传播/折叠（Z5 实验已有先例） | `sync_r2_cnt`>0、`st1`=0、`sb_preempt`=0，state 仍恒 0 |
| **H3** | `sync_r0` 抢占（功能 bug） | `sb_preempt`=1 |

⚠️ **我原先的"`pos_sync` 持续多拍导致抢占"假设已被推翻**（Claude 推导：`start_sync` 序列 `00→01→11→…`，
`pos_sync` **每帧严格单拍**，单拍时 `sync_r0`/`sync_r2` 不会重叠）。

### 本版（路标 `A6`）新增的决定性观测

`dbg`（`0xE0`）新位表：

| `dbg_sb` 位 | `0xE0` bit | 内容 |
|---|---|---|
| [18] | 23 | `free_cnt[25]` |
| [17:14] | 22:19 | **`sync_r2_cnt`**（4 位饱和）★最关键 |
| [13:10] | 18:15 | **`sync_r0_cnt`** |
| [9:6] | 14:11 | `pos_sync_cnt` |
| [5] | 10 | `rdusedw[10]` |
| [4] | 9 | `wr_req` |
| [3:2] | 8:7 | `state` |
| [1] | 6 | `sb_st1`（粘滞） |
| [0] | 5 | `sb_pos_sync`（粘滞） |
| `[4:0]` of `test_wdata` | 4:0 | `frame_buffer` 的 5 个粘滞位（不变） |

`0xE4` 另放了 `rst_n`、`free_cnt[25:23]`、`awvalid`、`awready`、`sb_preempt` 等（该通道可信度未验证，仅作补充）。

**读法**：
- `sync_r2_cnt`=0 且 `sync_r0_cnt`>0 ⇒ **H1（工具删了同步链）** ⇒ 加 `preserve`
- `sync_r2_cnt`>0 且 `state` 恒 0 ⇒ 看 `0xE4` bit19 `sb_preempt`：1=H3（功能），0=H2（state 被折叠）
- 若 `sb_pos_sync` 仍与 `pos_sync_cnt` 矛盾 ⇒ **读数与 RTL 不对应**，先查位流/寄存器映射
