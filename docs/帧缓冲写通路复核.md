## 0. 结论（先看这个）

### 0.1 判定：**是死逻辑，不是厂商正常写法，也不是"被综合成 SRL"**

`checker0/u_ddr_buffer/ddr_wr_buffer_inst/u_wr_fifo` 这一整块 **128bit × 1024 深的写 FIFO 在 mmt 的网表里被完全删除（两个端口都死）**，导致 `frame_buffer` 的 **AXI 写通道完全不工作**。

- 它**不是**"用 SRL 实现了所以不占 BRAM"：厂商在同款工程里，同一个 FIFO 用的是 **13 块 BRAM**。
- 它**不是**"读时钟域被裁掉"：写侧 `FifoWrEn` 在 mmt 报告里也完全消失。
- 它是**真死逻辑**：`fb_awvalid` / `fb_wvalid` / `fb_wlast` / 写 FSM 的 `state[1:0]` 全部被综合器证明为常量 0。

### 0.2 严重性：**摄像头图像进不了 DDR3，视频链路在"写"这一半断掉**

s0（`frame_buffer`）是 DDR 互联上**唯一**的视频写入主口。它的写通道死掉 ⇒ 帧缓存区 `0x0200_0000` 永远不被摄像头数据更新；读通道（13 块 BRAM）是活的 ⇒ 屏幕会**持续显示 DDR 里的旧内容/未初始化内容**。详见 §4。

### 0.3 根因（追到哪一步）

综合器能把整条写通道折叠掉，说明 `ddr_wr_buffer.wr_start` 被证明恒为 0。
`wr_start` 的来源是 `frame_start & frame_stable`（`rtl\frame_buffer\frame_buffer.v:196`）。
**推断**：真正的常量源在 `frame_stable`（或 `frame_start`）——因为 `ser2par_32_128_v1` 的像素打包逻辑同样由 `frame_stable` 门控（`ser2par_32_128_v1.v:35,57`），而 mmt 里 `ser2par_32_128_inst` 的 FF 数从厂商的 159 掉到 **31**（`out\mmt.res.csv:126`），与"`frame_stable` 恒 0"完全吻合。
**无法确认**：常量具体落在 `frame_stable` 还是 `frame_start`（还是两者），以及**为什么**两份逐字节相同的 RTL 在 mmt 里被证明为常量、在厂商工程里没有。见 §6、§7。

### 0.4 RTL 本身是对的（重要）

`ddr_wr_buffer.v` 的写 FSM **没有 bug**。iverilog 仿真：只给一个 `wr_start` 脉冲，`awvalid`/`wvalid`/`wlast` 全部正常拉起（§3）。
⇒ **修法方向是"让 `wr_start` 在正确时机有效"，不是"改写 FSM"。**

### 1.2 读地址计数器被优化成 0

```

3713-3722: 'checker0/.../u_wr_fifo/RdNextAddr[1],[10],[3],[7],[9],[2],[6],[5],[4],[8]' (rtl\frame_buffer\DC_FIFO.v:233) (optimized to 0)

（`out\mmt.map.rpt:2606`、`:3713-3722`）

> 注意分辨：`RdFirst` 被优化为 0 是**正常**的 —— `DC_FIFO.v:524-531` 只在 `FIFO_MODE=="ShowAhead"` 时给它赋值，本设计是 `"Normal"`（`ddr_wr_buffer.v:99`），`else` 分支就是 `RdFirst <= 1'h0`。
> 异常的是 **`RdNextAddr[1..10]` 全部为 0**：`RdNextAddr` 是读地址计数器 `U2_RdAddrCnt` 的输出，其时钟使能是 `FifoRdEn = ReadEn || RdFirst`（`DC_FIFO.v:542`）、`ReadEn = RdEn & ~RdEmpty`（`DC_FIFO.v:406`）。计数器全 0 ⇒ **`FifoRdEn` 恒 0** ⇒ 读侧完全没有活动。

### 1.3 写 FSM 被证明恒在 state 0，写通道三个 valid 恒 0

```

3655: 'checker0/u_ddr_buffer/ddr_wr_buffer_inst/burst_end_r' (rtl\frame_buffer\ddr_wr_buffer.v:446) (optimized to 0)
3578: 'checker0/u_ddr_buffer/wr_sw' (rtl\frame_buffer\ddr_buffer.v:105) (optimized to 0)

（`out\mmt.map.rpt:3578-3582`、`:3654-3655`、`:3808`）

- `state[1:0]` 都为 0 ⇒ 写 FSM 永远停在 state 0（`ddr_wr_buffer.v:414`，只有 `sync_r2` 能让它进 state 1）。
- `awvalid` 只在 state 1→2 时置 1（`ddr_wr_buffer.v:421`），`wvalid` 只在 state 2→3 时置 1（`:429`）⇒ 两者恒 0 与 `state≡0` 自洽。
- `wr_sw = burst_last`（`ddr_wr_buffer.v:313`），而 `burst_last` 需要 `burst_add_en = wlast & wvalid & wready`（`:481`）⇒ 写通道死了它也恒 0。
- `wlast` 恒 0 也是后果（`ddr_wr_buffer.v:453-465` 的两条置 1 路径都需要 `wvalid`/`awlen`）。

> ⚠️ **行号时效**：这些行号来自 **19:55:52 那一轮**的 `mmt.map.rpt`；而 `rtl\mmt\mmt_top.v` 的 mtime 是 **21:09:16**（那轮之后又被改过），所以报告里 `fb_awvalid` 标 `mmt_top.v:333` 而当前文件里它在 `:342`（偏移 9 行）。**引用时请按信号名匹配，不要按行号硬找。**

我把 mmt 报告里所有 FIFO 内部信号的出现情况列出来（`out\mmt.map.rpt`，都是 **EFX_FF CE enables** / SR 段）：

## 4. 如果真是死逻辑，会看到什么现象

按因果链（都是实测/推断，逐级标注）：

| 级别 | 现象 | 依据 |
|---|---|---|
| 1 | **摄像头图像永远进不了 DDR3**：帧缓存区 `0x0200_0000`（3 bank，至 `0x02BD_DDFF`）不被写入 | `frame_buffer.START_ADDR`（`mmt_top.v:661`）+ 写通道死（§1.3） |
| 2 | **写 FIFO 灌满后卡死**：`u_wr_fifo` 满，`WrFull` 常 1，`ser2par` 的像素数据被**静默丢弃**（`FifoWrEn = WrEn & ~WrFull`，`DC_FIFO.v:192`；且 `frame_buffer` 没有把 `wr_fifo_wrfull` 反馈去反压上游） | 仿真 RUN B：`rdusedw` 冻结在 1024 |
| 3 | **DDR 互联的 s0 口完全安静**：`s_axi_awvalid[0]`/`s_axi_wvalid[0]` 恒 0 ⇒ 仲裁器永远只在 s1(SoC)/s2(TinyML) 之间轮转；不会出现"三主口抢 DDR"的场景 | `fb_awvalid/fb_wvalid` 恒 0（`map.rpt:3579-3580`） |
| 4 | **屏幕显示静止/花屏**：读通道是**活的**（`u_rd_fifo` 13 块 BRAM、`arvalid` 未被裁），所以 frame_buffer 会不停从 `0x0200_0000` 读并送 HDMI；既然没人写，屏幕显示的是 **DDR 上电后的残留/随机内容，且一帧都不变** | 读 FIFO 与 `arvalid` 存活的实测（§1.4、`:3579-3581` 只列了写侧三个 valid） |
| 5 | **读回来的内容再喂给算法/OSD 的都是垃圾**：debayer→降采样→`u_algo`（帧差）→OSD 的输入都是旧/随机数据，运动检测与温度热力图会表现出"全屏随机"或"恒定不动" | `mmt_top.v` 视频链路（`o_clk(vid_clk_dvi2)`/`vout` → debayer → downscale → OSD → HDMI） |
| 6 | **不会报错**：综合/布局布线全部 exit 0，时序全正（工具认为你省掉了 13 块 BRAM，甚至更"干净"） | 本项目当前实测状态 |

> 一句话：**综合和 PnR 会一路绿灯，但板子上摄像头画面永远出不来（或只是上电残影不动）**，而且**没有任何报错提示**。这正是这类"被常量折叠掉的死逻辑"最危险的地方。

## 5. 为什么"读侧 tie off"和"写侧也死"是同一个原因

`dc_fifo` 的读侧活动完全由 `FifoRdEn` 决定（`DC_FIFO.v:542`），而 `wr_fifo_rden = (awvalid & awready) || (wready && wvalid && !wlast)`（`ddr_wr_buffer.v:482`）—— 三个信号全被证明为 0 ⇒ `RdEn ≡ 0` ⇒ `ReadEn ≡ 0` ⇒ `FifoRdEn ≡ 0` ⇒ `RdNextAddr` 恒 0 ⇒ RADDR tie off、RDATA disconnect。

而**写侧也死**说明 `wr_fifo_wren ≡ 0`。`wr_fifo_wren` 来自 `u_vid_rx_align.fifo_wr_en`（`frame_buffer.v:163`），后者来自 `ser2par_32_128_v1.fifo_wr_en`（`vid_rx_align_v1.v:118`），而 `ser2par` 的打包逻辑被 `frame_stable` 门控：

```
rtl\frame_buffer\ser2par_32_128_v1.v:13  input  wire        frame_stable,
rtl\frame_buffer\ser2par_32_128_v1.v:35      else if( de && frame_stable) frame_cnt <= frame_cnt + 1'b1;
rtl\frame_buffer\ser2par_32_128_v1.v:57      end else if(frame_stable ) begin
```
⇒ **`frame_stable ≡ 0` 同时解释**：(a) `fifo_wr_en ≡ 0`（FIFO 写侧死）、(b) `wr_start = frame_start & frame_stable ≡ 0`（写 FSM 死）。
这与"`ser2par_32_128_inst` 的 FF 从 159 掉到 31"完全一致（§1.5）。

## 6. 根因定位：到哪一步，以及**为什么比"厂商原件"更容易死**

### 6.1 `frame_stable` 是怎么产生的（`rtl\frame_buffer\frame_info_det.v`，与厂商逐字节相同）

```
:46-49   vs_r0 <= i_vs; de_r0 <= i_de; de_r1 <= de_r0;
:50-51   neg_vs = {vs_r0,i_vs}==2'b10;  pos_vs = {vs_r0,i_vs}==2'b01;
:53-54   w_frame_start = (~negtive_sync & neg_vs) | (negtive_sync & pos_vs);
         w_frame_end   = (~negtive_sync & pos_vs) | (negtive_sync & neg_vs);
:75-84   frame_end_r0 <= w_frame_end;  frame_end_r1 <= frame_end_r0;
:86-97   if (frame_end_r0) begin frame_len_d0 <= frame_end_r0; frame_len_d1 <= frame_len_d0; frame_len_d2 <= frame_len_d1; end
:99-109  if (!rst_n) frame_stable <= 0;
         else if (frame_end_r1) frame_stable <= (frame_len_d0==frame_len_d1 && frame_len_d0==frame_len_d2);
:110-116 total_frame_bytes = frame_cnt * VID_DATA_BYTE;   // VID_DATA_BYTE = 32/8 = 4
:117-123 if (AXI_DDR_WIDTH==128) ddr_frame_len <= total_frame_bytes[31:4] + |total_frame_bytes[3:0];
```

`frame_stable` 的置 1 条件（**推断，逐步推演**）：`frame_len_d0 <= frame_end_r0` 使三者只可能是 0/1，且只在 `frame_end_r0` 那一拍移位，所以
- 第 1 个 `w_frame_end` 后：(d0,d1,d2)=(1,0,0) → 比较不等 → 0
- 第 2 个后：(1,1,0) → 0
- 第 3 个后：(1,1,1) → **`frame_stable <= 1`**，此后保持
⇒ 逻辑上 `frame_stable` **可以**变 1（我最初的怀疑"`frame_len_d0 <= frame_end_r0` 是本地改坏的"经比对后**排除**：厂商原件就是这样写的）。

### 6.2 因此这是一个"边界条件很脆"的链路

写通道要活，必须**同时**满足：
1. `i_vs`（= `w_mipi_rx_vs`）有边沿 ⇒ 才有 `w_frame_end`/`w_frame_start`；
2. `frame_end_r1` 至少来 3 次 ⇒ `frame_stable` 才可能被置 1；
3. `frame_start` 也在同一窗口为 1（`frame_start` 由 `fifo_rst`←`w_frame_start` 置 1、由 `fifo_wr_en` 清 0，`vid_rx_align_v1.v:56-66`）；
4. 写 FIFO 双时钟（写 `i_clk`=`i_mipi_rx_pclk`、读 `core_clk`）两侧都要活。

**任一条在综合期被证明不可能成立，整条写通道就会被常量折叠、连 FIFO 一起删掉**，并且**不会报错**。

### 6.3 **无法确认**的部分（诚实标注）

我**没有**能把常量精确定位到某一个信号，原因是：
- `frame_stable` / `frame_start` **没有**出现在 `out\mmt.map.rpt` 的 Sequential Elements/Signals Trimming Report 里（该报告能列 `fb_awvalid` 这种顶层 wire，却搜不到 `frame_stable`）。这既可能是"它们没被裁"，也可能是"该报告不穷尽"——**无法确认**。
- 与"它们没被裁"矛盾的是：`ddr_wr_buffer_inst` 的 XLR 从厂商 320 掉到 **77**（`res.csv:129`），`state` 被证明为 0。**这一对证据只有在 `wr_start ≡ 0` 时才自洽**（§3.2 RUN B 已经严格复现）。
- 我也**排除了**几个候选：
  - **不是**顶层漏接端口（§1.6，warn.log 无相关告警）。
  - **不是** ddr_wr_buffer 的本地改动（只改了 `awid` 常量，且仿真证明 FSM 好使）。
  - **不是** `i_hs` 没接（厂商顶层也没接，且 RTL 内 `i_hs` 完全没被使用）。
  - **不是** `frame_info_det` 被大改（与厂商逐字节相同；mmt 里它的 FF=104、ADD=46 与厂商 104/46 一致，说明它本身**没被裁**）。

**剩下最可疑、且与证据最吻合的推断**：`frame_stable` 在综合期被证明恒 0（因为 `ser2par` FF 159→31 的塌缩正是它门控的结果）。若成立，则等价于"**CSI2 出的 `w_mipi_rx_vs`（或 `w_mipi_rx_de & w_mipi_rx_hs`）在综合期被证明没有活动/边沿**"，或"**`frame_end_r1` 到不了 3 次**"。

**建议 Lead 用一步就能定论**：在 Efinity 里对 `checker0/u_ddr_buffer/wr_start`、`checker0/u_vid_rx_align/frame_start`、`checker0/u_vid_rx_align/frame_stable`、`checker0/u_vid_rx_align/u_frame_info_det/frame_end_r1` 做一次**时序/常量传播查询**（例如 `efx_map` 后在这些网上加 `report_net`类查询，或临时把 `frame_stable` 引出到顶层 LED/引脚观察），看哪个被报成常量 0。这一步我受"不跑 Efinity 流程"的约束做不了。

## 7. 修法建议（只写文档，不改任何文件）

按"风险从低到高"排列。**前两条建议 Lead 先做，用来把根因钉死**。

### 建议 0（最先做，零风险）：定位常量
把 `u_ddr_buffer` 的 `wr_fifo_wrfull` 输出（`rtl\frame_buffer\frame_buffer.v:204` **已有**这条连接，但该线在 `frame_buffer` 内部且未声明为端口，需要再引一层到顶层）或 `u_vid_rx_align` 的 `frame_stable`（`rtl\frame_buffer\vid_rx_align_v1.v:20`）引到顶层一个空闲 LED / 调试引脚上，上板观察：
- 若 `frame_stable` **永远为 0** → 根因在视频输入侧（`i_vs`/`i_de` 没有正确到达 frame_buffer，或 CSI2 未出有效 vsync）；
- 若 `frame_stable` 能为 1 但 `wr_fifo_wrfull` 常 1 → 根因在写时钟域（`i_mipi_rx_pclk`）。
这一步同时能验证"板子上到底有没有图像"。

### 建议 1（低风险，纯顶层）：把写通道从互联里"物理隔离"验证一次
临时把 `checker0` 的 AXI 写通道**直连**到 DDR 控制器（照厂商 `_ddr_demo_ti60` / `Ti60f225_sc431hai2hdmi_v1` 的做法，1 主 1 从），重新 `efx_map`：
- 如果写通道**活过来**（`u_wr_fifo` 出现 13 块 BRAM）⇒ 问题出在 `axi_interconnect` 那一侧（例如 s0 口配置/ID 截断把 awvalid 路径整段判死）；
- 如果**仍然死**⇒ 问题在视频输入侧，回到建议 0 继续查。

> 依据：厂商工程与 mmt 的**唯一**结构差异就是"直连 vs 经互联"（§2.2）。这是一个可以用一次 `efx_map` 就把问题一分为二的实验，**不用上板**。

### 建议 2（中风险）：给 `wr_start` 加"启动兜底"
若确认根因是"`frame_stable` 需要 3 帧才置 1、而某些条件下到不了 3 帧"，**只写文档的建议**如下（**由 Lead 决定是否应用**）：
- 在 `frame_buffer` 里把 `.wr_start(frame_start & frame_stable)`（`rtl\frame_buffer\frame_buffer.v:196`）改成 `.wr_start(frame_start)`（去掉 `frame_stable` 门控）。
  - 代价：失去"画面长度稳定后才开始写 DDR"的保护，可能在摄像头刚上电几帧内写入长度异常的数据。风险中等。
- 或保留门控但给 `frame_stable` 加超时兜底（例如 `frame_end` 计数到 N 次仍未 stable 就强制放行）。这需要改 `frame_info_det.v`，风险更高，**不推荐作为第一步**。

> ⚠️ **注意**：上面两条都会改变写通道行为，属于**功能修改**，必须由 Lead 统一应用 + 重跑 `efx_map`/`efx_pnr` + 上板验证。**我没有改任何文件**。

### 建议 3（必做，与修法无关）：把"死逻辑"变成"会报错的检查"
本次问题的教训是**综合器删掉整条数据通路却一路绿灯**（§0.3、§4-6）。建议在流程里加一道**断言式检查**（例如在 `tools\` 下加一个脚本），每次 `efx_map` 后自动比对：
1. `out\mmt.res.csv` 里 `checker0/u_ddr_buffer/ddr_wr_buffer_inst` 的 RAM 列必须 **> 0**（当前是 0）；
2. `out\mmt.map.rpt` 的 Sequential Elements Trimming Report 里**不允许**出现 `fb_awvalid` / `fb_wvalid` / `ddr_wr_buffer_inst/state`；
3. `out\mmt.map.rpt` 的 Memory Trimming Report 里**不允许**出现 `ddr_wr_buffer_inst/u_wr_fifo` 的 `RADDR is tied off` / `RDATA disconnected`。
任一条不满足就报错。这样"视频写通路被优化掉"这类问题会在流程里立刻暴露，而不是留到上板。
