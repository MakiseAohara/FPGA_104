# 上板判据：写通路握手计数 + 视觉字段（task-16）

> 目的：把"帧缓冲写通路到底活没活 / 摄像头到底有没有出图"从**盯着屏幕猜**，变成**串口上直接读数**。
>
> 写权限遵守：只改了 `rtl\mmt\soc\mmt_soc_regs.v`、`sw\**`、新建本文档。
> **没碰** `rtl\mmt\mmt_top.v`、`rtl\frame_buffer\**`、`ip\**`；**没跑 Efinity**（位流由 Lead 重编）。
>
> 约定：**【实测】**= 本轮真跑过命令/仿真并贴原始输出；**【推算】**= 由实测算出；
> **【推断】**= 有依据无直接证据，写明怎么证实；没把握写"**无法确认**"。

---

## 0. 一页结论（先看这个）

1. **新增 5 个只读寄存器**（`0x6C`–`0x7C`，都在原有的 `0x00`–`0x68` 之后，**没有动任何既有地址**）：

   | 偏移 | 名称 | 内容 | 需要额外接线吗 |
   |---|---|---|---|
   | `0x6C` | `FB_AW_CNT` | 写**地址**通道 `fb_awvalid & fb_awready` 握手累计数 | ⚠️ **要**（见 §2） |
   | `0x70` | `FB_W_CNT` | 写**数据**通道 `fb_wvalid & fb_wready` 握手累计数 | ⚠️ **要**（见 §2） |
   | `0x74` | `FB_WR_STAT` | bit0..3 = 四个信号的**当前电平**；bit4/5 = `aw_seen`/`w_seen`（曾握手过的粘滞位） | ⚠️ **要**（见 §2） |
   | `0x78` | `VISION_WORD` | `[31:24]`=`conf_vision`（**完整 8 位**）`[23:16]`=`conf_temp` `[15:8]`=`conf_env` | ✅ **不要** |
   | `0x7C` | `FRAME_TGL_CNT` | `motion_frame_tgl` 的跳变次数（视频帧数） | ✅ **不要** |

2. **串口新增两行**（第 1 行原样保留，不破坏任何已有解析）：
   ```
   T=..C RH=..% IR=..C score=..            ← 原有第 1 行（不变）
   ALM=0 AUTH=1 EVT=0 ST=0x00000002 thr=154 hr=0 auth22-6     ← ★ 报警判据行
   [WR] AW=<累计>(d=<增量>) W=<累计>(d=<增量>) st=<bit0..5> FRM=<累计>(d=<增量>) [FS] raw=<0x..> vis_bit=<0x..> t=<0x..> e=<0x..> sc9=<0x..> [VW] vis=<0x..>
   ```
   - **判读写通路就看 `d=`**（本次与上次打印的差）：`d > 0` 才是"现在正在动"。
   - **判读报警就看 `ALM=`**：`ALM=1` 才是硬件真的报了警。

3. **不要靠看板上的 LED 判断"有没有报警"**（但 LED 能看出 DDR3 校准完没完，见 §4.3）。
   当前 RTL（`mmt_top.v:1822-1823`，2026-10-13 刚改过）下板载 2 个 LED 只有三种表现：
   不报警+DDR3 校准完成 ⇒ `led[0]` ~1.5Hz 闪；不报警+未校准完 ⇒ **两灯全灭**；报警 ⇒ **两灯同相 2Hz**。
   用户看到的"两灯错峰、频率不同"三者都对不上 ⇒ **【推断】那是板载 FT4232 的串口活动灯**。
   **判据一律以串口为准**；LED 只用来旁证"`cal_done`（DDR3 校准）"。详见 §4.3。

3. **⚠️ 最要紧的一句**：`0x6C/0x70/0x74` 依赖 §2 的两处接线补丁；**没打补丁就重编，这三个寄存器会读回 0 —— 那是"输入悬空"的假象，不是"写通路死了"**。
   打完补丁之前，请用 **`0x7C`（FRM）** 和 **`0x78`（VW）** 判读：它们**只依赖本轮改的这个文件**，重编位流即可用。

4. **本轮查出一个既有 bug（重要）**：`0x28 FUSION_SCORE` 的拼接是 46 位、赋给 32 位被**截断 14 位**，
   所以 `[31:24]` 实际只有 `conf_vision[0]` **一个位**（不是文档说的 8 位视觉字节）——
   **这正是"摄像头有没有出图看不出来"的根因**，不是摄像头的问题。见 §3。本轮**不改** `0x28`（怕破坏既有映射），
   改为新开 `0x78` 提供完整字节。

5. **报警"是不是真的报了"也做成判据**（追加项）：串口新增 `ALM= AUTH= EVT= ST= thr= hr= auth..`
   一行，把 `MMT_ALARM_ST`（`0x2C`）三个字段摊开，并回显固件**实际写进硬件**的阈值与授权时段
   （`0x38`/`0x3C` 是**只写**寄存器，读不回来，所以只能由固件自己回显）。
   这一行专门解决"score 打印为 0、却怀疑报警激活"的矛盾：见 §4.2。

## 1. 寄存器怎么读（固件侧，已在 `sw\main.c` 实现）

`sw\mmt_regs.h` 里新增（与 RTL 一一对应）：

```c
#define MMT_FB_AW_CNT       (MMT_BASE + 0x6C)   /* [31:0] 写地址通道握手累计 */
#define MMT_FB_W_CNT        (MMT_BASE + 0x70)   /* [31:0] 写数据通道握手累计 */
#define MMT_FB_WR_STAT      (MMT_BASE + 0x74)   /* bit0..3 电平, bit4/5 曾握手 */
#define MMT_VISION_WORD     (MMT_BASE + 0x78)   /* [31:24] 完整视觉字节 */
#define MMT_FRAME_TGL_CNT   (MMT_BASE + 0x7C)   /* [31:0] 视频帧翻转次数 */
```

读法就是普通的 32 位读：`MMT_REG32(MMT_FB_AW_CNT)`（`MMT_BASE = 0xF8100000`）。

**在旧位流下读这些地址安全吗？** 安全：本寄存器块的 APB 读是
`case(PADDR) ... default: PRDATA = 32'h0;`（`mmt_soc_regs.v` 读进程），
且 `PREADY` 恒 1、`PSLVERROR` 恒 0 ⇒ 未映射地址读回 **0**，不会挂总线、不会报错。
所以**先烧新固件也不会出问题**，只是这几个数显示 0（等重编位流后才有意义）。

固件里打印"增量"的实现（`sw\main.c` 串口打印段）：用 `static` 记住上次的值，打印 `(d=本次-上次)`。
为什么要增量：累计值可能是很久以前攒的（例如写通路曾经活过、现在卡住），**只有 d 能说明"现在在不在动"**。

关于 `(* preserve, syn_keep = 1 *)`（按任务要求加的，也在注释里写清了理由）：
- 计数器本身被 `PRDATA` 读到、不会被删；但它的**输入** `fb_*` 若被工具当成"只喂给可优化逻辑"，
  仍可能被折成常量 —— 这正是 `mmt_top.v:1141-1142` 记录过的那个坑。
- 加上属性后综合器必须保留这段时序逻辑及驱动它的路径。
- 该属性是 Synopsys 系（Efinity 也用）的写法；Xilinx 的等价物是 `dont_touch`，**别混写**。

## 3. 查出的既有 bug：`0x28` 的视觉字段其实只有 1 位（**实测**）

RTL 里 `0x28` 的拼接（`mmt_soc_regs.v` 读进程）：

```verilog
16'h0028: PRDATA = {7'd0, conf_vision, conf_temp, conf_env, 6'd0, score};
```

**位宽 = 7 + 8 + 8 + 8 + 6 + 9 = 46 位**，赋给 32 位 `PRDATA` 时**高 14 位被截掉**。
所以实际读到的布局与注释（"`[31:24]`=视觉"）**不一致**：

| 位 | 实际内容 | 注释说的 |
|---|---|---|
| `[31]` | **`conf_vision[0]`（1 个位）** | `[31:24]` = 视觉 8 位 ❌ |
| `[30:23]` | `conf_temp` | `[23:16]` = 温度 ❌ |
| `[22:15]` | `conf_env` | `[15:8]` = 环境 ❌ |
| `[14:9]` | 0 | — |
| `[8:0]` | `score`（9 位） | `[8:0]` ✅ |

**仿真实测**（`conf_vision=0xB7 / conf_temp=0x5A / conf_env=0x3C / score=0x1AB`）：

```
  0x28 FUSION_SCORE raw read = 0xAD1E01AB
  PASS  0x28 bit31 == conf_vision[0] = 0x00000001
  PASS  0x28 [30:23] == conf_temp    = 0x0000005A
  PASS  0x28 [22:15] == conf_env     = 0x0000003C
  PASS  0x28 [8:0] == score          = 0x000001AB
  PASS  0x28[31:24] NOT 8bit vision  = 0x00000000      ← [31:24] 并不是 0xB7
```

手工复算也对得上：`1 | 01011010 | 00111100 | 000000 | 1_1010_1011` = `0xAD1E01AB` ✅

**后果（就是这次的痛点）**：固件里

```c
uint8_t conf_v = (uint8_t)(fs >> 24);   /* sw\main.c：以为拿到 8 位视觉，实际只有 vis[0]，只能是 0x00 或 0x01 */
```

⇒ 串口/OSD 上的 `V/T/E=` 里那个 **V 值永远只有 0 或 1**，**根本区分不出"没出图"和"出了图但置信度低"**。
**这不是摄像头的问题，是寄存器拼接的问题。**

**本轮的处置**（两种都不破坏既有映射）：

- ✅ **新开 `0x78 VISION_WORD`**：`{conf_vision, conf_temp, conf_env, 8'd0}` = 8+8+8+8 = **32 位，不再截断**，
  视觉字节就在 `[31:24]`（与文档期望的位置一致）。
- ❌ **没有改 `0x28`**：因为要装下 8+8+8+9 = **33 位**，32 位里塞不下 —— 任何"修好视觉"的方案都必须
  牺牲 `score[8]` 或 `conf_env` 的 1 位。改它会**改变既有寄存器语义**，与"不破坏既有映射"冲突。
  若将来要根治，建议**升版本、重排整张表**，而不是就地截断。
- ⚠️ 顺带提醒：OSD 第 2 行的 `V/T/E=`（`sw\main.c`）读的就是 `conf_v`，所以**屏幕上那个 V 同样受限**。
  想让 OSD 也显示完整视觉值，把 `conf_v` 改成从 `MMT_VISION_WORD >> 24` 取即可（本轮没改 OSD，避免动显示布局）。

## 4. 上板判据表（核心交付）

### 4.1 写通路 / 视频通路的三场景

先定义要看的量：

| 记号 | 来源 | 含义 |
|---|---|---|
| `AW_d` / `W_d` | `0x6C`/`0x70` 的 `d=` | 本次打印间隔内发生的写地址/写数据握手次数（>0 = 现在在动） |
| `st` | `0x74` | bit0..3 当前电平；**bit4=`aw_seen`、bit5=`w_seen`** = 开机以来是否**曾经**握手过 |
| `FRM_d` | `0x7C` 的 `d=` | 本次间隔内视频帧翻转次数（>0 = 视频通路在出帧） |
| `VW` | `0x78 >> 24` | 完整 8 位视觉字节 |

| # | 场景 | `AW_d`/`W_d` | `FRM_d` | `st` | `VW` | 结论与下一步 |
|---|---|---|---|---|---|---|
| **A** | **写通路死**（被折成常量 / 握手卡住） | **恒 0**（且若 `st` bit4/5 = 0 说明开机以来从没通过） | 可能仍 >0 | 可能电平有 1 但永不握手 | 可能 >0 | 帧缓冲没在写 DDR。**最要命**。查：① `preserve` 是否真生效（看 `out\mmt.map.rpt` 里 `fb_awvalid` 是否还被写成 `(optimized to 0)`）② 互联 s0 口的 `awready`/`wready` 是否恒 0（死锁）③ `ddr_wr_buffer` 的 `wr_req`/`state` 是否有效 |
| **B** | 写通路活，**摄像头无数据** | 恒 0 | **恒 0** | bit4/5 = 0 | 恒 0/不变 | 视频源没出图 ⇒ 写通路自然没得写。查：MIPI 摄像头供电/时钟/排线、`rtl\cam_i2c_ctrl` 的配置是否真写进 sensor、`w_mipi_rx_de`/`w_mipi_rx_vs` 有没有动 |
| **C** | **两者都活**（正常） | **持续 >0** | **持续 >0** | bit4/5 = 1 | 随画面变化 | 正常。可以开始看 OSD 画面与融合结果 |
| D | 附加：只有 W 在动、AW 不动 | `W_d>0, AW_d=0` | — | — | — | 异常（AW 先被接受但 W 卡住）。查互联的 wstrb/wlast 与 ID 路由 |
| E | 附加：只有 AW 在动、W 不动 | 反 | — | — | — | 异常（地址发了但数据没来）。查 frame_buffer 写侧的 FIFO/`wr_req` |

**判读流程（4 步，30 秒）**：

0. **先看板载 `led[0]` 在不在闪**（不报警时）：闪 = `cal_done`=1（DDR3 校准完成）；
   **全灭 = DDR3 还没校准完** ⇒ 此时写通路**不可能**握手成功，先别急着查互联/帧缓冲（见 §4.3）。
1. 看 `FRM=(d=?)`：**d = 0** ⇒ 视频没出帧 ⇒ 先按场景 B 查摄像头（此时写通路不涨是正常的，别误判成 A）。
2. `FRM_d > 0` 但 `AW_d = W_d = 0` ⇒ **写通路没在握手** ⇒ 按场景 A 查（这时 A 才是真的）。
3. `FRM_d > 0` 且 `AW_d = W_d > 0` ⇒ 正常（场景 C）；若两者不等 ⇒ 看场景 D/E。
4. **报警那一路单独看**：`ALM=` 与 `EVT=`（§4.2），不要用 LED 代替。

**串口"正常长什么样 / 异常长什么样"**（下面的**数字是示意**，不是实测，真实值以板子为准）：

正常（场景 C）——两个 `d` 都是正的、且 `AW` 与 `W` 同步增长、报警行按实际状态显示：
```
T=25.0C RH=50.0% IR=36.5C score=600  ALARM!
ALM=1 AUTH=1 EVT=1 ST=0x00000003 thr=154 hr=0 auth22-6
[WR] AW=15234(d=120) W=15234(d=120) st=0x3F FRM=612(d=2) [FS] raw=0xAD1E01AB vis_bit=0x01 t=0x5A e=0x3C sc9=0x1AB [VW] vis=0xB7
```
写通路死（场景 A）——`FRM` 在涨但 `AW/W` 一动不动、`st` 说明从没握过手：
```
T=25.0C RH=50.0% IR=36.5C score=0
ALM=0 AUTH=1 EVT=0 ST=0x00000002 thr=154 hr=0 auth22-6
[WR] AW=0(d=0) W=0(d=0) st=0x00 FRM=612(d=2) [FS] raw=0x00000000 vis_bit=0x00 t=0x00 e=0x00 sc9=0x000 [VW] vis=0x00
```
> ⚠️ 这个"全 0"也可能是**没打 §2 补丁**造成的假象。区分办法：看 `st` 的 bit0..3 电平有没有在变、
> 以及**先确认补丁已应用**。若补丁没打，`AW/W/st` 全部无意义。

摄像头/视频不出（场景 B）——`FRM` 的 `d` 也是 0：
```
T=0.0C RH=0.0% IR=0.0C score=0
ALM=0 AUTH=1 EVT=0 ST=0x00000002 thr=154 hr=0 auth22-6
[WR] AW=0(d=0) W=0(d=0) st=0x00 FRM=0(d=0) [FS] raw=0x00000000 vis_bit=0x00 t=0x00 e=0x00 sc9=0x000 [VW] vis=0x00
```

### 4.2 报警判据（追加项）：一行解决"score=0 却有报警"的矛盾

**矛盾从哪来**：硬件里 `alarm = (score >= 阈值) && in_auth_window`（阈值复位 154），
而固件在 main 开头写了 `hour = 0`（板子没 RTC）⇒ `in_auth_window = (0 >= 22) || (0 < 6)` = **真**。
所以"报警会不会响"**完全取决于 hardware 内部的 score**，而串口上能看到的 `score=` 是
`0x28[8:0]` 的快照 —— 两者理论上应该一致，但不一致时**必须靠 `ALARM_ST` 定性**。

**报警行的每个字段**：

| 字段 | 来源 | 含义与判读 |
|---|---|---|
| `ALM=` | `0x2C` bit0 | `1` = 硬件**真的**报过警（该位"读清"，本行就是那次读的结果） |
| `AUTH=` | `0x2C` bit1 | `in_auth_window` 电平。固件写 `hour=0` ⇒ **应为 1**（若不是 1，说明 `0x3C` 没写进去或 RTL 判据不同） |
| `EVT=` | `0x2C` bit[4:2] | 事件类型。**注意它是锁存**：一旦报过警就保持 1（只有复位才清）⇒ `EVT=1` 表示"开机以来报过警" |
| `ST=` | `0x2C` 完整 32 位 | 原始值，便于反查未被文档覆盖的位 |
| `thr=` `hr=` `auth22-6` | 固件本地变量 | **固件实际写进硬件的**阈值/当前小时/授权时段（`0x38`/`0x3C` 只写、读不回来） |

**判据表**：

| # | 现象 | 结论 | 下一步 |
|---|---|---|---|
| A1 | `score=0` 且 `ALM=0` `EVT=0` | **没有报警**。"报警激活"的猜测不成立 | 若外面看到 LED 乱闪 ⇒ 就是 §0-3 说的 FT4232 串口灯，忽略 |
| A2 | `score=0` 但 `ALM=1` | 硬件在**某一瞬间**确实报过警，而软件读到的 `0x28` 快照是 0 | 查 `0x28` 的跨域路径（`alg_score` 在视频域产生、经同步到系统域，`mmt_top.v:1590`）：报警是硬件的**瞬时**比较，报告是**采样**，两者可以不同时。先把 `EVT` 与 `FRM` 一起看（`FRM_d>0` 才谈得上误报） |
| A3 | `AUTH=0` | 授权窗口没生效 | 查 `0x3C` 写入（`auth22-6` 显示的就是固件写的值）与 RTL 的 `in_auth_window` 判据 |
| A4 | `EVT=1` 但 `ALM=0` | 报警**曾经**发生过（EVT 锁存，不随 ALM 清） | 别把它当"正在报警"。要么查历史，要么复位重测 |
| A5 | `sc9=` 非 0 而第 1 行的 `score=` 仍是 0.0 | 打印换算问题（`score*1000/256`） | 用 `sc9=`（原始 9 位）为准 |

> **为什么原来的打印看不出这些**：老代码只打 `score` 和一句 `ALARM!`，
> 而 `ALARM!` 依赖的是**同一个** `alarm` 位（`sw\main.c` 读 `0x2C` 的那一次）——
> 也就是说老打印**信息量不足**，无法区分"没报警"与"报警了但 score 字段没反映"。
> 现在 `ALM/AUTH/EVT/ST` 四个信息一起出来，A1/A2 可以直接分。

### 4.3 LED 不能当"报警判据"，但它能白送一个 **DDR3 校准指示器**（实测当前 RTL）

⚠️ **先纠正一处引用**：任务书里写的 `rtl\mmt\mmt_alarm_ctrl.v` **不存在**；
报警模块在 **`rtl\mmt\alarm\mmt_alarm_ctrl.v`**（少了 `alarm\` 一层）。而且 `mmt_top.v` 的
LED 合并逻辑 **2026-10-13 刚被改过**（`cnt[24]`→`cnt[25]`，注释里写着"上板实测偏快"），
所以任何"按代码推 LED 行为"的说法**必须以当前文件为准**（我按当前文件核实如下）：

`rtl\mmt\alarm\mmt_alarm_ctrl.v`：
- `:129` `led = blink_phase ? 4'b1111 : 4'b0000;`（**报警**：4 灯全亮全灭）
- `:132` `led = HEARTBEAT_EN ? {3'b000, hb_div} : 4'b0000;`（**不报警**：只有 led[0] 心跳）
- `:53` `HALF_TICKS = CLK_HZ/(2*HF_BLINK_HZ)`，`HF_BLINK_HZ=2` ⇒ 报警闪烁 **2Hz**

`rtl\mmt\mmt_top.v:1822-1823`（顶层只把低 2 位引到板载 LED，因为只有 2 个 LED 脚）：
```verilog
assign led = (alg_alarm_s) ? alarm_led[1:0]
                           : {1'b0, (cal_done ? cnt[25] : 1'b0)};
```

⇒ 板载那 2 个 LED 一共只有**三种**表现：

| 状态 | 板载 LED 表现 | 依据 |
|---|---|---|
| 不报警 **且 DDR3 校准完成**（`cal_done=1`） | 只有 `led[0]` 以 **~1.5Hz** 闪（`cnt[25]`：100MHz/2²⁵ ≈ 0.3355s 翻转 ⇒ 周期 0.671s） | `mmt_top.v:1822-1823` |
| 不报警 **但 DDR3 没校准完**（`cal_done=0`） | **两个灯全灭**（心跳被 `cal_done` 门掉） | 同上 |
| 报警（`alg_alarm_s=1`） | **两个灯同相、2Hz** | `rtl\mmt\alarm\mmt_alarm_ctrl.v:129` + `:53` |

**用户报的"两个 LED 错峰、频率不同"三种都对不上** ⇒ **【推断】看到的是板载 FT4232 的串口活动指示灯**
（每打印一行闪一次，频率跟着打印走，看起来就和 `led[0]` 错峰）。
**怎么证实**：停掉/拔掉串口（或让固件停打），再看那两个灯是否仍有规律地闪。

**★ 顺手得到的一个免费判据（很有用）**：`cal_done` 是 **DDR3 控制器的校准完成信号**
（`mmt_top.v:264` 声明、`:1043` 由 `u_ddr3_top` 输出 ⇒ `.cal_done(cal_done)`）。
所以 **"不报警时 led[0] 闪不闪" = "DDR3 校准完成没有"**：

- `led[0]` 在闪 ⇒ DDR3 校准完成 ⇒ 写通路若还不动，问题在互联/帧缓冲侧（§4 场景 A 的后两项）。
- `led[0]` 全灭 ⇒ **DDR3 校准还没完成**，此时**写通路不可能握手成功** ——
  这是一种**比"写通路死"更上游的原因**，而串口以前完全看不到它（SoC 没有 DDR 校准状态寄存器）。
  这也解释了为什么"写通路计数"必须和这个指示灯一起看。

> 注意：这一节结论依赖"板载那 2 个 LED 引脚确实是 `GPIOR_27/GPIOR_24`"（`mmt_top.v:1817-1818` 注释所述，
> 依据是 `mmt.peri.xml`）。**没有上板复核引脚对应关系**，列在 §6-V10。
