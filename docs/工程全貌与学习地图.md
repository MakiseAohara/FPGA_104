## 1.2 赛题三任务书原文（逐字）

> ## 赛题三：多模态AI智能终端
>
> **核心场景**：智慧康养（室内老人跌倒检测与预测）、智能家居（感知人体位置和体温的智能环境控制）、
> 智能安防（多模态异常行为检测）
>
> **Ti60亮点**：支持MIPI摄像头及I2C传感器接口，可在FPGA内部署RISC-V软核，结合TinyML轻量级AI推理框架，
> 实现人体检测、姿态分析等边缘智能应用；同时可利用FPGA DSP、片上存储及自定义硬件加速单元对关键AI算子
> 进行加速，RISC-V负责模型调度、多模态数据融合及系统控制。
>
> **赛题背景**：本赛题要求参赛者基于Ti60 FPGA，构建一个"视觉+红外温度+环境传感"的多模态AI智能终端，
> 在本地完成数据采集、融合推理与事件响应，真正实现低延迟、高隐私、高可靠的边缘智能。典型应用包括：
> 室内跌倒检测与预警、智能空调人员跟随控制、非授权区域入侵报警等。
>
> **赛题要求**
>
> ### 任务1：多传感器数据采集与FPGA预处理（基础）
>
> 目标：建立多模态传感器的数据采集通路，实现数据预处理和时间对齐。
>
> 要求：
> - 通过MIPI CSI接口驱动摄像头，完成视频流实时采集，分辨率不低于720p@30fps
> - 通过I2C接口驱动红外温度传感器（如MLX90640），实现人体温度分布采集
> - 通过I2C接口驱动温湿度传感器（如SHT30），实现环境温度采集
> - 在FPGA内实现数据预处理：滑动平均滤波、异常值剔除、多传感器时间戳对齐
> - 通过HDMI/LCD显示各传感器实时数据（视频画面+温度热力图+环境参数叠加显示）
>
> 技术要点提示：
> - 多传感器时间对齐：以视频帧时间戳为主时间基准，对红外温度和环境传感器数据进行时间戳标记，
>   通过最近时间匹配、缓存或插值实现多模态数据的时间对齐
> - 温度数据预处理：读取MLX90640原始红外数据及EEPROM校准参数，完成环境温度、增益、偏置、发射率等补偿，
>   计算各像素目标温度；可采用定点化、分段近似或LUT等方法对部分计算进行硬件优化
> - 显示叠加：在HDMI画面上分区域显示——主区域视频画面、侧边温度热力图小窗、底部环境参数文字
> - I2C多设备管理：使用I2C地址区分不同传感器，设计分时复用控制器
>
> ### 任务2：多模态AI处理与感知决策（核心）
>
> 目标：在FPGA端实现轻量级AI推理和多模态融合决策。
>
> 要求：
> - RISC-V + FPGA AI推理：在Ti60 FPGA内部署RISC-V软核，运行TinyML等轻量级AI推理框架，
>   实现人体检测、姿态识别或其他视觉感知算法。鼓励利用FPGA DSP、BRAM、并行逻辑及RISC-V自定义指令
>   实现卷积、矩阵运算等关键算子的硬件加速，提高推理性能。
>   运动分析：通过帧差法或光流法（Farneback简化版），分析人体运动状态（静止/行走/跌倒/异常动作）
> - 多模态融合决策：结合视觉检测结果（位置、动作）+ 红外温度数据（体温异常检测）+ 环境数据
>   （温度/湿度异常），进行综合判断
> - 事件检测与响应：实现以下场景之一，或自定义一个智能场景：
>   - 跌倒检测：人体姿态突变+长时间静止+温度正常（排除倒地物体），触发报警
>   - 智能空调控制：检测人员位置分布和体温，结合环境温度，输出空调控制建议（或驱动GPIO模拟控制）
>   - 入侵检测：非授权时段人体出现+体温正常（排除热源干扰），触发报警
> - 本地报警与显示：检测到异常事件时，通过LED闪烁+蜂鸣器报警+HDMI画面红色边框提示+
>   显示事件类型和置信度
>
> 技术要点提示：
> - 轻量级神经网络：建议使用定点量化（INT8），利用DSP做矩阵乘法加速。网络结构建议不超过5层卷积+
>   2层全连接，参数量控制在100K以内
> - 多模态融合策略：加权投票法——视觉置信度60% + 温度置信度25% + 环境置信度15%，
>   综合得分超过阈值触发事件
> - 帧差法运动检测：当前帧与背景帧差分，阈值分割后计算连通域面积和质心位移，判断运动类型

**⚠️ 重要澄清**：任务书里「网络不超过 5 层卷积+2 层全连接、参数量 100K 以内」**是建议（技术要点提示），
不是硬性规则**。原文用词是"建议"。这一点曾被误读为硬指标，已核对原文确认。

## 1.3 任务3（7 选 2）

任务书附录列了 7 个可选方向，要求至少实现 2 项。**本项目已选定：**

- **② RISC-V 软核决策控制** —— 用 Sapphire RISC-V 软核承担融合决策、事件状态机、外设调度
- **⑤ 低功耗场景管理** —— 无事件时降低采样率/关闭部分模块

## 1.4 本项目的选题与方案

**选定的智能场景：非授权区域入侵检测**（任务2 给的三个场景之一）。

判断逻辑：非授权时段 + 视觉检出人体 + 体温正常（用来排除热源干扰，比如暖气片、热饮、阳光）
→ 触发报警（LED 闪烁 + 蜂鸣器 + HDMI 画面红框 + 显示事件类型与置信度）。

**整体方案一句话**：
SC431HAI 摄像头走 MIPI CSI-2 进来 → FPGA 内部去马赛克 → DDR3 三缓冲帧缓存 →
降采样(1920×1080→160×120)做帧差法运动检测 → 同时 I2C 轮询 MLX90640（32×24 红外阵列）和
SHT30（温湿度）→ 三路结果按 **60/25/15 加权投票**（Q8 定点）融合 → 输出到 HDMI
（主画面 + 右上角温度热力图小窗 + 底部三行环境参数文字 + 报警红框）→
报警走 LED + 蜂鸣器；整条链路由一颗 **Sapphire RISC-V 软核**做决策调度，
通过自研的 **APB3 寄存器桥**读写所有硬件状态。

# 第二部分：硬件平台

## 2.1 FPGA 器件 Ti60F225

| 项 | 值 |
|---|---|
| 厂商 / 系列 | Efinix **Titanium**（钛金，16nm 工艺） |
| 型号 | **Ti60F225**（225-ball FBGA） |
| 容量 | **60,800 XLR**（逻辑单元）/ **256 BRAM**（存储块）/ **160 DSP**（乘法器块） |
| 定时模型 | **I3**（综合/布局布线必须指定，否则时序结果不对） |
| 开发工具 | **Efinity**（本机装的是 **2026.1.132**，路径 `D:\Efinity\2026.1`） |

**XLR 是什么**：Efinix 对"可配置逻辑单元"的叫法。一个 XLR 可以当一个 LUT4、或一个 LUT4+触发器、
或加法器的一部分用。资源报告里 `XLRs: 20833 / 60800 (34.26%)` 表示逻辑用了约三分之一。
BRAM 和 DSP 是独立的硬块。**本设计里最紧的资源是 BRAM**（TinyML 的权重和激活缓冲全吃 BRAM）。

## 2.2 开发板 Ti60F225I3-V4 板上资源

- **DDR3**：`MT41J128M16JT-125`，16 位宽、2Gb（256MB）、Row14/Col10/Bank3。
  ⚠️ Ti60F225 的 DDR3 控制器是**软核**（用 FPGA 逻辑搭），**数据速率上限 800Mbps**，不是硬核。
- **HDMI**：一个标准 **HDMI Type-A 座**（原理图型号 `HDMI_TXYT8531SH`），同时接了 RX 与 TX 通路。
  本设计只用**输出**（TMDS TX）。厂商文档强调两条必须注意：**FPGA 差分对的 P/N 脚要对调**；
  HDMI 设置里要**勾选 Enable Common Mode Driver**。忽略会不出画面。
- **两路 MIPI FPC 座**：一路给显示屏、一路给摄像头。我们用摄像头那路。
- **一个 QSE 扩展座（J7）**：Samtec `QSE-020-01-X-D-A`，**0.8mm 间距 40 脚高密度座**。
  板上**只有这一个地方引出了空闲 GPIO**。
- **板载下载器**：`FT4232HL`，一根 USB 线同时提供 **供电 + JTAG 下载 + UART 串口**，不用另买下载器。
- **4 个 LED、4 个按键**。
- **片上晶振 OSC_0**：可选 10/20/40/80 MHz。板上另有 25 MHz 晶振（`CLK_25M`，引脚 `GPIOL_P_08`，走全局时钟）。

### 2.3.4 摄像头接口

- MIPI CSI 差分对：`cam_ck → GPIOT_PN_09`、`cam_d0 → GPIOT_PN_07`、`cam_d1 → GPIOT_PN_10`、
  `cam_d2 → GPIOT_PN_06`、`cam_d3 → GPIOT_PN_11`
- 摄像头侧 I2C（配置 sensor 用）：`io_cam_scl → GPIOR_20`、`io_cam_sda → GPIOR_18`、

## 2.5 两个传感器共用一条 I2C 总线

MLX90640（0x33）和 SHT30（0x44）地址不冲突，**挂在同一条 I2C 上**，只需 2 根信号线（SCL/SDA）
加 3.3V 和 GND，一共 **4 根线**接到 J7（用 `GPIOL_11`/`GPIOL_09`），蜂鸣器再接 1 根（`GPIOR_13`）。
I2C 需要**上拉电阻**，模块一般自带；若不自带要在 SCL/SDA 上各加一个 4.7kΩ 上拉到 3.3V。

## 3.3 时钟域与复位

本设计有**两个主要时钟域**：

| 域 | 时钟 | 频率 | 用途 |
|---|---|---|---|
| 视频域 | `hdmi_tx_slow_clk` / `vid_clk_dvi2` | 148.5 MHz（1080p60 像素时钟） | CSI RX、debayer、帧缓存、降采样、帧差、OSD、HDMI 输出 |
| 系统域 | `core_clk` | 100 MHz | RISC-V SoC、APB 寄存器桥、I2C 子系统、传感器控制器 |

另有 `sdram_clk` 400 MHz 给 DDR3 控制器。

**跨时钟域（CDC）处理**（这是 FPGA 设计的经典难点，本工程专门硬化过）：

1. **`mmt_sync2.v`** —— 标准两级触发器同步器，用于单比特电平信号跨域。
   工程里所有跨域信号都走它，例如 `bg_clear_tgl`、`alg_frame_tgl`。

2. **`bg_clear`（清背景请求）的问题与修法**：
   软件核写寄存器产生的是一个"单周期脉冲"，而系统域周期（10ns）比视频域周期（6.7ns）慢，
   跨域后这个脉冲**可能被完全漏掉**。
   **修法：改成电平翻转（toggle）**——软件每写一次就翻转一次电平，视频域用两级同步器同步过来后，
   检测"翻转沿"再产生一个本域的 1 拍脉冲。单比特跨域 + 两级同步是可靠的；
   只有"两次请求间隔小于同步延迟"才会合并，而这是人手触发的，不存在。

3. **多比特状态量的跨域**：直接同步多比特会读到中间值。
   **修法：加"帧翻转标志"**——视频域每完成一帧就翻转一个单比特标志 `alg_frame_tgl`，
   单独同步到系统域；软件核**只在标志变化时才去读** `sum_area` 等数据，
   而那时数据早已稳定（数据是帧结束才更新的）。寄存器 `MMT_MOTION_ST` 的 bit2 就是这个标志。

# 第四部分：模块逐个详解

> 说明：标「厂商」的是从板卡包 demo 复用、**未修改**的代码；标「自研」的是本工程新写的。

## 4.1 视频链（全部厂商复用）

链路来自板卡包 10 号 demo（`10_Ti60f225_sc431hai2hdmi_demo`），干净构建实测 **16,830 XLR / 138 BRAM**。

| 模块 | 职责 |
|---|---|
| `csi_rx_controller` | MIPI CSI-2 RX（IP 形式），把摄像头差分串流解成并行像素 |
| `cam_i2c_ctrl` | Wishbone 总线的 I2C master + `i2c_master_reg_set`（内部 ROM 存 SC431HAI 的初始化寄存器表）。用来在上电时配置摄像头 |
| `debayer` | RAW Bayer → RGB |
| `frame_buffer` | 三缓冲乒乓帧缓存，读写 DDR3。三 bank 地址约 `0x000000 / 0x005EEE00 / 0x00BDDC00` |
| `ddr3_controller` | DDR3 软核控制器（AXI4 接口 + PHY 训练） |
| `dvi_tx` | TMDS 编码（`dvi_encoder`），输出到 HDMI |

**★ 本工程做的一个关键删减：砍掉 MIPI DSI TX。**
原 demo 同时带 DSI（接 MIPI 屏）和 HDMI 两条输出。我们只用 HDMI，所以把 `dsi_tx` 整个从顶层摘掉了。
实测省下 **−5,093 XLR / −76 BRAM**（BRAM 从 138 降到 62）。
这也是为什么**不需要买那块 500 元的官方 MIPI 屏**。

## 4.2 I2C 子系统（自研，这是任务1 的"亮点"）

任务书明确要求「I2C 多设备管理：使用地址区分不同传感器，设计**分时复用控制器**」。
厂商只给了一个"配置摄像头用"的 I2C master（Wishbone 接口、写死在 ROM 里），
**没有可复用的通用 I2C 主机，也没有多设备仲裁**。所以这部分全部自研。

### 4.2.1 `mmt_i2c_master.v` —— 通用 I2C 字节级主机（371 行）

- **接口**：`req / dev_addr[6:0] / tx_data[31:0] / tx_len[2:0] / rd_len[7:0]`，
  回 `busy / done / err / rd_data[7:0] / rd_valid`
- **支持**：START、重复 START、写 0~4 字节、连续读最多 255 字节、STOP、开漏三态
- **不支持时钟拉伸**（从机把 SCL 拉住）—— 这是已知限制，所以给 SHT30 用的是
  "禁止拉伸"的测量命令 `0x2400`，靠固定延时规避
- **分相时钟**：`div_cnt/ph` 把每个 SCL 位周期切成 4 个相位
  - `ph==1` 改变 SDA（SCL 低时）
  - `ph==2` 采样 SDA（SCL 高时）
  - `ph==3` 位结束，状态推进
  - SCL 电平 = `(ph >= 2) && !scl_hold_low`
- **`scl_hold_low`**：START / 重复 START 之后那一个位周期必须强制 SCL 保持低，
  否则相位块会在 `ph>=2` 时把它抬高，多出一个 SCL 上升沿，从机会把它当成一个数据位，整体错一位

**★★ 这个模块里发现并修掉了一个极隐蔽的真 bug（值得单独记住）**：

`ST_IDLE` 原来在**任意相位**接受请求，而 `ST_START1` 靠 `act_sda(ph==1)` 把 SDA 拉低来产生 START 条件、
靠 `act_next(ph==3)` 推进状态。如果进入 `ST_START1` 时 `ph` 已经越过 1（坏窗口是 `ph∈{2,3}`，
占整个位周期的**一半**），这个位周期内 `act_sda` 再也不会出现，而 `act_next` 照样把状态推到
`ST_START2` —— **SDA 从未被拉低，START 条件根本没产生**，从机不激活，地址字节必然收到 NACK。

表现极具迷惑性：**复位后第一笔事务完全正确，之后每一笔都失败**（因为复位时恰好 `ph=0`）。

**修法**：`ST_IDLE` 只在分相时钟的位边界接受请求：
```verilog
if (req && req_armed && (ph == 2'd0) && (div_cnt == 16'd0)) begin
```
这个 bug 之前写的 7 个测试**全都抓不到** —— 因为它们都在固定时刻发请求，相位每次一样，恰好落在安全区。
后来补了一条「请求相位遍历」测试专门扫相位才抓到。

### 4.2.2 `mmt_i2c_hub.v` —— 分时复用控制器（131 行）

- 3 个客户端（SHT30 / MLX90640 / 预留）共享一条物理 I2C 总线
- 轮询仲裁（round-robin），保证不饿死
- **约定**：`c_grant`（授权）和 `c_done`（完成）必须在**同一拍**给出，
  否则客户端可能在"还没被授权"时就看到 done，去撤 req，导致状态机错乱
- **客户端契约**：客户端必须"看到 done 之后才撤 req"；master/hub 用**边沿重新武装**
  （`req` 掉过一次才允许再接受请求）来避免 `req`/`done` 的竞争

### 4.2.3 `mmt_sht30_ctrl.v` —— SHT30 温湿度控制器（227 行）

- 周期（默认 1 秒）发起一次测量：写命令 `0x2400` → 等 20ms（手册最坏 15ms，留 5ms 裕量）→
  读 6 字节 → CRC-8 校验 → 定点换算
- **CRC-8**：poly=0x31（x⁸+x⁵+x⁴+1），init=0xFF，不反转，无最终异或。
  测试向量 `CRC(0xBEEF)=0x92` 已与数据手册核对
- **换算公式**：`T[°C] = -45 + 175·S_T/65535`，`RH[%] = 100·S_RH/65535`
  定点化用 `>>16` 近似（除以 65536）。**误差是 Python 全量扫描实测出来的，不是推的**：
  最大误差 1.26 个定点单位（< 0.013°C），远小于传感器自身精度
- 失败处理：CRC 错 → 置 `crc_err` 并**保留上一次有效值**；NACK → 置 `bus_err`，下周期重试

### 4.2.4 `mmt_mlx90640_ctrl.v` —— MLX90640 红外帧搬运（348 行）

- 上电初始化：读 `CTRL_REG(0x800D)` → **只替换刷新率字段 bit[9:7]** → 写回
  （严格照抄官方库 `MLX90640_SetRefreshRate()` 的"读-改-写、只动一个字段"模式）
- 主循环：轮询 `STATUS_REG(0x8000)` 的 data-ready 位（bit3）→ 写 `0x0030` 清标志位 →
  分 26 个 chunk（24×32 像素字 + 2×32 辅助字 = 832 字）依次读回，写入 BRAM
- 每 chunk 用"写 16 位寄存器地址 + 重复 START + 顺序读 64 字节"的事务
- 已知限制（写在文件头）：
  1. **EEPROM（0x2400 起 832 字）本模块不读** —— 设计上是"RISC-V 开机读一次"
  2. `ta_raw` 只搬了 `frameData[800]`（Ptat）一个字，完整 Ta 还需要 `[768]`(Vbe) + EEPROM 系数
  3. `frame_addr` 只有 10 位装不下 EEPROM 地址

### 4.2.5 `mmt_sensor_subsystem.v` —— 子系统封装

把 master + hub + 两个控制器 + BRAM 封成一个模块，可以独立综合/验证。

## 4.3 算法层（自研）

### 4.3.1 `mmt_frame_diff.v` —— 帧差法运动检测（187 行）

- 把降采样后的 160×120 灰度帧与**背景帧**做差分
- 阈值分割 → 累加运动像素数（面积 `sum_area`）、以及 Σx·mask / Σy·mask（用来算质心）
- 背景更新：**每帧更新 1/32**（`bg = bg + (cur - bg)/32`，用移位实现），做慢速自适应
- 输出 `motion_flag`、`frame_done`（脉冲）、面积、质心坐标

**这个模块踩了两个把综合搞爆的坑**（详见第六部分）：
① 用 `for` 循环给 RAM 赋初值 → 背景 RAM 被推断成 **153,909 个触发器**，综合一步跑 475 秒不结束；
② 读写挤在同一个 `always` 块 → Efinity 报 `EFX-0657`，RAM 又被映射成逻辑单元。
修法是抽出了 `mmt_dpram.v` 这个"能正确推断 BRAM 的模板"。

### 4.3.2 `mmt_fusion_vote.v` —— 60/25/15 加权融合（130 行）

完全按任务书的融合策略实现，**Q8 定点**（×256）：

```
综合得分 = 视觉×154 + 温度×64 + 环境×38      // 154/256≈60%, 64/256=25%, 38/256≈15%
            ^^^^      ^^^^      ^^^^
            三个权重加起来正好 256
```

判定：得分过阈值 + 非授权时段 → 报警。

**已验证**：与浮点原型逐帧对比 60 帧，**最大得分偏差 0.00613（0.61%）**，
报警结论**零处不一致**，10 个关键场景（含 30.0°C / 38.0°C 边界）全部一致。

### 4.3.3 `mmt_video_downscale.v` —— 降采样（125 行）

1920×1080 → 160×120（X 方向 12 抽 1，Y 方向 9 抽 1）。
**为什么要降采样**：1080p 逐像素跑帧差对 BRAM 和时序都太贵，而且送给软核的推理输入本来就是小的。
160×120 正好和 MLX90640 的 32×24 热成像在空间上可比。

## 4.4 OSD 叠加（自研，279 行）

`mmt_osd_overlay.v` 按任务书要求「分区域显示」实现三层叠加，4 级流水线：

1. **主区域**：原视频画面
2. **侧边温度热力图小窗**：32×24 像素，放大到 8 倍显示在 (1632, 32) 位置，
   色阶由软核写进 `MMT_OSD_TH_*` 缓冲
3. **底部环境参数文字**：3 行 × 48 列的字符，8×16 点阵字体（`font8x16.hex`），

4. **报警红框**：8 像素宽的红色边框

文字内容由 RISC-V 固件通过 `MMT_OSD_TXT_ADDR/DATA` 写进 144 字节的字符缓冲

### 4.6.3 固件的内存布局（**实测出来的，不是照抄**）

```
RAM = 0xF9000000，32 KB (0x8000)
  ├── .text / .rodata   约 3 KB
  ├── .bss              约 1.6 KB
  └── .stack            1 KB（从 0x8000 顶端往下长）
```

实测：`text 3089 + bss 2688 = 5777 字节`，剩余约 27 KB 可用。

**复位向量 = 0xF9000000**（从生成的网表里读出来的：`IBusCachedPlugin_fetchPc_pcReg <= 32'hf9000000`）。

### 4.6.4 固件是怎么"装进" FPGA 的（重要且不直观）

SoC 的片内 RAM **不是下载进去的，而是在综合时作为 BRAM 初值烧进 bitstream 的**。
厂商网表用 `$readmemb` 读 4 个文本文件：

```verilog
$readmemb("EfxSapphireSoc.v_toplevel_system_ramA_logic_ram_symbol0.bin", ram_symbol0);
// ... symbol1/2/3
_zz_ram_port0 = {sym3, sym2, sym1, sym0};              // 小端拼接
_zz_address  = io_bus_cmd_payload_fragment_address >>> 2;
```

格式（**自己解出来的，后来在厂商自己的脚本里得到印证**）：
- 4 个文件，每个 **RAM字节数/4** 行
- 每行 **8 个 `'0'`/`'1'` 字符**（`$readmemb` = 二进制文本格式），LF 换行
- **地址 `4*i+N` 处的字节 → `symbolN[i]`**

工具 `sw\hex2soc.ps1` 就是做这个转换的，**自带往返校验**（生成后解回来逐字节比对，不一致就非零退出），
并有 `-Install` 直接把文件装进 IP 目录（**必须同时覆盖两处副本**，否则会出现"换了固件但烧进去还是旧的"）。

## 5.3 ★★ 自建的 RV32IM 裸机模拟器（本工程最有价值的工具）

**背景**：本机**没有宿主 C 编译器**（gcc / clang / cl / tcc 全都没有），只有 RISC-V 交叉工具链；
**也没有任何 RISC-V 模拟器**；板子还没到。结果是：`sw\` 下所有代码和移植的厂商库，
**此前只能证明"能编译"，从来没被真正运行过**。

**解决方案**：自己写一个 RV32IM 裸机模拟器 —— `tools\rv32sim.py`（约 500 行 Python）。
裸机 RV32 程序是一个封闭世界：载入平铺二进制、从入口符号开始执行、就完了。
足够小，可以在几百行 Python 里忠实地模拟。

**支持范围**：RV32IM（无压缩指令 C、无原子 A、无浮点 F/D）、小端、无 MMU、无缓存。
MMIO 用"陷阱+钩子"建模 —— 测试程序就是靠往 `0xF0000000` 写字节来"打印"的。

**它立刻带来了两个真实收获**：

1. **能真正运行厂商的 Melexis MLX90640 库**，并与独立重算的 Python 期望值**逐位比对**（见 5.4）
2. **测出了固件的真实性能**：整条 `ExtractParameters + GetVdd + GetTa + 768 像素 CalculateTo`
   跑完只要 **7.87M 周期**（约 11 秒模拟时间）

**顺带测出一个关键性能事实**：厂商库里的 `POW2(x)` 宏展开是 `pow(2, (double)x)`，
没有 FPU 的 RV32 上要走 libgcc 的**软双精度**，**每次 pow 约 13 万周期**。
768 个像素 × 4 次 pow ≈ **3 亿周期**（在 100MHz 主频下就是 3 秒）—— **根本跑不动**。
解决办法：`sw\test\rv32_fastmath.c` 提供了一个**逐位等价**的快实现 ——
因为 `pow(2, n)`（n 为整数）的结果是精确可表示的，直接按 IEEE-754 位布局拼出 2^n（指数域 = n+1023），
与 libm 结果完全相同，但只要几十个周期。**这条经验对将来的固件实现至关重要。**

## 5.4 Melexis 官方库的验证（任务1 的"温度数据预处理"）

任务书要求「读取 MLX90640 原始红外数据及 EEPROM 校准参数，完成环境温度、增益、偏置、发射率等补偿，
计算各像素目标温度」。这部分厂商给了完整的 C 库，我们的做法是**移植 + 往返验证**：

1. **库原样纳入**：`sw\lib\mlx90640\MLX90640_API.c` **一字未改**（Melexis 官方，Apache-2.0）。
   平台相关部分只有 `MLX90640_I2C_Driver.h` 声明的 5 个 I2C 函数，由我们提供实现
2. **合成 EEPROM**：`sw\test\gen_mlx_ee.py` 按 EEPROM 位域布局，把**已知的参数**编码成
   `eeData[832]`，同时算出"应该被提取回什么"
3. **在 RV32 上真跑**：`sw\test\t_mlx.c` 调厂商的 `MLX90640_ExtractParameters()` 等，
   把所有参数以**十六进制位模式**打印（浮点比较做到逐位相等，比十进制更有说服力）
4. **独立重算比对**：`sw\test\verify_mlx.py` 按 EEPROM 位域**独立重新推导**每个参数，逐位比对

**结果：27 项全部逐位一致**（kVdd、vdd25、vPTAT25、gainEE、KtPTAT、KvPTAT、alphaPTAT、tgc、KsTa、
ksTo[0..4]、ct[0..4]、alphaScale、ktaScale、kvScale、alpha[0]、offset[0]、kta[0]、kv[0]），
且 `CalculateTo` 对 768 个像素全部产出有限值。

**并且做了反向验证**：在厂商 C 里注入一个 `+1` 的错误，校验脚本**精确报出**
`PIX_offset0 got=0x60 want=0x5F`，恢复后回到全过 —— 证明这个校验链不是空跑。

**顺带发现的库缺陷（重要）**：`MLX90640_API.c` 里有 **3 处无界的 `while` 重标定循环**
（alpha `while(temp<32767.4)`、kta/kv `while(temp<63.4)`）。
**如果 EEPROM 是空白/损坏的（校准系数全 0），`temp` 恒为 0，这些循环会永久死循环** ——
库自身没有任何超时机制。另外 `GetFrameData` 里的 `while(dataReady==0)` 轮询也没有超时。
→ **结论：固件必须先校验 EEPROM 再交给库**。这个坑我们真的踩到了（测试卡死过一次）。

## 6.1 工程配置类

### 坑 1：`link.ld` 的内存大小写错了（链接能过、一跑就飞出 RAM）

**现象**：链接脚本写的 `RAM ORIGIN=0x00000000, LENGTH=124K`，但真实片内 RAM 只有 8 KB，
而且基址也不是 0。链接器不报错，固件却根本跑不起来。

**根因（查了很久才水落石出）**：那个 `124` 来自 SoC IP 的参数 `LDSize=124`。而读 IP 的参数定义
（`ip_component.xml`）发现：

```xml
<ipxact:name>LDSize</ipxact:name>
<ipxact:displayName>Application Region Size</ipxact:displayName>
<efinix:isPresentGUI>${DDR} == 1</efinix:isPresentGUI>
<efinix:enable>(${DDR} == 1)</efinix:enable>
```

**`LDSize` 是"应用区大小"，而且只在 `DDR == 1` 时才存在/生效**。
我们那个 IP 是 `DDR=0`，所以 `LDSize=124` 是个**未激活的残留参数**，被误当成了 RAM 大小。

**教训**：**读 IP 参数之前，先确认它在你当前的配置下是否生效。**

**正确的值从哪来**（三条独立证据）：
1. 生成 IP 的原始命令行 `source/soc_config`：`--onChipRamAddress 0xf9000000`、`--onChipRamSize 0x2000`
2. 生成的网表：`IBusCachedPlugin_fetchPc_pcReg <= 32'hf9000000`（复位向量）、
   `logic_hitsS0_0 = ((addr & ~32'h00001fff) == 32'hf9000000)`（8KB 窗口掩码）
3. 反汇编板卡包自带的 demo 固件：里面出现 `0xF9001000`(RAM)、`0xF8010000`(UART)、`0xF8016000`(I2C)

### 坑 2：三处软硬件地址全错（而且是"编译全绿、只有上板才炸"的类型）

| 名字 | 曾经写的（错） | 正确值 | 依据 |
|---|---|---|---|
| 片内 RAM 基址/大小 | `0x00000000 / 124K` | **`0xF9000000 / OCRSize` 字节** | 生成的网表复位向量 + 窗口掩码 |
| 自定义寄存器基址 | `0x00100000` | **`0xF8100000`** | APB 解码器 `==0x100000`，APB 桥在 `0xF8000000` |
| UART 基址 | `0xF8001000` | **`0xF8010000`** | APB 解码器 `==0x010000`；demo 固件里也出现 |

**错的来源**：全部抄自 `ip\sapphire_soc\settings.json`。但**那份文件自相矛盾** ——
它把 UART 写在 `4096`（0x1000），而 `soc_config` 和 demo 固件都用 `0x10000`，差 16 倍。
`APBSlave0_M_Addr=0x00100000` 这个值本身没错，但它只是**APB 桥内部的偏移**，被当成绝对地址用了。

**教训**：**以生成的 RTL / soc_config 为准，settings.json 只当参考。**

### 坑 3：`OCRSize` 才是片内 RAM 大小（单位：字节）

| `OCRSize` | 生成的 symbol 文件 | 推算 RAM |
|---|---|---|
| 4096 | 9216 字节（1024 行） | 4 KB |
| 8192 | 18432 字节（2048 行） | 8 KB |
| 32768 | 73728 字节（8192 行） | **32 KB** |

规律：**行数 × 4 = RAM 字节数**。（因为 4 个符号文件各存一路字节，地址 `4*i+N`）

## 6.2 Efinity 工具链的坑

### 坑 4：`EFINITY_HOME` 必须是正斜杠

`D:\Efinity\2026.1` 里的 `\2026` 会被 Tcl 当成**八进制转义**吃掉，PnR 直接崩。
必须写成 `D:/Efinity/2026.1`。

### 坑 5：`.cmd` / `.bat` 里不能写中文注释

cmd.exe 用 OEM 代码页解析，UTF-8 中文会把后面的行拆坏。**批处理一律纯 ASCII。**
（`.ps1` 也有类似问题：无 BOM 的 UTF-8 会被 Windows PowerShell 5.1 按 ANSI 解码）

### 坑 6：GUI 和命令行脚本的包含目录不一致（"我这儿能编、IDE 编不了"）

**现象**：命令行脚本能综合通过，但在 Efinity IDE 里点"综合"就报：
```
ERROR : mmt_top.v(32): cannot open include file 'ddr3_controller/ddr3_parameter.vh'
```

**根因**：`\`include` 是相对**包含它的文件所在目录**解析的。原顶层在 `rtl\` 下，
写的 `"ddr3_controller/ddr3_parameter.vh"` 能找到；我们把新顶层放到 `rtl\mmt\` 子目录后，
它就去找 `rtl\mmt\ddr3_controller\` 了 —— 找不到。
命令行脚本靠额外传了一个包含目录（`rtl`）绕过去了，但 **IDE 不知道**。

**修法**：把 include 改成**相对本文件的路径**（`../ddr3_controller/ddr3_parameter.vh`），
这样**不再依赖任何包含目录设置**，两边行为一致。

**另一个相关点**：工程 XML 里的 `<efx:param name="include" value="..."/>` 就是包含目录设置，
**GUI 读它生成 `-I` 参数，但 `efx_map` 自己并不读**。所以脚本要么也读同一份 XML，要么显式传 `-I`。
本工程的做法：**构建脚本从 XML 里解析 include 列表**，保证两边永不漂移。

### 坑 7：工程 XML 的注释里不能出现 `--`

XML 规范禁止注释内容含 `--`。我写了一句带 `--I` 的注释，XML 直接解析失败：
`An XML comment cannot contain '--'`。

### 坑 8：删 XML 子块时把根结束标签一起删了

手动按行号删 `mipi_dphy_info` 段，把结尾的 `</efx:design_db>` 也删了，lxml 报
`Premature end of data in tag design_db`。
**教训**：删 XML 子块要按"起止标签"定位，并且**事后一定用解析器验一遍**
（PowerShell 一行：`(New-Object System.Xml.XmlDocument).Load(路径)`）。

### 坑 9：把 peri 里的 DPHY 块整个删掉，会让 Interface Designer 自己崩

我们删了 DSI TX，但 `peri.xml` 里还留着 DPHY 块，生成的 `interface.csv` 里带这些行：
```
required output, 172, 323, 0, __bypass__, mipi_dp_clk_RST
```
`efx_pnr` 于是报 `Required pin mipi_dp_clk_RST is not found` 并失败。

看起来删掉那个块就行 —— **但删了之后 Interface Designer 自己崩**：
```
File ".../pt/bin/design/service.py", line 2537, in _build_common_mipi_dphy
    self.design.mipi_dphy_reg.apply_device_db(self.design.device_db)
AttributeError: 'NoneType' object has no attribute 'apply_device_db'
```
即块不存在时 `_build_block_reg()` 返回 None，而 MIPI 这条路**没有 None 判断**
（它的兄弟 `_build_spi_flash_reg` 就有）。这是**厂商工具的 bug**，不适合去改安装目录里的代码。

**采用的方案**：peri 文件保持原厂原样（工具能跑），**改为过滤生成出来的 CSV** ——
写了个 `filter_interface.ps1`：从顶层 HDL 解析真实端口表，把 CSV 里"设计上不存在的 required 行"删掉，
并**逐行打印删了什么**（可审计）。实测恰好只删那 5 行。

### 坑 10：给 output 端口接常量

SoC 的自定义指令端口里，`cpu0_customInstruction_cmd_valid` 等是 **output**（SoC 发给加速器），
`cmd_ready` / `rsp_valid` / `outputs_0` 是 **input**。
我第一次把方向搞反了，给 output 接常量，Efinity 报 `constant is not allowed here [VERI-1180]`。
**教训：端口方向要读真实模块声明，不要凭"名字像输入"猜。**

## 6.3 RTL 设计的坑

### 坑 11：把 `gp` 忘了设

RTL 仿真/裸机测试里，如果用 `-nostartfiles` 排除了 crt0，**就没人设 `gp`（x3，全局指针）**。
而 RISC-V 链接器的 relaxation 会把小数据访问改写成 gp 相对寻址，
于是 `gp=0` 时访问地址变成 `0 + 小偏移` —— 表现为莫名其妙的陷阱地址（比如 `0xFFFFFA3C`，其实就是 −1476）。
**修法**：模拟器启动时把 `gp` 设成 `__global_pointer$` 符号的值（这正是 crt0 干的事）。

### 坑 12：链接顺序 —— `-lm` 必须放在源文件之后

GNU ld 是**单遍链接器**。把 `-lm` 放在源文件前面会得到
`undefined reference to 'sqrt'`，明明 libm 装了也没用。

### 坑 13：用 RAM 必须按模板写，否则综合爆炸

**现象**：`mmt_frame_diff.v` 原来用 `for` 循环给背景 RAM 赋初值，
综合报 `Clock Network 'clk' with 153909 loads` —— **背景 RAM 被推断成了 153,909 个触发器**，
综合一步跑 475 秒还没结束。

**第二个症状**：修了初值之后，读写又挤在同一个 `always` 块里，
Efinity 报 `EFX-0657`，RAM 又被映射成逻辑单元。

**正确写法**（抽成了 `mmt_dpram.v` 模板）：
- **读写分成两个独立的 `always` 块**
- **读口无条件寄存读**（不要在 `if` 里条件寄存）
- **绝对不要用 `for` 循环给 RAM 赋初值**（要初值就用 `$readmemh` 或让外部灌）

### 坑 14：多驱动（VDB-1000）

`scl_o` 被两个 `always` 块同时赋值 → Efinity 报 `VDB-1000`。
**同一个信号只能在一个 `always` 块里赋值。**

### 坑 15：位宽不够导致静默截断

`bit_cnt` 只有 3 位，代码里写 `3'd8` 被截断成 0 → ACK 判断从根上就错了。
**这个只有编译器 warning 提示，不报错。** 后来改成 4 位。

### 坑 16：`3*` 写成了 `2*`（扁平向量宽度）

hub 有 3 个客户端，扁平向量要按 `3*` 声明。写成 `2*` 会被 iverilog 报
`Port c_dev_addr expects 21 bits, got 14` 并**自动补零**，导致事务全错（而且是静默错）。

## 6.4 验证方法本身的坑（**这一类最容易被忽视**）

### 坑 17：加了测试 ≠ 测到了（空测试）

**案例 A**：第一版冒烟测试里写 `if (100 % 7 != 14) fail;` 这类检查 ——
**操作数全是常量，编译器直接常量折叠成结果，被测的指令根本没执行**。
于是模拟器里一个真实的 bug 被"全部通过"掩盖了。
→ 正确做法：操作数从 `const` 数组里读，编译器不能折叠。

**案例 B**：给 I2C 主机补"请求相位遍历"测试时，第一版抖动只做了 1~8 拍，
而一个位周期是 100 拍 —— **100 拍里只挪了 8 拍，压根进不了坏窗口**，
把修复撤掉重跑**照样全绿**。那就是个空测试。

**教训**：**"加了个测试"不等于"测到了"。任何新测试都必须做一次"反向验证"** ——
把被修复的 bug 重新注入，确认测试真的会红。

### 坑 18：旧产物骗过测试（**我在整理工程时又踩了一次**）

`run_rv32_tests.ps1` 漏传了头文件搜索路径，`t_mlx` 编译失败 ——
**但它一直"通过"**，因为目录里还留着手工构建的旧 `t_mlx.bin`，
编译失败不影响模拟器去跑那个**上一次的**二进制，校验脚本照样全绿。

**教训**：**任何"只是跑一下已有产物"的测试步骤，都必须先清掉产物再构建。**
现在脚本开头会 `Remove-Item test\build -Recurse -Force`，
编译一失败就会因为"二进制不存在"立刻暴露。

### 坑 19：PowerShell 把函数的输出流吃掉了

```powershell
if (-not (Run-Test ...)) { $fail++ }     # ← Run-Test 内部所有 Write-Output 都不显示
```
**用在表达式上下文里的函数，其整个输出流被当作表达式的值吃掉。**
所以那段时间所有小节标题一行都没打印，我还以为测试没跑。
→ 函数里要直接写控制台就用 `Write-Host`。

### 坑 20：iverilog 的两个怪癖

1. **`fork ... join_none` 会卡死父进程**。在 tb 的主 `initial` 块里挂一个
   `fork forever begin : probe ... end join_none` 调试探针，iverilog 11.0 下**主块直接停住**，
   表现为 `0 checks` + 看门狗超时。查了很久才发现是探针干的。
   → **调试监视一律用普通 `always` 块。**
2. **`$display("%0s", <宽向量>)` 会把多字节 UTF-8 打散成乱码**：
   同一个文件里 `$display("...通过")` 这种**字符串字面量**中文完全正常，
   但经向量传参的 `check(cond, msg)` 里的中文就糊成一团。
   → **`check()` 的消息只用 ASCII**，中文解释写在注释里。
3. **`$time` 用 `%0t` 打印的是 ps**（timescale `1ns/1ps` 的精度），不是 ns。
   按"ns"读时间戳会得出完全错误的结论。

### 坑 21：等错了信号

测试平台用 `wait_valid()` 等"失败周期" —— 但 **CRC 错 / NACK 的周期根本不会产生 `data_valid`**，
于是只能等到超时；而超时窗口比一个完整周期还长，期间 DUT 早就跑完下一轮正常测量把 `crc_err` 清掉了。
结果检查项永远失败，看着像 RTL 错，其实是测试平台等错了信号。
→ 改为分别等 `crc_err` / `bus_err`。

## 6.5 厂商库/模型的坑

### 坑 22：通用 I2C 从机模型的四个 bug（写共用模型时踩的）

1. **预装数据丢失**：寄存器堆的写只在 `posedge scl or negedge scl` 触发。
   但**总线空闲时 SCL 一直被上拉、根本不跳变**，于是 testbench 在仿真最开始做的预装**全部丢失**，
   从机读出来永远是 0。→ 敏感列表要加上 `posedge mem_we`
2. **`byte_count` 跨事务累加**："第一个数据字节 = 寄存器地址"的判断是 `byte_count == 1`，
   而它从不复位 → 第二笔事务开始它再也不是 1，于是**命令字的第一个字节被当成数据写进寄存器**。
   实测把 `mem[0]` 从 `0x60` 冲成 `0x24`。→ START 时复位计数器
3. **多字节读只出第一个字节**：读事务里 `tx` 只是被移空成 0，没有"装载下一个字节"的逻辑。
   SHT30 一次要读 6 字节，除第一个外全是 0，CRC 必然不过
4. **最后一个字节后不释放 SDA**：主机回 NACK 表示"读完了"，从机却继续驱动下一个字节的 MSB，
   把 SDA 一直拉住 —— **主机做不出 STOP 条件**。→ 在做 ACK 位时记住主机电平，NACK 就释放

### 坑 23：厂商 MLX90640 库会用"零值"死循环

见 5.4 末尾。**EEPROM 空白/损坏时，三个重标定 `while` 循环会永久死循环。**

   - **路线 A（推荐先做）**：跑小模型（如 ds_cnn_kws / hello_world），
     **不给 SoC 开 DDR**，模型权重放 BRAM。改动小、风险低、能先把"加速器 + 自定义指令 + 后处理"
     整条数据通路打通
   - **路线 B**：一步到位给 SoC 开 DDR（官方 demo 是 `DDR=1` + 16MB，固件镜像 4 MB），
     能跑 mobilenet 那种真模型，但改动大（SoC 要加 DDR 端口、固件链接脚本要改成 DDR 运行、bootloader 问题）
3. **把 Melexis 接进固件** —— 库已验证可跑；差的是数据通路：
   FPGA 侧要能把 EEPROM（0x2400 起 832 字）和红外帧搬到软件能读的地方。
   目前 `mmt_mlx90640_ctrl` 只搬了帧、没搬 EEPROM（设计上是"RISC-V 开机读一次"）。
4. **实现滑动平均滤波**（任务书明确要求的数据预处理之一）

## 9.2 第 1 层：FPGA 是什么

**一句话**：FPGA 是一块"可以由你重新连线的数字电路"，里面是海量的可配置逻辑块和可配置连线。
你写代码描述电路，工具把电路"烧"进去。

**和单片机的根本区别**：
- 单片机（比如 STM32）是**顺序执行**的，一条指令一条指令跑；硬件固定
- FPGA 是**并行**的，你描述的所有逻辑**同时**在工作；硬件由你的代码决定

**这个区别在本工程里的体现**：
摄像头像素流是**每个时钟来一个像素**，帧差、降采样、OSD 叠加都是**同时**在流水线上做的，
不是"一条条处理"。而融合决策那种"要算一下、判断一下"的逻辑，就交给 RISC-V 顺序执行更合适 ——
**这就是软硬协同的价值**。

**关键概念**：
- **LUT（查找表）**：FPGA 里实现任意组合逻辑的基本单元。一个 4 输入 LUT 就是一张 16 项真值表
- **触发器（FF）**：存 1 bit 的存储单元，是时序逻辑的基础
- **BRAM**：块状 RAM，FPGA 里大容量存储的硬块（本工程 256 个）
- **DSP**：专用的乘法累加硬块（本工程 160 个）
- **XLR**：Efinix 特有的逻辑单元叫法（一个 XLR ≈ 一个 LUT4 或一个 LUT4+FF）

**本工程对应**：`out\mmt.place.rpt` 里 `XLRs: 20833 / 60800` 就是逻辑占用；
`Memory Blocks: 140 / 256` 是 BRAM 占用；`DSP Blocks: 12 / 160` 是乘法器占用。

## 9.3 第 2 层：Verilog HDL 基础

Verilog 是**硬件描述语言** —— 你写的不是"程序"，是"电路的结构"。

**必须建立的两个心智模型**：

1. **`always @(posedge clk)` 块 = 一组触发器**。
   里面每一句 `a <= b;` 意思是"在时钟上升沿，把 b 的值锁存到 a"。
   这不是"赋值语句"，是"连了一根线 + 一个触发器"。

2. **`assign y = a & b;` = 一根线 + 一个与门**。纯粹的组合逻辑。

**阻塞 vs 非阻塞赋值（初学者最容易错的地方）**：
- `=`（阻塞）：像写软件一样，立刻生效。**只用在组合逻辑**（`always @(*)`）里
- `<=`（非阻塞）：**在时序逻辑（`always @(posedge clk)`）里必须用这个**。
  它表示"所有赋值在时钟沿同时发生"，如果你用 `=`，仿真结果会和实际电路不一致

**本工程对应**：
- 时序逻辑例子：`rtl\mmt\sensors\mmt_i2c_master.v` 里的分相时钟计数器
  ```verilog
  always @(posedge clk or negedge rst_n) begin
      if (!rst_n) begin div_cnt <= 16'd0; ph <= 2'd0; end
      else if (tick) begin div_cnt <= 16'd0; ph <= ph + 2'd1; end
      else begin div_cnt <= div_cnt + 16'd1; end
  end
  ```
- 组合逻辑例子：同一个文件里
  ```verilog
  wire tick    = (div_cnt == DIV[15:0] - 16'd1);
  wire act_sda = tick && (ph == 2'd1);
  ```

**还要理解**：
- `parameter` / `localparam`：参数化设计（本工程里 I2C 分频、传感器周期都是参数）
- 位宽：`[7:0]` 是 8 位。**位宽不匹配会静默截断**，本工程为此踩过坑（`3'd8` 被截成 0）
- `case` / `if`：和软件类似，但注意**组合逻辑里必须覆盖所有分支**，否则会综合出锁存器
- `generate`：批量例化（本工程 OSD 里批量例化文字行）

## 9.4 第 3 层：时序与同步设计（**FPGA 的核心难点**）

**时钟**：FPGA 里绝大多数电路都跟着一个时钟节拍工作。本工程有两个主要时钟：
视频域 148.5MHz、系统域 100MHz。**不同时钟域的东西不能直接连**（见第 6 层）。

**建立时间 / 保持时间（Setup / Hold）**：
- 数据必须在时钟沿**之前**稳定一段时间（建立时间）
- 在时钟沿**之后**再保持一段时间（保持时间）
- 违反了这个，触发器可能采到不稳定的值 → **亚稳态**

**为什么要关心**：这就是"时序收敛"。综合/布局布线工具会算每条路径的延迟，
报告"最高能跑到多少 MHz"。本工程 PnR 带 `--timing_analysis on` 通过。

**同步设计原则**：
- 一个 `always` 块里只用**一个**时钟
- 不要用时钟去做逻辑（比如 `assign clk2 = a & clk;`）—— 会产生毛刺
- 需要分频就产生**时钟使能信号（clock enable）**，而不是真的分一个时钟出来

**本工程对应**：`Panel_1080p_reg.mem` 里存的就是 1080p60 的时序参数
（H total、前后沿、同步宽度等）。`hdmi_tx_slow_clk` 148.5 MHz 就是 1080p60 的像素时钟。

## 9.5 第 4 层：★★ IP 核是什么（用户点名要搞清楚）

**IP = Intellectual Property（知识产权）**，但在 FPGA 语境里，**"IP 核"就是"别人写好、验证好、
你直接拿来用的功能模块"**，可能以源码、网表或加密形式给你。

**打个比方**：写 FPGA 项目像搭积木。你不会自己去"造"一个 USB 控制器、
一个 DDR3 控制器、一个 PCIe 接口 —— 这些又复杂又要严格符合协议，
硬做出来也没人敢用。所以厂商把常用功能做成 IP 核，你例化一下就能用。

**IP 核的三种形态**：
| 形态 | 特点 | 本工程的例子 |
|---|---|---|
| **源码 IP**（Verilog/VHDL 源码给你） | 能看能改 | `rtl\` 下从 demo 复用的那些模块（严格说这是"参考设计源码"，不算正式 IP） |
| **加密/网表 IP**（给你一个巨大的不可读 .v） | 能例化、能综合，但看不懂内部 | `ip\csi_rx_controller\csi_rx_controller.sv`、`ip\sapphire_soc\sapphire_soc.v`（1.1 MB！） |
| **硬核 IP**（FPGA 芯片里**固化的**电路） | 不占逻辑资源，性能固定 | 板上的 PLL、BRAM、DSP、片上的晶振 OSC |

**"生成 IP"是什么意思**：很多 IP 是**可配置**的，你需要先选参数，工具再根据参数生成对应的源码。
比如本工程的 Sapphire SoC，需要配置：
- 片内 RAM 多大（`OCRSize`）
- 有没有 DDR 接口、APB 从口、多少个 GPIO、UART 波特率分频
- 要不要自定义指令端口（`CustomInstruction`）

**这些参数会决定生成的网表长什么样、有哪些端口**。配置完之后工具生成
`<ip名>.v` + `<ip名>_tmpl.v`（例化模板）+ `settings.json`（配置记录）。

**⚠️ 本工程在 IP 上踩过的最大坑**（见第六部分坑 1）：**参数不是都生效的**。
`LDSize` 这个参数写着 124，看起来像"RAM 大小"，实际上它只在 `DDR=1` 时才生效，
直接抄它就翻车了。**读 IP 参数前先确认它在你当前配置下是否生效。**

**IP 通常怎么来的**：
- Efinity 的 **IP Catalog**（图形界面里选）：本工程 38 个官方 IP，比如 `efx_soc`（RISC-V）、
  `efx_bram`、`efx_dma`、`efx_axi_interconnect`、`efx_pll_cfg` 等
- 厂商的**参考设计包**（板卡包 demo）：本工程视频链的 66 个文件都是从这里来的
- **第三方开源 IP**：本工程用的 Efinix TinyML 加速器就来自 GitHub 公开仓库
- 自己写：本工程 `rtl\mmt\` 下约 3,000 行全是自己写的

**本工程用到/将要用的 IP 清单**：
| IP | 来源 | 作用 |
|---|---|---|
| `csi_rx_controller` | 板卡 demo | MIPI CSI-2 摄像头接收 |
| `sapphire_soc` (efx_soc 3.4.0) | Efinity IP Catalog（**用脚本命令行生成**） | RISC-V 软核 |
| TinyML 加速器 | Efinix 官方 GitHub 仓库 | 神经网络硬件加速（**还没接**） |
| `efx_axi_interconnect` | Efinity IP Catalog | 将来接 TinyML 时要把多个 AXI 主口汇到 DDR3 |

## 9.6 第 5 层：从代码到电路 —— 综合与布局布线

**三个步骤**：
1. **综合（Synthesis / `efx_map`）**：把你的 Verilog 翻译成 FPGA 里的基本单元
   （LUT、触发器、BRAM、DSP）的**连接表**。输出 `.vdb`。
   - 这一步会做**逻辑优化**：比如 `a & 1'b1` 直接变成 `a`
   - 也会**推断**（inference）：你写 RAM 的写法决定了它被推断成 BRAM 还是触发器
     （**本工程为此踩过大坑**，见第六部分坑 13）
2. **布局（Place）**：把这些单元放到芯片上的具体位置
3. **布线（Route）**：连好线
   - 布局布线合称 PnR（Place and Route），Efinity 里是 `efx_pnr`

**为什么要关心"推断"**：BRAM 和触发器都是存储，但代价天差地别 ——
BRAM 是硬块（本工程 256 个），触发器是逻辑资源（用 XLR 实现）。
一块 160×120 的 8 位背景帧 RAM 如果被推断成触发器，就是 153,600 个触发器，
**直接超过整颗芯片的容量**（本工程真的踩到了，见坑 13）。

**时序约束（SDC）**：一个文本文件，告诉工具"我的时钟是多少 MHz、
哪些路径是假的不用管"。本工程是 `constr\ti60f225_oob.sdc`。

## 9.7 第 6 层：跨时钟域（CDC）

**问题**：两个不同时钟域的电路，一个在 148.5MHz 下跑、一个在 100MHz 下跑。
你从 A 域送一个信号到 B 域，会发生什么？
- 单比特电平信号：可能采到**亚稳态**（不确定是 0 还是 1）
- 单比特脉冲：B 域时钟更慢的话，**可能完全采不到这个脉冲**（脉冲太窄）
- 多比特数据：各位的延迟不同，可能采到**中间值**（比如从 0x0F 变到 0x10，采到 0x1F 这种不存在的值）

**三种标准解法**（本工程三种都用到了）：
1. **两级触发器同步器**（`mmt_sync2.v`）：用于单比特电平信号。
   第一级可能进亚稳态，但到第二级就稳定了
2. **脉冲 → 电平翻转**：单比特脉冲跨域会丢，就改成"每来一次脉冲就翻转一次电平"，
   同步过去后检测翻转沿，还原成本域的脉冲。
   **本工程的 `bg_clear_tgl` 就是这么做的**
3. **数据 + 握手/标志**：多比特数据不能直接同步，要配合一个标志位。
   **本工程的 `alg_frame_tgl` 就是这个思路** —— 视频域每完成一帧翻转标志，
   系统域只在标志变化时才去读数据（数据早就稳定了）

**本工程对应源码**：`rtl\mmt\common\mmt_sync2.v`、
`rtl\mmt\mmt_top.v` 里 `sy_bg_clear` 和 `alg_frame_tgl_s` 那两段。

## 9.8 第 7 层：总线与接口协议

### APB3（Advanced Peripheral Bus）—— 低带宽外设寄存器

**用途**：CPU 读写外设寄存器用的简单总线。**本工程的软硬件接口就是 APB3**。

**时序**：一次读写 3 拍
1. `PSEL` 拉高 + `PENABLE=0`（setup 阶段）
2. `PENABLE=1`（access 阶段），`PWRITE=1` 表示写、`PADDR`/`PWDATA` 有效
3. `PREADY` 拉高表示完成

**本工程对应**：`rtl\mmt\soc\mmt_soc_regs.v` 就是一个 APB3 从设备，
实现了一组寄存器（见 3.4 节的寄存器映射表）。

### AXI4 —— 高带宽内存访问

**用途**：大块数据传输（DMA、DDR 访问）。比 APB 复杂得多，
有 5 个独立通道（写地址、写数据、写响应、读地址、读数据），支持突发传输（burst）。

**本工程对应**：DDR3 控制器就是 AXI4 接口；将来 TinyML 加速器也要通过 AXI 去读模型权重。

### I2C —— 两线串行总线（**本工程自研的重点**）

**物理层**：两根线 SCL（时钟）+ SDA（数据），**开漏输出 + 上拉电阻**。
开漏的意思是：器件只能把线拉低，不能主动拉高；拉高靠上拉电阻。所以两根线都是双向的。

**为什么开漏**：多个器件挂同一条线，如果都推挽输出（能主动拉高/拉低），
一个拉高一个拉低就短路了。开漏保证"谁想拉低就拉低"，不会冲突。

**协议**：
- **START 条件**：SCL 为高时，SDA 从高变低
- **STOP 条件**：SCL 为高时，SDA 从低变高
- **数据位**：SCL 低时改 SDA，SCL 高时采样 SDA
- **每字节 9 拍**：8 位数据 + 1 位 ACK（接收方把 SDA 拉低表示应答）
- **重复 START**：不先 STOP 直接再来一个 START，用于"先写地址再读数据"的场景

**本工程对应**：`rtl\mmt\sensors\mmt_i2c_master.v` 完整实现了上面全部要素，
逐行注释写得很详细，是学习 I2C 的好材料。

**本工程用到的三个 I2C 器件地址**：SC431HAI(0x30)、MLX90640(0x33)、SHT30(0x44)。

### MIPI CSI-2 —— 摄像头串行接口

差分信号，1~4 条数据 lane + 1 条时钟 lane，速率可到 1.5Gbps/lane。
摄像头把图像按行打包成包发出来。**本工程用厂商 IP 处理，自己不用实现。**

### HDMI / TMDS —— 显示输出

TMDS 是差分编码，4 对差分线（1 对时钟 + 3 对数据，数据里编了 RGB + 控制信号）。
**本工程用厂商的 `dvi_encoder`。**

## 9.9 第 8 层：软核处理器与软硬件协同

**"软核"是什么**：用 FPGA 逻辑**搭出来**的 CPU。
- 硬核 CPU：芯片里固化的 CPU 电路（比如 Zynq 里的 ARM）
- **软核 CPU**：用 LUT/FF 拼出来的 CPU，**占逻辑资源，但可以裁剪、可以改**

**本工程用的**：Efinix 官方的 **Sapphire SoC**，RISC-V 架构，配置见 4.6.1。

**RISC-V 是什么**：一个**开放指令集架构**（ISA）。和 ARM/x86 的区别是它是开放的，
任何人都可以实现。**指令集**就是"这颗 CPU 认识哪些指令"。

本工程用的是 **RV32IM**：
- RV32 = 32 位
- I = 基础整数指令集
- M = 乘除法扩展
- （没有 F/D，即没有硬件浮点 —— 所以浮点要用软件模拟，**很慢**，见 5.3 的 pow 教训）

**为什么用软核**：
- 灵活：可以加自定义指令给特定算法加速（本工程 SoC 开了 `CustomInstruction` 端口，
  正是为了接 TinyML 加速器）
- 省事：复杂的状态机、协议、决策逻辑用 C 写比用 Verilog 写快得多

**软硬件协同的设计思路（本工程的核心思想）**：
| 放硬件（FPGA 逻辑） | 放软件（RISC-V） |
|---|---|
| 高速、并行、定时的部分 | 复杂逻辑、判断、状态机 |
| 摄像头采集、图像流水线 | 融合决策 |
| I2C 时序（精确到微秒） | 事件判断、授权时段比较 |
| 帧差法的逐像素运算 | OSD 文字内容的组装 |
| 报警波形生成 | 参数配置 |

**分工的原则**：能用硬件流水线做的、要求实时性的，放硬件；
"要想一想"的、逻辑复杂但不需要快的，放软件。

## 9.10 第 9 层：图像处理基础

- **RAW / Bayer 格式**：摄像头的原始输出。每个像素只有 R、G、B 中的一个
  （按 2×2 的 Bayer 图案排列），需要**去马赛克（debayer）**插值出完整 RGB
- **帧缓存与乒乓/三缓冲**：图像处理需要同时读上一帧、写当前帧，
  所以要多个缓冲区来回切换，避免撕裂
- **降采样**：1920×1080 → 160×120，就是每 12 列取 1 列、每 9 行取 1 行。
  本工程用这个来降低帧差法的运算量
- **帧差法**：当前帧 − 背景帧 → 超过阈值就是"有变化"的像素 →
  统计这些像素的数量（面积）和重心（质心）→ 判断有没有运动
- **背景建模**：背景不是固定不变的（光线会变），所以要慢慢更新：
  `背景 = 背景 + (当前 − 背景)/32`，本工程用移位实现除以 32
- **热力图色阶**：把温度值映射成颜色（蓝→绿→黄→红），本工程由软核算好色阶写进 OSD 缓冲

## 9.11 第 10 层：TinyML 与量化推理

**TinyML 是什么**：在资源极其有限的设备（单片机、FPGA）上跑神经网络推理。

**为什么不用普通神经网络**：一个 ResNet 有 2500 万参数、几 GFLOPs 的运算量，
单片机根本跑不动。TinyML 靠两招：
1. **小模型**：比如 MobileNet（深度可分离卷积，把标准卷积拆成两步，运算量降一个数量级）
2. **量化**：把 32 位浮点权重压成 **INT8**（8 位整数）。模型缩小 4 倍，
   而且整数乘法可以用 DSP 硬块做，快得多

**量化的代价**：精度会掉一点。需要"量化感知训练"或者事后校准来减少损失。

**"卷积"是什么**：一个小窗口（比如 3×3）在图像上滑动，每个位置做加权求和，
得到一个特征图。网络就是"卷积 → 激活 → 池化"堆叠起来，最后接全连接层出分类结果。

**Efinix 的 TinyML 加速器**：
- 官方 GitHub 公开仓库 `github.com/Efinix-Inc/tinyml`（国内可用 Gitee 镜像 `gitee.com/uesoft/tinyml`）
- 加速的是：卷积/深度可分离卷积、全连接、Add、Mul、Min/Max、LeakyReLU
- 配置方式：用自带的 GUI 工具分析 `.tflite` 模型，按层选"Lite 模式"或"Standard 模式"，生成配置头文件
- **接口**：命令/响应口（挂在 SoC 的自定义指令端口上）+ AXI4 主口（去读模型权重和输入张量）
- 资源（Ti60 视觉 demo 的配置，用官方估算库算的）：14,106 LUT / 9,143 FF / 59 BRAM / 12 DSP

**本工程现状**：加速器拿到了、资源核算过了、SoC 前提（自定义指令端口）也开了，**但还没接进 RTL**。

## 9.12 第 11 层：本工程的专用知识

- **Efinity 工具链**：`efx_map` / `efx_pnr` / `efx_pgm`，以及 Interface Designer
- **Interface Designer**：图形界面里配置引脚、时钟、PLL、MIPI、LVDS，
  输出 `<project>.peri.xml`（状态文件）和 `<design>.interface.csv`（给 PnR 用的约束）
- **器件手册**：SC431HAI、MLX90640、SHT30 —— 寄存器怎么配、时序要求是什么
- **多模态时间对齐**：任务书要求"以视频帧时间戳为主基准"。
  视频 30fps（33ms 一帧），传感器 1Hz（1 秒一次），
  所以要做"最近时间匹配"—— 把最新一次传感器读数配到当前视频帧上
