## 5. 任务3 第 ⑤ 项「低功耗场景管理」最小可行方案

**结论**：「固件几十行」**成立，但只成立在逻辑层**——它是"场景状态机 + 可见指示"，**不会真的省电**。真省电要动 RTL，不是今晚的事。

**可验证的事实**：
- `grep` `rtl\`+`sw\` 无任何低功耗实现（你已确认）。
- 板上没有功率计/电流测量手段——**我无法确认你有**，所以即使真省电，视频里也无法量化展示。
- CPU 没有可靠的睡眠方式（VexRiscv 的 `wfi` 是否生效我**无法确认**）。固件能做的"降功耗"只有降低主循环频率，对板级功耗几乎无影响。

**v2 固件实现（只改 `sw\main.c`，约 50~70 行，0 行 RTL）**：
- 状态：`ACTIVE`（近期有运动）/ `IDLE`（`IDLE_FRAMES` 帧无运动）/ `SLEEP`（`SLEEP_FRAMES` 帧无运动）。**用帧计数，不用时间**：主循环节拍是软件空循环，间隔不定（`main.c:583`）；`frame_ms=frame_no*33` 的 30fps 假设也**未经验证**（`main.c:272`）。
- 动作：
  - ACTIVE：现状。
  - IDLE：主循环空转 ×4（`for … 2000000` 乘系数）；不再刷热力图（`osd_write_thermal` 768 次 APB 写，`main.c:317`）；OSD 第 0 行尾追加 ` PWR:IDLE`。
  - SLEEP：空转 ×16；OSD 追加 ` PWR:SLEEP`；串口降频打印。**不要**动 `MMT_CTRL`（bit0 是帧差使能，关掉就没法唤醒）；LED 由 RTL 驱动（`mmt_top.v:1928`），固件改不了，所以 LED 指示在本方案里**做不到**，只能靠 OSD+串口。
  - 唤醒：任一帧 `motion==1` 或 `alarm` ⇒ 立即回 ACTIVE。
- **OSD 只有 3 行×48 列**（`mmt_regs.h:172-174`，`mmt_osd_overlay.v:58,171`），没有第 4 行 ⇒ 状态只能挤在现有行尾（第 0 行 28 字符，余量足）。
- 视频演示：第 5 段，手离开画面 ⇒ `PWR:ACTIVE→IDLE→SLEEP` 逐级切换 + 串口 `[PWR] state=…`。阈值取 `IDLE_FRAMES`/`SLEEP_FRAMES` 使录制时 ≤10 秒内可见（上板后按实际帧率现场调，v2 提供 UART 命令改阈值）。

**若要"真"省电的真实工作量（不建议今晚）**：
- 在 `mmt_soc_regs.v` 加 `PWR_MODE` 寄存器；`mmt_top.v` 里据此拉住 `o_cam_rst_p`（`:678`）使摄像头断电+HDMI 输出静帧。
- **难点**：摄像头配置序列（`i2c_master_reg_set.v` 61 条）只在复位后跑一次，唤醒需要重新触发该序列——要改 I2C 配置控制器 + 唤醒后重新训练 MIPI。这是 **RTL 改动+仿真+重新 PnR+上板验证**，保守估计 **1~2 个工作日**。
- 其余任务3 项更远：RGMII 以太网（板有 YT8531SC，有 `04_Ti60f225_GE_demo`，`协作日志.md:620`）、Web 监控、语音（SPI）都是 **多天** 的集成。**今晚能打勾的任务3 第二项暂无；** 建议明天决定第二项选哪个（见 §9 待问）。

## 6. 「非授权时段」输入源最小方案

**关键发现：不需要 RTL**。`CFG_AUTH`（0x3C）的 `[12:8]` 就是"当前小时"，RTL 已支持软核写入（`mmt_soc_regs.v:34,472`；`mmt_fusion_vote.v:128-133` 用它判窗口）。今天的问题只是固件把它写死成 0（`main.c:236`）。

**推荐：UART RX 命令（只改 `sw\main.c`，约 25 行；`uart_rx_ready()/uart_getc()` 已存在，`uart.c:98-111`）**：

| 键 | 效果 |
|---|---|
| `n` | `hour=0`（夜间/非授权）：`MMT_REG32(MMT_CFG_AUTH)=beg\|(0<<8)` |
| `d` | `hour=12`（白天/授权） |
| `p` | 循环测试图案 0→彩条→红→绿→蓝→关（`MMT_TEST_PATTERN_SET`） |
| `+` / `-` | 得分阈值 ±8（重写 `MMT_CFG_FUSION`） |
| `s` | 强制进入 SLEEP 状态（演示用） |

- **串口 RX 不通怎么办**：`i_uart_rxd` 绑 GPIOL_02（`mmt.peri.xml:275`），是否确实接 FT4232 的 TX **我无法确认**（该文件的注释把 GPIOR_28 称为"FT4232 的 UART_TX"，命名方向有歧义）。**备份方案（无输入也能演示）**：固件内定时自动翻转——每 N 个运动帧窗口 `hour` 在 12 和 0 间切换，OSD 第 2 行显示 `DAY`/`NIGHT`。两套都写进 v2。
- **KEY0 方案（不建议今晚做）**：KEY 脚在 `mmt.peri.xml:304` 注释里被提到（GPIOR_21=KEY2、GPIOR_22=KEY1，**我没找到是否有"KEY0"，无法确认**），但当前 `mmt_top.v` **没有任何按键输入端口**。要加：顶层端口 + `peri.xml` 绑脚 + 2FF 同步 + 消抖 + 寄存器读口（`mmt_soc_regs.v`）+ 固件轮询。= 改 RTL + 全流程重编 + 重验时序，**至少 +1 小时且有新风险**。UART 方案零 RTL。

## 8. 最可能让今晚白干的 5 件事

1. **摄像头始终不出图**（任务1 第一条 + 视频 1/2/4 段全依赖）。预防：G1 先用厂商位流隔离硬件/设计；`[CAM]` 全程存档；设 1:40 的止损点。
2. **写通路又被折掉**（综合/布线全绿、零报错，图像永远进不了 DDR，`check_wr_path.ps1:3-8`）。预防：每次构建后必跑守卫，且 v2 构建完成后**再跑一次**。v2 不改 RTL，但 Efinity 综合有非确定性风险，不要想当然。
3. **v2 固件改坏**（比如串口 RX 轮询阻塞、状态机死循环）。预防：所有新逻辑**非阻塞**（只用 `uart_rx_ready()` 判断后再读）；保留 A 位流作为回退；v2 在上板前**用 `sw\run_rv32_tests.ps1` 的仿真跑一遍**（`sw\run_rv32_tests.ps1` 存在，我未核实它覆盖 `main.c`）。
4. **传感器 I2C 没上拉或接线错**（SHT30/MLX 两个都全 0，视频第 3 段没东西）。预防：G0 先量；两路 I2C 共总线，一路短路会拖垮另一路，故障时逐个拔。
5. **报警触发不稳**（挥手幅度不够、融合门槛高）。预防：§4 的数学已经算出 `area ≥ ≈1930`；v2 加 `+/-` 调阈值；录制前先在串口上看 `score` 与 `thr` 的余量。

附：**FTDI 蓝屏**（`0xFC`）也能让一晚归零，预防见 §1 第 5 条。
