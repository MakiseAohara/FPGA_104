## 0. 一句话

在**没有摄像头**的情况下，往 `frame_buffer`（`checker0`）的输入端注入一条**与 CSI 摄像头同构**的视频流（8 色彩条 + 移动方块，Bayer/RGGB 编码），从而把 **“DDR 写 → DDR 读 → 显示”** 这条链路与 **“摄像头”** 彻底解耦。仿真已证明：图案能驱动 `checker0` 产生正确的 AXI 写（地址全在 `[0x02000000, 0x02BDDE00)` 内）且读出侧有数据。

**开 / 关只写一个 APB 寄存器**（`0xC8`），上板**不用重编**；**复位默认 = 摄像头**，现有行为完全不变。

## 1. 怎么开（上板操作）

### 1.1 寄存器（APB，基址 `0xF8100000`）

| 偏移 | 读写 | 含义 |
|---|---|---|
| **`0xC8`** | W/R | `[0]` = `test_pattern_en`（**复位默认 0 = 摄像头**）；`[2:1]` = `mode`：`0`=8色彩条+移动方块，`1`=纯红场，`2`=纯绿场，`3`=纯蓝场 |
| `0xCC` | R | `LINES_PER_FRAME` — 一帧内 `hs` 上升沿个数（1080p 应 ≈1080） |
| `0xD0` | R | `PIXELS_PER_LINE` — 一行内 `de` 拍数（4 像素/拍、1920 宽应 ≈480） |
| `0xD4` | R | `VID_FRAME_CNT` — 上电以来 `vs` 个数（**判断“到底有没有在出帧”的第一手依据**） |

固件头 `sw\mmt_regs.h` 已加好：
```c
#define MMT_TEST_PATTERN    (MMT_BASE + 0xC8)
#define MMT_LINES_PER_FRAME (MMT_BASE + 0xCC)
#define MMT_PIXELS_PER_LINE (MMT_BASE + 0xD0)
#define MMT_VID_FRAME_CNT   (MMT_BASE + 0xD4)
MMT_TEST_PATTERN_SET(1, 0);   /* 开：彩条 + 移动方块 */
MMT_TEST_PATTERN_SET(1, 1);   /* 开：纯红场（判“红是红”）*/
MMT_TEST_PATTERN_SET(0, 0);   /* 关：切回摄像头（= 复位默认）*/
```

> ⚠️ **不要用 `0x80..0xC4`**：那是摄像头上游探针 `mmt_cam_probe` 的区间
> （`mmt_soc_regs.v:333-337` 的 `probe_sel` 覆盖 `probe_word` 32..49 ⇒ `0x80..0xC4`）。
> 本组寄存器从 `0xC8` 起，已确认在 RTL 与 `mmt_regs.h` 里都空闲。

### 1.2 上板步骤

```powershell
# 串口（115200）连上后，用调试口写寄存器（按你们现有调试方式），等价于：
#   write 0xF81000C8 = 0x00000001     # 开彩条
#   read  0xF8100000                  # 应为 0x4D4D5401（在位流活）
#   read  0xF810000C8                 # bit0=1 确认已切到图案
#   read  0xF81000CC / D0 / D4        # 行数 / 每行 de / vs 计数

#   write 0xF81000C8 = 0x00000000
```
**注意切换时机**：见 §2.3 的安全切换说明（图案与摄像头在同一个像素时钟域方案（方案 A）下，切换只是改多路选择，写寄存器即可；方案 B 才需要注意时钟 mux）。

## 2. 需要在 `rtl\mmt\mmt_top.v` 加的行（按锚点）

### 2.0 现状（锚点）

| 位置 | 内容 |
|---|---|

| `mmt_top.v:70` | `input wire vid_clk_dvi2,` |

| `mmt_top.v:706-728` | `checker0` 例化：`:710 .i_clk(i_mipi_rx_pclk)`、`:711 .i_vs(w_mipi_rx_vs)`、`:712 .i_de(w_mipi_rx_de & w_mipi_rx_hs)`、`:713 .vin({w_mipi_rx_data[39:32],w_mipi_rx_data[29:22],w_mipi_rx_data[19:12],w_mipi_rx_data[9:2]})` |

**关键事实**：`i_mipi_rx_pclk` 是 PLL 输出、**不是摄像头来的像素时钟** ⇒ “没摄像头时它不跳”这个担心**不成立**。因此有两种接法，见 §2.1 / §2.2。

### 2.1 方案 A（**推荐**）：图案跑在 `i_mipi_rx_pclk` 域 ⇒ **不需要时钟 mux**

既然 `i_mipi_rx_pclk` 一直在跳，最稳的做法是让图案也用它 —— 这样**不用动时钟**，只切 4 根数据/控制线，完全没有时钟毛刺风险。

在 `checker0` 例化**之前**插入：
```verilog
// ================= ★ task-23 / M0：测试图案注入 =================
wire        tp_en;                  // 来自 mmt_soc_regs 的 0xC8[0]
wire [1:0]  tp_mode;                // 来自 mmt_soc_regs 的 0xC8[2:1]
wire        tp_vs, tp_hs, tp_de;
wire [31:0] tp_vin;

mmt_test_pattern #(
    .H_ACTIVE(1920), .V_ACTIVE(1080),      // 与真实摄像头同构：480 de/行 × 1080 行
    .H_FRONT(120), .H_SYNC(2), .H_BACK(88),
    .V_FRONT(20),  .V_SYNC(2), .V_BACK(20),
    .PPC(4)
) u_test_pattern (
    .i_clk(i_mipi_rx_pclk), .i_rstn(vid_rst_n), .i_en(tp_en), .i_mode(tp_mode),
    .o_vs(tp_vs), .o_hs(tp_hs), .o_de(tp_de), .o_vin(tp_vin),
    .o_frame_cnt(), .o_line_cnt(), .o_pix_cnt(),
    // 测量输入 = 下面多路选择**之后**的线（见下）
    .i_vid_de(mipi_de_sel & mipi_hs_sel), .i_vid_hs(mipi_hs_sel), .i_vid_vs(mipi_vs_sel),
    .o_lines_per_frame(vid_lines_per_frame),
    .o_pixels_per_line(vid_pixels_per_line),
    .o_vid_frame_cnt  (vid_frame_cnt)
);

// 摄像头 / 图案 多路选择（**默认 tp_en=0 ⇒ 全部选摄像头，行为不变**）
wire        mipi_vs_sel = tp_en ? tp_vs : w_mipi_rx_vs;
wire        mipi_hs_sel = tp_en ? tp_hs : w_mipi_rx_hs;
wire        mipi_de_sel = tp_en ? tp_de : w_mipi_rx_de;
wire [31:0] mipi_vin_sel = tp_en ? tp_vin
                                 : {w_mipi_rx_data[39:32], w_mipi_rx_data[29:22],
                                    w_mipi_rx_data[19:12], w_mipi_rx_data[9:2]};
// ==============================================================
```
然后把 `checker0` 的四行改成（**只改这 4 行，`.i_clk` 不用改**）：
```verilog
/*i*/.i_clk			(i_mipi_rx_pclk      ),   // 不变：图案与摄像头同域
/*i*/.i_vs			(mipi_vs_sel	),
/*i*/.i_de			(mipi_de_sel & mipi_hs_sel	),
/*i*/.vin 			(mipi_vin_sel	),
```
并且需要新增 3 根往 `mmt_soc_regs` 的线（见 §3）：
```verilog
wire [15:0] vid_lines_per_frame, vid_pixels_per_line, vid_frame_cnt;
```
以及从 `mmt_soc_subsystem` 出来的 `tp_en` / `tp_mode`（见 §3）。

### 2.2 方案 B（Lead 提的“连带时钟一起切”）：图案跑在 `vid_clk_dvi2` 域

把 §2.1 里 `u_test_pattern` 的 `.i_clk(i_mipi_rx_pclk)` 改成 `.i_clk(vid_clk_dvi2)`，并**在 `checker0` 的 `.i_clk` 上加时钟 mux**：
```verilog
wire mipi_pclk_sel = tp_en ? vid_clk_dvi2 : i_mipi_rx_pclk;   // ⚠️ 组合 mux
/*i*/.i_clk (mipi_pclk_sel),
```
**风险与要求**：
- 组合时钟 mux 会产生**毛刺**。必须保证 `tp_en` **只在视频通路处于复位/空闲时改变**（例如固件先拉 `vid_rst_n` 再写 `0xC8`）。`u_test_pattern` 内部在 `i_en=0` 时把相位归零，所以切换后图案一定从帧首开始，不会出半帧。
- 若要彻底无毛刺，可用“每侧两级同步 + 与门”的标准无毛刺时钟 mux；但它需要**两个时钟都在跳**才能完成切换（切到一个停了的时钟会让输出停住 —— 那正是“摄像头不在”的期望现象，可以接受）。
```verilog
// 可选：无毛刺时钟 mux（需要两侧时钟都跳才能完成切换）
reg sa1, sa2, sb1, sb2;
always @(posedge vid_clk_dvi2  or negedge vid_rst_n) if(!vid_rst_n) {sa1,sa2} <= 2'b0; else {sa1,sa2} <= {sa2, ~sb2};
always @(posedge i_mipi_rx_pclk or negedge vid_rst_n) if(!vid_rst_n) {sb1,sb2} <= 2'b0; else {sb1,sb2} <= {sb2, sa2};
wire mipi_pclk_sel = (vid_clk_dvi2 & sa2) | (i_mipi_rx_pclk & sb2);
```

> **我的建议**：**用方案 A**。既然 `i_mipi_rx_pclk` 一直在跳（PLL 输出），方案 A 少一个时钟 mux、少一处毛刺风险、少改一行 `checker0`；而且图案与摄像头同域意味着**切换前后 checker0 看到的东西结构完全一致**，M0 的结论更能外推到摄像头模式。

### 2.3 切换安全性

- `tp_en` 复位默认 `0` ⇒ 上电位流跑的就是**摄像头**，与现在**逐位一致**（多路选择器全选摄像头支路）。
- 方案 A 下 `tp_en` 是纯数据多路选择，任何时刻写 `0xC8` 都安全；不过保险起见，建议**先停视频（拉复位）再切**，避免 `frame_info_det` 在切换瞬间看到一个长度异常的“帧”（它最多让 `frame_stable` 掉一下，下一帧恢复；不影响 DDR 数据正确性，因为 `frame_stable` 只是“够 3 帧才开始写”的门）。

## 3. 需要在 `rtl\mmt\soc\mmt_soc_subsystem.v` 加的行

`mmt_soc_regs` 已新增 **3 个只读输入 + 2 个输出**：

| 端口 | 方向 | 来源/去向 |
|---|---|---|
| `vid_lines_per_frame[15:0]` | in | `mmt_top` 的 `vid_lines_per_frame`（`u_test_pattern.o_lines_per_frame`）|
| `vid_pixels_per_line[15:0]` | in | 同上（`o_pixels_per_line`）|
| `vid_frame_cnt[15:0]` | in | 同上（`o_vid_frame_cnt`）|
| `test_pattern_en` | out | → `mmt_top` 的 `tp_en` |
| `test_pattern_mode[1:0]` | out | → `mmt_top` 的 `tp_mode` |

补法完全照 task-22 的 3 处接线（`mmt_soc_subsystem.v` 端口 L211 + 例化 L502、`mmt_top.v` L1671）同样的模式：**端口加在 `fb_awaddr` 之后 / `cam_probe_rdata` 之后，例化处按同名连接**。

**时钟域说明**：`vid_*_per_*` 是 `u_test_pattern` 在**像素域**数完后寄存下来的**准静态**值（每帧才变一次），跨到 `core_clk` 直接采样即可；如果要严格，可在 `mmt_soc_regs` 里加两级同步（不影响功能，只是消除亚稳态概率）。

**为什么计数放在像素域、不放在 `mmt_soc_regs`**：像素时钟 `i_mipi_rx_pclk` 是 PLL 输出、可能**快于** `core_clk`(100MHz)。在 `core_clk` 域采 `de` 电平会**漏掉窄脉冲**，`PIXELS_PER_LINE` 会偏小 —— 那就失去“判断摄像头模式对不对”的意义了。所以计数逻辑跟图案模块一起放在像素域，`mmt_soc_regs` 只做寄存器存储与 APB 读写。

## 7. 仿真抓到的 3 个真实问题（都已在 RTL 里修掉）

这三个都是**只有仿真才会暴露**的坑，记录在此避免以后重犯：

| # | 问题 | 现象 | 根因 / 修法 |
|---|---|---|---|
| 1 | `o_vin` 字节序与文件头约定相反 | T5 报“相位颠倒”：x=0 读到 0、x=1 读到 235 | 写成 `{p3,p2,p1,p0}`（p3 进了最高字节）⇒ 改成 `{p0,p1,p2,p3}`，`o_vin[31:24]` 才是本拍第 0 个像素 |
| 2 | **`de` 没有受垂直有效约束** | `frame_stable` 能起来，但 `fifo_wr_en` 恒 0、`AW` 恒 0 —— **和上板症状一模一样** | 只写了 `o_de <= h_active`，于是**垂直消隐期也在发 `de`**（每帧多 4×48=192 拍）。这会产生 `de=1 且 vs=0`，把 `frame_info_det` 的 `negtive_sync` 打成 0 ⇒ `w_frame_start` 永不产生 ⇒ `ser2par` 的 `pre_state` 卡在 0 ⇒ 打包器根本不启动。修法：`o_de <= h_active & v_active` |
| 3 | 测量放在 `core_clk` 域会漏脉冲 | （设计推演，未实测） | 像素时钟可能快于 `core_clk`，`PIXELS_PER_LINE` 会偏小 ⇒ 计数逻辑放进像素域的 `mmt_test_pattern`，`soc_regs` 只做寄存器 |

> ⚠️ **问题 2 值得单独留意**：它说明 “`AW` 恒 0” 可以由**纯粹的视频时序形状错误**造成，而不需要摄像头坏。
> 反过来说，上板若见到 `AW=0`，除了“摄像头没数据”，还要查 **`i_de` 的形态**（有没有在消隐期乱发 `de`、
> `de & hs` 是不是恒 0）。`0xCC/0xD0/0xD4` 三个寄存器正是为此准备的。

按**从上到下的顺序**查（每一行都给了能一眼看出的寄存器判据）：

| 序 | 怀疑对象 | 怎么判（看哪个寄存器 / 信号） | 结论 |
|---|---|---|---|
| 1 | 位流没起来 / 不是这一版 | `0x00` 应 = `0x4D4D5401` | ≠ ⇒ 位流/复位问题，别往下查 |
| 2 | **到底有没有在出帧** | `0xD4 VID_FRAME_CNT` 是否在涨 | **不涨 ⇒ 根本没有 vs**，问题在最上游（摄像头没出图 / 图案没在跑 / 探针接线） |
| 3 | 出帧了但没有有效像素 | `0xD0 PIXELS_PER_LINE` = 0 或远小于 480 | =0 ⇒ `de` 没来；查 `de` 是否被 `vs`/消隐影响（见 §7 问题 2） |
| 4 | 行数不对 | `0xCC LINES_PER_FRAME` ≠ 1080 | 偏小 ⇒ 摄像头模式/时序不对（如 720p、隔行、lane 数不对） |
| 5 | 上游到了帧缓冲却是 0 | `0x74` 的 `fb_awvalid/fb_wvalid` 电平与 `fb_aw_seen/fb_w_seen` | 电平=1 但 seen=0 ⇒ 握手对端没响应；全 0 ⇒ 帧缓冲没启动（看 6） |
| 6 | 帧缓冲没启动（`AW=0`）| `0x6C/0x70` AW/W 计数 | 结合 `0xD4`：`0xD4` 在涨但 `AW=0` ⇒ **时序形状问题**（最可能是 `frame_stable` 起不来或 `de` 形态错） |
| 7 | 写了但地址越界 | `0xA8 MMT_FB_AWADDR_MAX` + `0xAC` 采样状态 | 必须**联合**读：`0xA8<0x02BDDE00` 且采样数 >0 才算“没越界” |
| 8 | 写了但没显示 | 切 `0xC8 mode=1/2/3` 纯色场 | 纯色场也不显示 ⇒ 问题在**读出→debayer→HDMI**，与写无关 |
| 9 | 有画面但**红蓝反了** | 彩条模式下红条应显红、蓝条应显蓝 | 反了 ⇒ debayer R/B 通道（参考 `docs\去马赛克Bayer相位分析.md`） |
| 10 | 有画面但**水平错一像素 / 颜色乱** | 彩条边界是否整齐 | 错位 ⇒ `o_vin` 4 个字节的先后顺序（§7 问题 1，改一行即可） |

**最有用的一条**：**`0xD4` 不涨 ⇒ 别怀疑 DDR、别怀疑 debayer，问题在最上游**；`0xD4` 在涨但 `AW=0` ⇒ 问题在**帧缓冲的输入形态**，不是“没数据”。

## 9. 未验证 / 限制

1. **未跑 Efinity**：资源占用、时序收敛、布线都要 Lead 重编后确认。本模块是纯组合比较 + 计数器，预期几十 LUT、0 BRAM、0 DSP。
2. **上板现象未验证**：彩条顺序、方块移动、三个纯色场、以及“红是红蓝是蓝”都只是仿真 + 代码推断，需上板确认。
3. **`o_vin` 字节序**：按 `mmt_top.v:713` 的拼接顺序（lane0 占最高字节）取“最高字节 = 本拍第 0 个像素”。若上板发现颜色水平错位，把 `o_vin <= {p0,p1,p2,p3}` 改成 `{p3,p2,p1,p0}` 即可（§7 问题 1 就是反过来的情形，改一行）。
4. **Bayer 相位**假设 RGGB（依据 `docs\去马赛克Bayer相位分析.md` 的实测）。若实际是 BGGR/GRBG，画面颜色会整体错，需要调整 `px_val` 里的相位判断。
5. **图案几何默认 1920×1080**（与真实摄像头同构）。仿真用小尺寸（192×32）跑，只验证了**结构**正确；上板若要更快出图可把参数改小，但那时 `LINES_PER_FRAME/PIXELS_PER_LINE` 的期望值也随之改变。
6. **`i_mipi_rx_pclk` 的频率**未确认（只确认它是 PLL 输出、一直在跳）。若它的频率与 `core_clk` 关系导致 `u_test_pattern` 的 `wait` 逻辑有额外约束，需要上板确认——但本模块没有任何跨域逻辑，只有单域计数。
