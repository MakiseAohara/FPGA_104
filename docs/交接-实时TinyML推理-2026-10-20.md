# 交接：实时 TinyML 推理已在板上跑通（2026-10-20）

本文是接手本工程所需的全部信息：现状、可复现步骤、内存与寄存器约定、帧格式实测结论、踩过的坑、以及未完成项。

---

## 1. 一句话现状

**MIPI 摄像头 + SapphireSoC（RISC-V）+ TinyML 加速器跑在同一份位流里**，
SoC 从 DDR 帧缓冲取实时画面、降采样成 96×96 INT8、交给硬件加速器推理，
结果经 UART 输出。

> **可用位流：`p2d_ci.bit`**（SHA256 `04946BC2…C1D3E3`）。
> 带 OSD 红框的 `p4_osd.bit` 有显示回归，见 §14，不要用于演示。

实测判决稳定性：无人区段 3% 误报，有人区段 93% 检出，最长连续 34 帧无抖动。

## 3. 设计结构

```
MIPI 摄像头 ──► csi_rx ──► debayer ──► frame_buffer ──► DDR3 @0x01000000
                                            │                 │
                                            │            ┌────┴─────┐
                                            │            │ DDR3 控制器 │
                                            │            └────┬─────┘
                                            │                 │
                                     ┌──────┴─────────────────┴──────┐
                                     │  mmt_axi_bridge3（3 主口仲裁）  │
                                     │  lane0: 帧缓冲                │
                                     │  lane1: SapphireSoC           │
                                     │  lane2: TinyML 加速器         │
                                     └───┬───────────┬───────────┬───┘
                                         │           │           │
                                    帧缓冲读写    SoC(DDR+APB)  加速器(AXI)
                                                     │           │
                                                     └─CI 指令───┘
                                                     │
                                                  UART / OSD
```

**为什么自研桥而不是用 `efx_axi_interconnect`**：
3 主口互联会触发 Efinity 的 `infer-clk-enable` 折叠 bug（写通路 FSM 被折成常量，
见 `docs/2026-10-18-ice0实测-写通路已救回.md`）。手写的单笔仲裁桥绕开了它。

## 4. 内存映射（板上验证过）

| 区域 | 地址 | 说明 |
|---|---|---|
| SoC 固件 | `0x00001000` 起 | 由片上 UART loader 灌入 |
| 模型权重 | `0x00100000` 起 | |
| **帧缓冲** | **`0x01000000` 起，3 个 bank** | 每 bank `960×1080×4 + 0x200` 字节 |
| CPU DDR 窗口 | `0x1000 – 0xE0001000` | CPU 可直接读帧缓冲 |

**注意**：`0x0 – 0xFFF` 是 SoC 的**解码空洞**，任何访问都会总线错误并挂死 CPU。
指针扫描必须从 `0x00100000` 起。

## 5. 帧缓冲格式（实测结论，血泪）

| 项 | 值 | 依据 |
|---|---|---|
| 每像素 | **4 字节** | `FRAME_LEN/1080 = 3840 = 960×4`；帧搜索器四通道统计 |
| 32 位字内容 | **一个 16 位像素复制到高低两半** | 统计显示 `lane0≈lane2`、`lane1≈lane3` |
| 行步长 | 3840 字节 | |
| **亮度通道** | **byte0（bits[7:0]）** | 该通道方差最大；A/B 实验排除 RGB565 |
| 活跃 bank | `bank2`（读校验和变化确定） | |

### 5.1 下采样的关键：必须用区块平均

**点采样会毁掉分类**。960×1080 → 96×96 若每 10×11 取一个点，
每 11 行才取 1 行，人的竖直结构被切碎，模型输出在阈值附近乱跳。

改成**区块内 5×5 共 25 点求均值**后立即稳定（34 帧连续 PERSON）。
而且**更快**（420 ms vs 435 ms）。

### 5.2 已排除的错误假设（不要重复走）

| 假设 | 否掉的方式 |
|---|---|
| YUV422、每字 2 像素 | 四通道统计一致 ⇒ 不是通道结构问题 |
| RGB565 | A/B 双推理：RGB565 变体恒输出 −105（退化） |
| 亮度是 byte1 | 帧搜索器显示 byte0 方差更大 |
| 视频没写 `0x01000000` | 帧搜索器在该地址扫到图像结构 |
| 点采样够用 | 改区块平均后立刻稳定 |

## 6. APB 寄存器表（SoC 侧，基址 `0xF8100000`）

| 偏移 | 寄存器 | 读/写 |
|---|---|---|
| `0x00` | `cal_done` | R |
| `0x04` | SoC 侧 AW 计数 | R |
| `0x08` | SoC 侧 AR 计数 | R |
| `0x0C` | `{init_state, bridge_state}` | R |
| `0x10` | 加速器 AW 计数 | R |
| `0x14` | 加速器 AR 计数 | R |
| **`0x18`** | **CI 指令计数** | R |
| `0x1C` | 中断计数 | R |
| `0x20` | `soc_system_reset` 快照 | R |
| **`0x24`** | **OSD 红框使能（bit0）** | **W** ⚠️ 见 §14 |

> **坑**：`0x18` 的 CI 计数器一度没实现，导致固件读到 0、误判"加速器没工作"。
> 验收判据依赖的观测寄存器必须逐个核对语义。

> ⚠️ **`0x24` 写寄存器只在 `p4_osd.bit` 里存在，而那个位流有显示回归，不要用。**
> 当前验证过的位流是 `p2d_ci.bit`（无 OSD 告警通路）。详见 §14。

## 8. 上板与运行

**顺序很重要**：先起加载器（它在等启动标志），再烧位流触发复位。

```powershell
# 1) 起加载器（阻塞等待 MMT_BOOT）
D:\Efinity\2026.1\python311\bin\python.exe <work>\ai-onboard-20261020\load_and_run.py ^
  --port COM15 --image D:\FPGA\codex20\fw_v9_out\tinyml_pdti8.bin ^
  --out <capture_dir> --boot-timeout 45 --run-timeout 110

# 2) 另开一个窗口：烧位流
powershell -File outputs\fpga_onboard_verified_20261020\tools\flash_vendor.ps1 ^
  -Bit <project>\out\p4_osd.bit -Sha256 <sha256> -EfinityHome D:\Efinity\2026.1 ^
  -ExpectedDriverVersion 2.12.36.20 -UsbUrl "hiftdi://0x0403:0x6011/1" -LogRoot <log_dir>
```

## 14. ⚠️ 已知回归：OSD 告警叠加会让画面出现条纹

### 现象

烧了 `p4_osd.bit`（在 `p2d_ci.bit` 基础上加了"APB 写 → 同步 → OSD alarm"通路）后，
画面出现**若干条竖线分隔**和左侧**紫色条纹**，且在镜头前活动几下后更容易出现。

### 二分定位（已做）

| 组合 | 结果 |
|---|---|
| `p4_osd.bit` + v9 固件 | ❌ 有条纹 |
| **`p2d_ci.bit` + v9 固件（同一份固件）** | ✅ **条纹消失** |

⇒ **不是固件读帧缓冲的带宽竞争**，是 `p4_osd.bit` 的 RTL 改动引入的。

### 已找到的时序证据

新增 CDC 路径被当作同步路径分析并**违规**：

```
Path Begin    : osd_alarm_core~FF|CLK
Path End      : osd_alarm_v1~FF|D
Launch Clock  : core_clk (RISE, 10 ns)
Capture Clock : hdmi_tx_slow_clk (RISE, 6.734 ns)
Slack         : -0.663 (required time - arrival time)
Constraint    : 0.002 ns      ← 被当成同步路径
```

全设计**只有这一条负 slack**，其余全为正。

### 修复方向（未验证）

1. **给 SDC 加假路径**（首选）：
   ```tcl
   set_false_path -from [get_clocks core_clk] -to [get_clocks hdmi_tx_slow_clk]
   ```
   或更精确地用 `set_clock_groups -asynchronous`。这是 CDC，本来就不该按同步约束。
2. 加约束后重新 PnR 并**重新目视验证画面** —— 时序违规消失不代表条纹一定消失，
   还需要排除"PnR 为了这条路径牺牲了视频布线"的可能。
3. 若仍复现，退一步用**纯视频域的自计时闪烁**（原来的 `frame_count[7]` 方案）
   配合 APB 只做"使能门控"，避免跨域信号进入 OSD 组合逻辑。

### 当前建议

**用 `p2d_ci.bit`**（`_p2a/v7_camera_ai/out/p2d_ci.bit`，SHA256
`04946BC2AE0EA1A4C9BF2F40A95BFCA07B621F27A46C55CC580709FBC2C1D3E3`）。
它没有 OSD 告警通路，但推理、UART、DDR、显示全部正常。

`p4_osd.bit` 请当作**实验产物，不要上板演示**。
