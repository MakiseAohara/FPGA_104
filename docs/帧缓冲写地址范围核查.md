## 0. 结论先行

> **写地址会越界。** 用接近真实的帧长（1920×1080 ÷ 4 像素/时钟 = **518,400 个 `de` 拍/帧**）实测，最大写地址 = **`0x031CC7FF`**，比约定的视频区上界 **`0x02BDDE00` 超出 ≈ 5.93 MB**（0x5EEA00）。**根因不是地址跑飞，而是 3 个 bank 的基址算错了**：`bank_switch` 收到的 `MAX_VID_WIDTH/HIGHT` 是 `ddr_buffer` 的**默认值 1920×1080**，而工程约定按 960×1080 规划，于是 `FRAME_LEN` 大了整整一倍。

> ⚠️ **状态（2026-10-13 第二轮）**：本根因**已被 Lead 修复**（`rtl\frame_buffer\frame_buffer.v:194-196` 补上三行参数转发）。**§2–§5 是修复前的取证**（保留以说明证据链），**§10 是修复后的复核**：bank 基址已回到 960 版、真实帧长下 `AW beyond region = 0`，**越界已消除**。以 §10 为当前状态。

## 2. 关键发现：`FRAME_LEN` 被算成了 1920 版

### 2.1 参数没有传下去

`rtl\frame_buffer\frame_buffer.v:181-189`：
```verilog
ddr_buffer #(
.AXI_DATA_WIDTH ( AXI_DATA_WIDTH	),
.AXI_ADDR_WIDTH ( AXI_ADDR_WIDTH	),
.WR_FIFO_DEPTH	( WR_FIFO_DEPTH		),
.RD_FIFO_DEPTH 	( RD_FIFO_DEPTH 	),
.START_ADDR		( START_ADDR      ),
.I_VID_WIDTH    ( I_VID_WIDTH     ),
.BURST_LEN      (BURST_LEN        )
)u_ddr_buffer(
```
**没有 `.FB_NUM` / `.MAX_VID_WIDTH` / `.MAX_VID_HIGHT`。**

`rtl\frame_buffer\ddr_buffer.v:8-10` 的默认值：
```verilog
parameter FB_NUM			= 	3,
parameter MAX_VID_WIDTH		=	1920 ,
parameter MAX_VID_HIGHT		=	1080 ,
```
`ddr_buffer.v:220-227` 把这几个原样转给 `bank_switch`：
```verilog
bank_switch #(
		.FB_NUM ( FB_NUM), .MAX_VID_WIDTH ( MAX_VID_WIDTH),
		.MAX_VID_HIGHT ( MAX_VID_HIGHT), .START_ADDR ( START_ADDR ),
		.VID_DATA_WIDTH (I_VID_WIDTH), .AXI_DATA_WIDTH (AXI_DATA_WIDTH )
) u_bank_sw
```
⇒ `bank_switch` 实际拿到 `MAX_VID_WIDTH=1920, MAX_VID_HIGHT=1080, VID_DATA_WIDTH=32`。

### 2.2 于是 FRAME_LEN 翻倍

`rtl\frame_buffer\bank_switch.v:32`：
```verilog
localparam FRAME_LEN = MAX_VID_WIDTH*MAX_VID_HIGHT*VID_DATA_WIDTH/8 + 32'h200;
localparam FRAME_1ST_START_ADDR = START_ADDR;
localparam FRAME_2ND_START_ADDR = FRAME_LEN + START_ADDR ;
localparam FRAME_3RD_START_ADDR = FRAME_LEN + FRAME_2ND_START_ADDR;
```

| | 工程约定（960×1080） | RTL 实际（1920×1080） |
|---|---|---|
| `FRAME_LEN` | `0x3F4A00` (4,147,712) | **`0x7E9200` (8,294,912)** |
| bank0 | `0x02000000` | `0x02000000` |
| bank1 | `0x023F4A00` | **`0x027E9200`** |
| bank2 | `0x027E9400` | **`0x02FD2400`** |
| 3 bank 上界 | `0x02BDDE00` | **`0x037BB600`** |

### 2.3 仿真观测值与 1920-based 公式逐位吻合

短帧场景（`H_ACTIVE=128, V_ACTIVE=16`）实测：
```
[RELOAD 1] t=66985  ddr_wr_addr <= start_addr_r = 0x02000000  (wr_start=0x02000000 wr_bank=00)
[RELOAD 2] t=89585  ddr_wr_addr <= start_addr_r = 0x02fd2400  (wr_start=0x02fd2400 wr_bank=10)
[SW-RD]    t=93275  rd bank switch -> rd_bank=01 rd_start_addr=0x027e9200
[RELOAD 3] t=111865 ddr_wr_addr <= start_addr_r = 0x027e9200  (wr_start=0x027e9200 wr_bank=01)
```
- 观测到的 `wr_start_addr` = `0x02fd2400` = `START_ADDR + 2×0x7E9200` ✓ **= bank2（1920-based）**
- 观测到的 `rd_start_addr` = `0x027e9200` = `START_ADDR + 1×0x7E9200` ✓ **= bank1（1920-based）**

两个都**只**能用 1920-based 的 `FRAME_LEN` 解释（960-based 会给出 `0x027E9400` / `0x02FD2800`，与观测不符）。**这条证据链已经足够定案。**

**⇒ 这个发现同时修正了工程文档**：`docs\DDR固件与模型放置方案.md:328,343`（"3 bank 到 `0x02BDDDFF`"）与 `docs\DDR执行路径决策.md:53`（"占 `0x02000000`–`0x02BDDDFF`"）**都不成立**；该文档 §8 的 `U5` 项自己就标注了"本轮未逐位复核 RTL 例化计算"——本轮复核的结论是**它错了**。

## 3. Q1：地址推进公式（逐条给 `文件:行`，并与实测数值对照）

1. **帧内**：每笔 AW 握手后地址前进 `(awlen+1) × 16` 字节
   - `ddr_wr_buffer.v:262` `assign nx_ddr_wr_addr = ddr_wr_addr + {(ddr_awlen+9'd1),{WR_ADDR_SHIFT_BITS{1'b0}}};`（`WR_ADDR_SHIFT_BITS = clogb2(16) = 4`）
   - `ddr_wr_buffer.v:278-283` `addr_add_en <= awvalid & awready;`
   - `ddr_wr_buffer.v:255-261` 仅在 `addr_add_en` 时更新
2. **一帧总推进量** = `ddr_frame_len × 16` 字节 = **`frame_cnt × 4` 字节**（即一帧的真实字节数）
   - `frame_info_det.v:113-115` `total_frame_bytes = frame_cnt * VID_DATA_BYTE`（`VID_DATA_BYTE = I_VID_WIDTH/8 = 4`）
   - `frame_info_det.v:120-122` `ddr_frame_len <= total_frame_bytes[31:4] + |total_frame_bytes[3:0];`（= 向上取整到 128-bit 字）
   - 实测核对：`V_ACTIVE=1920,H_ACTIVE=34` ⇒ `frame_cnt=65280` ⇒ 每帧推进 `65280×4 = 261,120 = 0x3FC00` 字节；实测 FRAME 1 地址 `0x02000000 .. 0x0203f800`（末突发 2048 字节 ⇒ 覆盖到 `0x0203FFFF` = `0x02000000 + 0x3FC00 − 1`）✓ **逐字节吻合**
3. **帧边界重载**：`sync_r2` 时 `ddr_wr_addr <= start_addr_r`
   - `ddr_wr_buffer.v:408` `else if( sync_r0 ) … state <= 'd0;`、`ddr_wr_buffer.v:415-416` `state 0 → 1 on sync_r2`
   - `ddr_wr_buffer.v:255-261` `else if(sync_r2) ddr_wr_addr <= start_addr_r;`
   - `ddr_wr_buffer.v:142-151` `start_addr_r <= pos_sync ? start_addr : start_addr_r;`，`start_addr` 来自 `bank_switch.wr_start_addr`（`ddr_buffer.v:129,241`）
   - `sync_r2` 由 `wr_start = frame_start & frame_stable`（`frame_buffer.v:196`）经 `pos_sync → sync_r0..r3` 得到（`ddr_wr_buffer.v:119-140`）
4. **bank 轮转**：`burst_last` → `wr_sw`
   - `ddr_wr_buffer.v:306-313` `burst_last <= (burst_add_en && burst_num == total_burst_num+2)`；`assign bank_sw = burst_last;`
   - `bank_switch.v:106-118` `pos_wr_sw_en / pos_rd_sw_en`；`bank_switch.v:131-156` dirt/clean 三 bank 轮转，在 `pos_wr_sw_en` 且 `dirt_en` 时更新 `wr_bank / wr_start_addr`
   - ⚠️ **注意**：`ddr_buffer.v:233-239` 把 `wr_sw/rd_sw` 与 `wr_sw_ack/rd_sw_ack` 都接上了，所以 **`bank_sw_ack` 不是问题**（task-21 问的三种可能里，这个可以排除）
5. **约束参数**：`BURST_LEN=127` 决定单突发 ≤ 2048 字节；`ddr_frame_len` 决定一帧突发数（`burst_num`，`ddr_wr_buffer.v:203-208`，`BURST_LEN==127` 分支）

## 4. Q2 / Q3：真实帧长实测 —— 越界，且会盖掉张量区

### 4.1 场景与原始输出（实测）

运行（`H_ACTIVE=1920, V_ACTIVE=270` ⇒ `de` 拍/帧 = **518,400**，等价 1920×1080 ÷ 4 像素/时钟；`N_FRAMES=6`）：

```
 frame geometry: 270 lines x 1920 pixels(de cycles) = 518400 de/frame
 documented region: [0x02000000 , 0x02bdde00)
 actual 3-bank span:[0x02000000 , 0x037bb600)
[RELOAD 1] t=15626125 ns sync_r2 -> ddr_wr_addr <= start_addr_r = 0x02000000 (wr_start=0x02000000 wr_bank=00)
[FRAME 1] AW=1013  addr range 0x02000000 .. 0x021fa000  (first 0x02000000 last 0x021fa000)
[RELOAD 2] t=20835105 ns sync_r2 -> ddr_wr_addr <= start_addr_r = 0x02fd2400 (wr_start=0x02fd2400 wr_bank=10)
[FRAME 2] AW=1013  addr range 0x02fd2400 .. 0x031cc000  (first 0x02fd2400 last 0x031cc000)
[RELOAD 3] t=26043765 ns sync_r2 -> ddr_wr_addr <= start_addr_r = 0x02fd2400 (wr_start=0x02fd2400 wr_bank=10)
AW handshakes        = 3039   W beats = 388688   wlast = 3037   B = 3037
address range        = 0x02000000 .. 0x031cc000
documented region    = [0x02000000 , 0x02bdde00)
actual 3-bank span   = [0x02000000 , 0x037bb600)
bytes of the 3rd bank BEYOND the documented region: 0x6218240 (5 MB)
AW beyond REGION_HI  = 2026
first breach         = 0x02fd2400  (REGION_HI + 0x4146688)
=== ADDRESS RANGE: OVERFLOW DETECTED (2026 AW beyond region) ===
```

- 每帧 `AW=1013` ≈ `ddr_frame_len/128 = 129,600/128 = 1012.5` ✓
- 每帧地址推进 `0x021FA800 − 0x02000000 = 0x1FA800`（末突发覆盖到 `0x021FA7FF`）≈ `518,400×4 = 0x1FA400` ✓ **与公式一致**
- **最大写地址 `0x031CC7FF`**（末突发起始 `0x031cc000` + 2047）
- 超出 `0x02BDDE00` **`0x5EEA00` = 6,220,288 字节 ≈ 5.93 MB**
- **2026 笔 AW**（正好两帧的量）落在约定区之外

### 4.2 会盖掉什么（**这是最要紧的一条**）

按工程自己的 DDR 规划 `docs\DDR固件与模型放置方案.md:343-345`：

| 区 | 起 | 止 | 大小 | 归属 |
|---|---|---|---|---|
| R5 视频帧缓存 | `0x02000000` | `0x02BDDDFF` | ≈11.9MB | `frame_buffer` AXI 主口 |
| R6 帧缓存余量 | `0x02BE0000` | `0x02FFFFFF` | 128KB | 对齐/保险 |
| **R7 张量/激活区** | **`0x03000000`** | **`0x03FFFFFF`** | **16MB** | **TinyML 输入/输出/中间张量**（`DDR执行路径决策.md:321` `mmt_tensor_base=0x03000000`） |

而 `frame_buffer` 的 bank2 实际写 **[`0x02FD2400`, `0x031CC800`)**：

```
       0x02BDDE00              0x03000000                     0x031CC800
R5 尾 ────┘                        │                              │
           R6/R7 之间的空隙          │◄──── bank2 覆盖这一段 ────►│
                                    └────── R7 张量区前 1.8 MB ───┘
重叠 = 0x031CC800 − 0x03000000 = 0x1CC800 = 1,886,208 字节 ≈ 1.80 MB
```

⇒ **只要写 bank2，就会把 R7 张量/激活区的前 1.80 MB 覆盖掉。** TinyML 的输入/输出/中间张量正放在那里，**加速器跑起来必然读到被视频像素踩过的数据**。

> 补充：哪怕用我 task-21 的中间尺度场景（`de` 拍/帧 = 65,280，约真实帧的 1/8），bank2 也已经写到 `0x03011FFF`，盖掉张量区前 **72 KB**。也就是说**只要相机出图，这个问题立刻发生**，不需要等很久。

### 4.3 三种"可能根因"的排查结论

| 候选 | 结论 |
|---|---|
| `bank_sw_ack` 没接？ | **排除**。`ddr_buffer.v:233-239` 已把 `wr_sw/rd_sw` 与 `wr_sw_ack/rd_sw_ack` 都接上；仿真里 `[SW-WR]`/`[SW-RD]` 事件正常产生，bank 确实在轮转 |
| `frame_len` 计算错？ | **✅ 这是根因**（不是公式错，而是**公式的输入参数**没传对——`frame_buffer.v:181-189` 漏传 `MAX_VID_WIDTH/HIGHT`，落回 `ddr_buffer.v:9-10` 的 1920×1080 默认值） |
| `burst_add_en` 有问题？ | **排除**。`burst_add_en = wlast & wvalid & wready`（`ddr_wr_buffer.v:481`）按预期每突发末拍脉冲；`burst_num / total_burst_num / burst_last` 的计数与实测逐帧一致（每帧 1013 突发、末突发触发 bank 切换） |

**⇒ 最小复现**：`sim\frame_wr\run_frame_addr.ps1` 的 `MID`（65,280 de/帧，55 秒）或 `REAL`（518,400 de/帧）场景，看 `[FRAME n]` 行里出现 `0x02fd2400` 起、`0x030...` 止的地址段即可。

## 5. 修法（按代价排序）

### P0 —— 根因修法：补 3 行参数转发（**推荐**）

`rtl\frame_buffer\frame_buffer.v:181-189`，`ddr_buffer` 例化里加上：
```verilog
ddr_buffer #(
.AXI_DATA_WIDTH ( AXI_DATA_WIDTH	),
.AXI_ADDR_WIDTH ( AXI_ADDR_WIDTH	),
.WR_FIFO_DEPTH	( WR_FIFO_DEPTH		),
.RD_FIFO_DEPTH 	( RD_FIFO_DEPTH 	),
.START_ADDR		( START_ADDR      ),
.I_VID_WIDTH    ( I_VID_WIDTH     ),
.BURST_LEN      (BURST_LEN        ),
.FB_NUM         ( FB_NUM          ),   // +
.MAX_VID_WIDTH  ( MAX_VID_WIDTH   ),   // +  960，与工程约定一致
.MAX_VID_HIGHT  ( MAX_VID_HIGHT   )    // +  1080
)u_ddr_buffer(
```
- **预期**：`FRAME_LEN = 960×1080×32/8 + 0x200 = 0x3F4A00`；bank 基址 = `0x02000000 / 0x023F4A00 / 0x027E9400`；真实帧下最大写地址 = `0x027E9400 + 0x1FA400 − 1 = 0x029E37FF` < `0x02BDDE00` ✓ **完全落回 R5 区**（R5 有 11.9 MB，3×2.07 MB = 6.2 MB，余量充足）
- **风险**：低。`FRAME_LEN` 变小 ⇒ bank 间距变小，但仍远大于一帧真实数据（4.15 MB vs 2.07 MB）；`FB_NUM` 传 3 与默认相同，等于不变。**唯一需要注意**：`MAX_VID_WIDTH/MAX_VID_HIGHT` 必须 ≥ 真实分辨率，否则 bank 会互相压。本工程 960×1080 正好对应"输入 4 像素/时钟 → 输出 960 宽"，是设计本意。
- **判据**：重跑 `tb_frame_addr.v`（REAL 场景），`[RELOAD n]` 行应出现 `0x023f4a00` / `0x027e9400`，`byte of the 3rd bank BEYOND the documented region` 应为 0，`AW beyond REGION_HI` 应为 **0**。

### P1 —— 若不想动 vendor RTL：把 R7 张量区往后挪（**不推荐**）

把 `mmt_tensor_base` 从 `0x03000000` 挪到 `0x03800000` 以上（要盖过 RTL 真实的 3 bank 上界 `0x037BB600`）。
- 代价：DDR 规划、`sw\ddr\link_ddr.ld`、TinyML 侧地址全部要改；而且 bank1 的 `0x027E9200` 也已越过 R5 尾（`0x02BDDE00` 之内，但把 R6 余量吃掉了）。**治标不治本，且更容易再错。**

### P2 —— 附带：`MAX_VID_WIDTH` 的真实语义要对齐

`frame_buffer` 传给 `bank_switch` 的 `VID_DATA_WIDTH` 是 `I_VID_WIDTH=32`，而 `FRAME_LEN` 的算式用的是 `MAX_VID_WIDTH×MAX_VID_HIGHT×VID_DATA_WIDTH/8`。若 `MAX_VID_WIDTH` 取 960（输出像素数）而 `VID_DATA_WIDTH` 取 32（输入每拍的位宽），量纲其实不统一（960×1080×4 = 4.15 MB，是实际帧数据 2.07 MB 的两倍）。**它偏大 2 倍是"安全"方向**，所以 P0 改完没问题；但建议在注释里写清这个"余量来自量纲不统一"，免得后人再算错。

```powershell
# 1) 生成 shim 副本（rtl\ 只读）
```

## 8. 限制 / 未证实

1. **合成帧仍不是完整 1080p 行结构**：`de` 拍/帧取了 518,400（= 1920×1080÷4，与真实一致），但行数取 270（每行 1920 拍）而非 1080 行 × 480 拍。**地址推进只取决于 `de` 总拍数**（§3 已实测吻合），行结构不影响 bank 基址与每帧推进量；但 `frame_cnt_end` 的边界行为在真实 1080 行下仍可能有细微差别（未验证）。
2. **未测 SoC/TinyML 同时访问 DDR 的竞争**：本仿真只有帧缓冲一个主口在跑。
3. **未在硬件上确认** `frame_buffer` 实际的 bank 基址：结论全部基于 RTL 仿真 + 参数展开计算。上板可用 `frame_info` 寄存器或 AXI 互联侧抓 AW 地址交叉验证。
4. **`MAX_VID_WIDTH=960` 是否为设计本意**：从 `mmt_top.v` 的 `frame_buffer` 例化（`.MAX_VID_WIDTH(960)`）看是；但 RTL 里它没生效（因为没往下传）。P0 修法会让它生效——这是"修好"还是"改变行为"取决于当初意图，**建议 Lead 确认一句**（我倾向：原本就是想传 960，漏传了）。

### 10.3 为什么轮转是 `00 → 10 → 10 → 10 → 01`（不是干净 0/1/2）

**实测状态机 trace（MID，修复后）**：
```
[SW-WR] #1 wr_bank=00 wr_start_addr=0x02000000 | dirt_en=1 dirt_bank=10 clean_en=0 clean_bank=00 | rd_bank=01 wr_sw=1 rd_sw=0
[SW-WR] #2 wr_bank=10 wr_start_addr=0x027e9400 | dirt_en=0 dirt_bank=10 clean_en=1 clean_bank=00 | rd_bank=01 wr_sw=1 rd_sw=0
[SW-WR] #3 wr_bank=10 wr_start_addr=0x027e9400 | dirt_en=0 dirt_bank=10 clean_en=1 clean_bank=00 | rd_bank=01 wr_sw=1 rd_sw=0
[SW-RD] #1 rd_bank=01 rd_start_addr=0x023f4a00 | dirt_en=0 dirt_bank=10 clean_en=1 clean_bank=00 | wr_bank=10
[SW-WR] #4 wr_bank=10 wr_start_addr=0x027e9400 | dirt_en=1 dirt_bank=01 clean_en=0 clean_bank=00 | rd_bank=00 wr_sw=1 rd_sw=1
[SW-WR] #5 wr_bank=01 wr_start_addr=0x023f4a00 | dirt_en=0 dirt_bank=01 clean_en=1 clean_bank=10 | rd_bank=00 wr_sw=1 rd_sw=1
bank switch events   : wr=5  rd=1
```

**机制**（`rtl\frame_buffer\bank_switch.v:131-156`，`FB_NUM==3` 的 dirt/clean 三 bank 轮转）：
- 写侧开关只有 `dirt_en == 1` 时才**真正换 bank**（取 `dirt_bank` 并清 `dirt_en`）；`dirt_en == 0` 时走 `else` 分支，`wr_bank`/`wr_start_addr` **原地不动**。
- `dirt_en` **只会被"配对的读侧开关"重新置 1**（`:144-156`，`if (clean_en) … dirt_bank <= rd_bank; dirt_en <= 1'b1;`）。
- 所以：**读侧不换 bank，写侧的 bank 就冻结。** 本次激励 `wr=5, rd=1`，于是写 bank 只推进了两次（`10` 然后 `01`），中间三帧冻结 → 正好是 `00 → 10 → 10 → 10 → 01`。

**这不是地址危害（关键）**：bank 冻结时，每帧的 `sync_r2` 仍把地址重载到**同一个基址**，所以 `[FRAME 2]/[FRAME 3]/[FRAME 4]` 的地址区间**完全相同**（`0x027e9400 .. 0x02828800`）——是"原地重写同一个 bank"，**不会累积、不会跑飞**。这也再次印证了 §4 的结论：越界**只**来自 bank 基址算错，不来自地址累积。

**为什么本仿真会 `wr >> rd`（推断 + 可验证）**：TB 的相机侧用 100 MHz 跑小帧（几毫秒一帧），而显示侧 `data_tx` 用 `H_VALID=960 / V_VALID=1080` 的输出时序在 ≈71 MHz 上跑（一帧要 ~1M 个 `o_clk`），所以显示侧在整个仿真里只完成约 1 帧 → 只换 1 次 bank。**真实系统里相机与显示帧率相当（都 ~60fps）**，`wr_sw ≈ rd_sw`，轮转应为干净的三 bank 循环。

**判据**（若 Lead 想确认轮转是否健康）：
- 跑本 TB 时看 `bank switch events : wr=N rd=M`。`N ≈ M` ⇒ 轮转健康；`N >> M` ⇒ 写 bank 冻结（当前激励如此，属预期）。
- 若在**真实帧率**激励下（相机与显示都按真实时序）仍出现 `N >> M`，那才是异常，需要查 `rd_sw` 为何不产生（`data_tx`/`par2ser_parse` 的 `fifo_rd_period` 链路）。
- 按代码推演，`wr`/`rd` 交替时干净轮转的顺序是 `bank2 → bank1 → bank0 → bank2 …`（初值 `dirt_bank=2'b10`，`bank_switch.v:98`），起点是 bank2 而不是 bank0，这是正常的。

### 10.4 数字核对（第 3 项）

- 全工程 grep `03AE4000` / `03ae4000`（含 `docs\`、`rtl\`、`sim\`、`*.ps1`）⇒ **0 命中**，该数字不存在于本仓库。
