## 3. 今天的核心成果：厂商 IP 的 4 个颜色 bug

**厂商 demo（v7）能出图，但颜色是错的。挖出来 4 个真实 bug，全部有代码依据 + 实拍验证。**

### Bug 1：`debayer_top_2to1.v:85` 缺字节交换

```verilog
// v7 原版（错）：
.i_p  (w_gain_data),
// 修法（对）：
.i_p  ({w_gain_data[7:0], w_gain_data[15:8]}),
```

**后果**：一拍进两个像素，`ch0_b` 在高位、`ch0_g` 在低位；不交换 ⇒ 像素奇偶错 ⇒ 拜耳相位偏一列 ⇒ 紫色 + 网格。
**验证**：变体 **X** ⇒ 紫变绿、网格减弱。

### Bug 2：`raw_to_rgb.v:396/398` R/B 插值来源对调

```verilog
// 修法（两行互换）：
L396: r_r_00_00_1P[PW-1:P_DEPTH] <= w_b_00_00_h0 >> 1;   // 原来 w_r_00_00_h0
L398: r_b_00_00_1P[PW-1:P_DEPTH] <= w_r_00_00_h0 >> 1;   // 原来 w_b_00_00_h0
```

**几何论证**（指挥官验证过）：
- T0 高位 G 点的左右邻居是 T0 低字节（**B**），上下邻居是 T1 高字节（**R**）
- 而 `w_r_00_00_h0` = 左右邻居低字节 = **B**，被赋给 R ⇒ 橙 (200,150,20) 变蓝 (20,150,200)

**验证**：变体 **XZ** ⇒ 蓝点消失。

### Bug 3：`rgb_gain_v1.v` 例化的 `gain_r` / `gain_b` 接在相反像素上

```verilog
// 原版（错）：
.gain_b (r_gain),   // 红像素吃到 B 增益
.gain_r (b_gain),   // 蓝像素吃到 R 增益

// 修法：
.gain_b (b_gain),   // ← 改
.gain_g (g_gain),
.gain_r (r_gain),   // ← 改
```

**后果**：调大 `b_gain` ⇒ 画面变红（因为作用在红像素上）。
**实拍验证**：
| 版本 | R 增益 | B 增益 | 画面 |
|---|---|---|---|
| XZL | 1.094× | 1.367× | 偏黄绿 |
| WB1 | 1.25× | **2.5×** | **非常红** |
| WB2 | 1.5× | **3.25×** | **全红** |

**⇒ 单调规律证明 B 增益作用在红像素上。**

### Bug 4：增益级与去马赛克的行奇偶差一行

**根因**（`line_buffer.v` 有三行，中心行延迟一行）：

| 输出 | 对应输入行 |
|---|---|
| `o_p_01` | 当前行 n（延迟 2 拍）|
| `o_p_00`（**中心行**）| **上一行 n−1** |
| `o_p_11` | 上上行 n−2 |

**而 `raw_to_rgb` 的 `r_y_cnt` 计的是当前输入行 n** ⇒ 去马赛克认识的行奇偶 = `~(n&1)`，与增益级 `r_line_cnt` 的 `n&1` **相反** ⇒ G 像素被乘了 B/R 增益。

**修法**：`rgb_gain_v1.v:68`
```verilog
// 原版：
if (r_line_cnt) begin
// 修法：
if (!r_line_cnt) begin
```

**验证**：变体 **XZL** ⇒ 马赛克/绿点全部消失，红线正确显示为红。

### 另外一条（不用改）

**`ti60f225_oob_top.v:1006/1008` 的 `.i_bdata/.i_rdata` 看起来交叉，但实际上游 `{hdmi_tx_bdata, hdmi_tx_gdata, hdmi_tx_rdata} <= rgb_datax2` 的拼接顺序也反 ⇒ 两次交叉抵消，最终 R/B 是对的。**（我一开始以为是 bug，后来查证是抵消的，**不要改**。）

### 还有一个厂商的坑（不是 bug，但要知道）

**传感器寄存器 `0x3221 = 0x66`** = 镜像 ON + 倒置 ON（180° 旋转）。
**⇒ 画面方向是正的（Kevin 确认），所以必须保留 `0x66`，不能改成 0x00。** 修拜耳相位要靠 RTL，不是靠改这个寄存器。

## 4. 构建流程（5 步，必须照做，不能手拼）

**厂商 v7 工程的正确构建链**（`tools\v7_flow.ps1` 已封装）：

```
[1] efx_map                                      综合 → 网表
[2] efx_pnr（无约束）                            产 vdb
[3] efx_run -f interface → interface.csv         生成引脚约束

[6] efx_pgm                                      bitgen
```

**⚠️ 最容易犯的错（我踩了一天）：**
- **`efx_pnr` 必须传 `--sync_file <design>.interface.csv`**，否则**引脚约束和时钟约束全部不生效**
- 症状：`pnr.log` 里全是 `WARNING: [SDC ...:10] No valid pin(s) found for clock` / `Unable to create_clock` ⇒ **位流烧上去就是"无信号"**
- **验收判据**：`No valid pin(s) found for clock` 必须 = **0**

**用法：**

```powershell

powershell -NoProfile -ExecutionPolicy Bypass -File D:\FPGA\mmt\tools\v7_flow.ps1 `

  -Tag 新版本
```

**耗时**：约 5-6 分钟/版（`efx_map` 1.5min + `efx_pnr` ×2 共 3min + bitgen 秒级）。

## 7. 已知问题（按优先级）

### 7.1 🔴 Debugger 热调 VIO 不通（影响效率，不阻塞）

**已查明：**
- **Debugger 枚举 USB 需要 `EFX_HIFTDI_ENABLE=1`**（不加就 `USB Target` 列表空 ⇒ `No target device available`）
- **即使枚举到，`config_jtag` 仍报 `No backend available`** —— 因为 `JtagManager` 走 **pyftdi + libusb** 后端，而我们板子用 **FTDI 原生 D2XX 驱动**
- 用 Zadig 换 WinUSB 可以通，但**会让 `ftdi_program.py` 的 D2XX 烧录路径失效**，且换驱动有蓝屏风险 ⇒ **不划算**

**⇒ 结论：热调 VIO 在当前驱动配置下不可行，只能重编（6-8 分钟/轮）。**

**GUI 操作路径（如果哪天环境变了想试）：**
1. `Perspectives` 菜单 → **`Debug`**（不是 Profile Editor）
2. `Program` 页 → `USB Target` → 点右边**刷新图标**（无文字，只有图标）
3. `Run` 页 → `Configuration` 分组 → **`Configure`**（初始是禁用的，刷新出设备才亮）
4. 注意：**profile 的 UUID 必须和板上位流匹配**（每个变体的 `debug.json` 里 vio0 UUID 不同），否则报 `EfxDbgMisMatchCoreUUIDError`

**详细文档**：`out\evidence\debugger_connect_solution.md`、`debugger_vio_card.md`、`debugger_vio_howto.md`

### 7.2 🔴 DDR 写通路 `AW=0`（独立问题，今天没碰）

**现象**：我们自己的工程（`D:\FPGA\mmt`）烧上去，串口 `[WR] AW=0` 永远不增长，屏幕上零雪花。

**已查明（同学分支的实测 + 指挥官验证）：**
- **写 FSM 是正常的**：`state=3`、`awvalid=1`、**`awready=0`**
- **⇒ 真因是 AXI 从端（互联/DDR3 控制器）从不返回 `awready`**
- 之前以为的"FSM 被综合删除"是**误判**（`infer-clk-enable` 的坑，见 7.4）

**下一步建议**：查 AXI Interconnect 的 `awready` 为什么恒 0 —— 可能是 `awlen`/`awsize`/`awid` 配置不匹配，或 DDR3 控制器没初始化完。

### 7.3 🟡 TinyML 推理没通

**缺 4 件（只在预编译 `tinyml_lib.a` 里，看不见源码）：**
1. 卷积参数寄存器语义
2. `init_accel()` 时序
3. 完成信号怎么等（PLIC 还是轮询）
4. 权重当前在 `0x00100000`，必须搬到 R7 `0x03000000`

**另外**：`infer-clk-enable=0` 时资源装不下（需 60833 XLR，器件只有 60800）⇒ **必须摘掉 TinyML 才能用 ice=0**。

### 7.4 🟡 Efinity 2026.1 的 `infer-clk-enable` 回归（已绕过，但要知道）

**现象**：`infer-clk-enable >= 1`（含默认 3）时，综合器会把"条件装载的寄存器"错写成 `.D(1'b0)` ⇒ 逻辑静默变常量。

**证据**：`out\evidence\synth_loop.md`（450 行）；最小复现件在 `D:\FPGA\易灵思\工作区\08_Efinix复现件\`。

**现状**：厂商 v7 工程用 `infer-clk-enable=3` 也能正常工作（写通路都是活的），所以**我们的 v7 路线不受影响**。我们自己的 `mmt` 工程受影响，但那条线已停在 `awready` 问题上。

### 7.5 🟡 JTAG 烧录是易失的

**`-m jtag` 是临时加载，断电/复位就丢配置**（屏幕变"无信号"或全红）。

**⇒ 不是坏了，重烧就好。**
**SPI 固化（`-m active`）在 hiftdi 后端不通，未解决。**

## 11. 重要纪律 / 踩过的坑

1. **"无法确认"是合法答案。** 不要凭记忆断言，每条结论要有实测证据。
2. **只由一个人跑 Efinity**（综合压力大、会互相抢 `work_syn`/`out` 目录）。并行代理必须用**独立目录**。
3. **`efx_pnr` 必须带 `--sync_file`**，否则约束全废（见 §4）。
4. **验证烧录结果不要看 exit code**，要看日志里是否同时出现 `Device ID read from JTAG: 0x10660A79` 和 `finished with JTAG programming`（脚本已实现）。
5. **烧之前确认板子枚举到 FTDI**：`VID_0403` 应该在位。
6. **JTAG 烧录易失**，断电要重烧。
7. **改参数前先确认"改的那个东西究竟作用在哪"** —— 今天有两次教训：
   - `v7_L` 改增益级行奇偶，但 A2 下三个增益都是 255 ⇒ 改了等于没改
   - WB1/WB2 假设"VIO 面板上 r_gain 就是红增益"，实际接反了
8. **不要用"位流大小差异"当作流程不一致的证据** —— `bitstream_compression=on`，大小随布局浮动。
9. **`mmt.xml` 里 `infer-clk-enable` 的注释可能和 value 不符**（踩过：注释写 3→0，value 实际还是 3）。
