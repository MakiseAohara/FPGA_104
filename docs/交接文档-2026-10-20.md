## 3. 今天的核心成果：厂商 IP 的 4 个颜色 bug

**厂商 demo（v7）能出图，但颜色是错的。挖出来 4 个真实 bug，全部有代码依据 + 实拍验证。**

### Bug 1：`debayer_top_2to1.v:85` 缺字节交换（**经验性修法，根因未完全证明**）

```verilog
// 厂商 v7 原版（实读 L85）：
.i_p  (w_gain_data),
// 最终版（v7_WBH7 实读 L85）：
.i_p  ({w_gain_data[7:0], w_gain_data[15:8]}),
```

**现象（已确证）**：加了这个交换后，画面从**紫**变成**绿**，网格明显减弱（变体 **X**）。

**根因解释（⚠️ 未完全证明）**：
- 支持的说法：一拍进两个像素，`ch0_b` 在高位、`ch0_g` 在低位；不交换 ⇒ 像素奇偶错 ⇒ 拜耳相位翻转。
- **但注意**：交换整个 16 位字的两个字节，同时改变了"一拍内两个像素的先后顺序"，**这与"改变拜耳相位"不是同一件事**。目前**没有仿真证据**能把两者分开。
- ⇒ 请把这条理解为「**现象已确证（紫→绿），根因解释是推断**」。

**备选方案（更干净，已编未烧）**：**`v7_Y`** —— 不改 `debayer_top_2to1.v` 的字节序，而是把 `raw_to_rgb.v:349` 的 `else if (r_y_cnt[0])` 取反成 `else if (!r_y_cnt[0])`。
**理由**：从"空间上把行奇偶翻过来"，比"交换一拍内两像素的先后"语义更清晰。
**状态**：`v7_Y` 位流已编好（`608A84BC…`），**从未烧过**。
**⇒ 如果以后 Bug 1 的表现出现争议，可以用 `v7_Y` 做对照。**

（待确认：Bug 1 与 `v7_Y` 之间是否等价 —— 见文末待确认清单 #1）

### Bug 2：`raw_to_rgb.v:396/398` R/B 插值来源对调

```verilog
// 修法（两行互换）：
L396: r_r_00_00_1P[PW-1:P_DEPTH] <= w_b_00_00_h0 >> 1;   // 原来 w_r_00_00_h0
L398: r_b_00_00_1P[PW-1:P_DEPTH] <= w_r_00_00_h0 >> 1;   // 原来 w_b_00_00_h0
```

**几何论证**（指挥官验证过）：
- T0 高位 G 点的左右邻居是 T0 低字节（**B**），上下邻居是 T1 高字节（**R**）
- 而 `w_r_00_00_h0` = 左右邻居低字节 = **B**，被赋给 R ⇒ 橙 (200,150,20) 变蓝 (20,150,200)

**验证**：变体 **XZ** ⇒ 蓝点消失。

**代码核对（v2 重新读过 `raw_to_rgb.v` L394-399，与上述描述一致）**：

```
L394:  r_b_00_00_1P[P_DEPTH-1:0]  <= r_bayer_00_00_1P_0;      // 低字节 = B 点，直接取
L396:  r_r_00_00_1P[PW-1:P_DEPTH] <= w_b_00_00_h0>>1;          // 高字节 = G 点，r 取"左右邻居"
L397:  r_g_00_00_1P[PW-1:P_DEPTH] <= r_bayer_00_00_1P_1;       // 高字节 = G 点，g 直接取
L398:  r_b_00_00_1P[PW-1:P_DEPTH] <= w_r_00_00_h0>>1;          // 高字节 = G 点，b 取"上下邻居"
```

**⇒ 该分支（`else if (r_valid_1P)` 后半段，注释 `//G R G R`）里：低字节是 B 点、高字节是 G 点。**
**G 点需要插值的 R 和 B：**
- R 来自**同一行左右邻居**（B 点 ⇒ 低字节）⇒ `w_?_00_00_h0` 里装的是"左右邻居的低字节"
- B 来自**上下行**（另一行的高字节）⇒ 另一个 wire 装"上下邻居的高字节"
- ⇒ 当前 L396 让 `r_r` 取自 `w_b_00_00_h0`（= 左右邻居 = B）**是错的**，L398 让 `r_b` 取自 `w_r_00_00_h0`（= 上下邻居 = R）**也是错的**
- ⇒ **两行互换后正确**（与实拍 XZ 蓝点消失一致）

**⇒ 核对通过：几何描述与代码一致。**

### Bug 3：`rgb_gain_v1` 例化的 `gain_r` / `gain_b` **与行奇偶错位，需要交换**

**⚠️ 修订（v2）：本节初稿把方向写反了。以下是实际读到的原文。**

**厂商原版**（`Ti60f225_sc431hai2hdmi_v7\rtl\debayer\debayer_top_2to1.v:51-53`，实读）：

```verilog
	.gain_b (b_gain		),     // 名字对得上
	.gain_g (g_gain		),
	.gain_r (r_gain		),     // 名字对得上
```

**最终版**（`v7_WBH7\rtl\debayer\debayer_top_2to1.v:51-53`，实读）：

```verilog
	.gain_b (r_gain		),     // ← 交换
	.gain_g (g_gain		),
	.gain_r (b_gain		),     // ← 交换
```

**⇒ 所以"修法"是：厂商 `.gain_b(b_gain)`／`.gain_r(r_gain)` ⇒ 改成 `.gain_b(r_gain)`／`.gain_r(b_gain)`（即 **b↔r 两个端口互换接线**）。**

**为什么要把"名字对得上"的接线故意交叉？** 因为 **Bug 4（行奇偶反转）** 让增益级作用到了相反的行上：

- 增益级以为在给"奇行"分配 `high=Gr(gain_g) / low=R(gain_r)`
- 但实际拿到的是"偶行"，偶行的正确分配是 `high=B(gain_b) / low=Gb(gain_g)`
- ⇒ 于是把 `gain_r` / `gain_b` 交叉，让错位后的行拿到正确增益

**⇒ ⚠️ Bug 3 必须与 Bug 4（`rgb_gain_v1.v:68` 取反）一起使用，二者是一套。单独回退任何一处都会让颜色变错。**

**这是独立厂商缺陷，还是 Bug 4 的配套补偿？**

**判定：证据支持"Bug 3 是 Bug 4 的配套补偿"，但不能完全排除两者独立。**

| 证据 | 指向 |
|---|---|
| 厂商原接线 `.gain_b(b_gain)`／`.gain_r(r_gain)` **名字本来就对** | 若厂商只有 Bug 3，颜色应该是对的 ⇒ 说明单独看 Bug 3 不成立 |
| 错位来源是 `line_buffer` 中心行延迟一行 ⇒ 行奇偶反转 | 解释了为什么"名字对"却"作用错" |
| XZL（Bug4 已修、增益未调）画面正确；WBF（再加 Bug3 交换）调参方向才变对 | 两者耦合 |
| WB1/WB2 偏红单调规律 | 这是 **Bug 3 未修时**的现象（B 增益作用在红像素上）|

**⚠️ 但严格说，我没有做"只修 Bug 4、不修 Bug 3"的对照实验（那需要额外一版位流），所以"Bug 3 不是独立缺陷"这个结论证据不足，只能写"证据支持配套补偿"。**

**实拍验证（Bug 3 修复前后调参方向的变化）**：
| 版本 | Bug3 状态 | R 增益 | B 增益 | 画面 |
|---|---|---|---|---|
| XZL | 未交换 | 1.094× | 1.367× | 偏黄绿 |
| WB1 | 未交换 | 1.25× | **2.5×** | **非常红** |
| WB2 | 未交换 | 1.5× | **3.25×** | **全红** |
| WBF | **已交换** | 1.25× | 2.5× | 白纸微蓝（方向正常了）|

**⇒ 未交换时 B 增益越大画面越红（单调）；交换后调参方向符合直觉。**

### Bug 4：增益级与去马赛克的行奇偶差一行

**根因**（`line_buffer.v` 有三行，中心行延迟一行）：

| 输出 | 对应输入行 |
|---|---|
| `o_p_01` | 当前行 n（延迟 2 拍）|
| `o_p_00`（**中心行**）| **上一行 n−1** |
| `o_p_11` | 上上行 n−2 |

**而 `raw_to_rgb` 的 `r_y_cnt` 计的是当前输入行 n** ⇒ 去马赛克认识的行奇偶 = `~(n&1)`，与增益级 `r_line_cnt` 的 `n&1` **相反** ⇒ G 像素被乘了 B/R 增益。

**修法**：`rgb_gain_v1.v:68`
```verilog
// 厂商原版（实读 L68）：
	if(r_line_cnt) begin
// 最终版（v7_WBH7 实读 L68）：
	if(!r_line_cnt) begin
```

**证据等级（v2 标注）：`源码推断 + 实拍佐证`，不是仿真证明。**

| 环节 | 证据强度 | 说明 |
|---|---|---|
| `o_p_00` = 输入行 n−1 | **源码推断** | 依据 `line_buffer.v` 的 `addr2={~r_addr1_sel, r_addr1}` 读另一块 RAM + `r_addr1_sel` 行尾翻转。**没有 `line_buffer` 独立仿真** |
| `r_y_cnt` 计当前行 n | **源码推断** | `raw_to_rgb.v` 的计数器逻辑 |
| 两者奇偶相反 | **推论**（由上面两条推出）|
| 奇偶相反 ⇒ G 像素吃错增益 | **推论** |
| **改 `!r_line_cnt` 后马赛克/绿点消失** | ✅ **实拍确证**（变体 XZL，Kevin 确认）|

**⇒ 请这样理解：「现象确证 + 机理推断」。** 若以后有异常，优先用仿真验证 `line_buffer` 的行延迟。

**验证**：变体 **XZL** ⇒ 马赛克/绿点全部消失，红线正确显示为红。

**⚠️ 这条与 Bug 3 是一套，见 Bug 3 末尾说明。**

**`ti60f225_oob_top.v:1006/1008` 的 `.i_bdata/.i_rdata` 看起来交叉，但实际上游 `{hdmi_tx_bdata, hdmi_tx_gdata, hdmi_tx_rdata} <= rgb_datax2` 的拼接顺序也反 ⇒ 两次交叉抵消，最终 R/B 是对的。**（我一开始以为是 bug，后来查证是抵消的，**不要改**。）

## 5. 白平衡调参记录（VIO 初值）

**参数在 `debug_top.v:102-105`：**

```verilog
.PROBE_OUT0_INIT_VAL ( 'h158 ),   // R 增益（Q8.8）
.PROBE_OUT1_INIT_VAL ( 'h118 ),   // G 增益
.PROBE_OUT2_INIT_VAL ( 'h170 ),   // B 增益
.PROBE_OUT3_INIT_VAL ( 'h0   ),   // gamma_sel
```

## 7. 已知问题（按优先级）

### 7.1 🔴 Debugger 热调 VIO 不通（影响效率，不阻塞）

**已查明：**
- **Debugger 枚举 USB 需要 `EFX_HIFTDI_ENABLE=1`**（不加就 `USB Target` 列表空 ⇒ `No target device available`）
- **即使枚举到，`config_jtag` 仍报 `No backend available`** —— 因为 `JtagManager` 走 **pyftdi + libusb** 后端，而我们板子用 **FTDI 原生 D2XX 驱动**
- 用 Zadig 换 WinUSB 可以通，但**会让 `ftdi_program.py` 的 D2XX 烧录路径失效**，且换驱动有蓝屏风险 ⇒ **不划算**

**⇒ 结论：热调 VIO 在当前驱动配置下不可行，只能重编（6-8 分钟/轮）。**

**GUI 操作路径（如果哪天环境变了想试）：**
1. `Perspectives` 菜单 → **`Debug`**（不是 Profile Editor）
2. `Program` 页 → `USB Target` → 点右边**刷新图标**（无文字，只有图标）
3. `Run` 页 → `Configuration` 分组 → **`Configure`**（初始是禁用的，刷新出设备才亮）
4. 注意：**profile 的 UUID 必须和板上位流匹配**（每个变体的 `debug.json` 里 vio0 UUID 不同），否则报 `EfxDbgMisMatchCoreUUIDError`

**详细文档**：`out\evidence\debugger_connect_solution.md`、`debugger_vio_card.md`、`debugger_vio_howto.md`

### 7.2 🔴 DDR 写通路 `AW=0`（独立问题，今天没碰）

**现象**：我们自己的工程（`D:\FPGA\mmt`）烧上去，串口 `[WR] AW=0` 永远不增长，屏幕上零雪花。

**已查明（同学分支的实测 + 指挥官验证）：**
- **写 FSM 是正常的**：`state=3`、`awvalid=1`、**`awready=0`**
- **⇒ 真因是 AXI 从端（互联/DDR3 控制器）从不返回 `awready`**
- 之前以为的"FSM 被综合删除"是**误判**（`infer-clk-enable` 的坑，见 7.4）

**下一步建议**：查 AXI Interconnect 的 `awready` 为什么恒 0 —— 可能是 `awlen`/`awsize`/`awid` 配置不匹配，或 DDR3 控制器没初始化完。

### 7.3 🟡 TinyML 推理没通

**缺 4 件（只在预编译 `tinyml_lib.a` 里，看不见源码）：**
1. 卷积参数寄存器语义
2. `init_accel()` 时序
3. 完成信号怎么等（PLIC 还是轮询）
4. 权重当前在 `0x00100000`，必须搬到 R7 `0x03000000`

**另外**：`infer-clk-enable=0` 时资源装不下（需 60833 XLR，器件只有 60800）⇒ **必须摘掉 TinyML 才能用 ice=0**。

### 7.4 🟡 Efinity 2026.1 的 `infer-clk-enable` 回归（已绕过，但要知道）

**现象**：`infer-clk-enable >= 1`（含默认 3）时，综合器会把"条件装载的寄存器"错写成 `.D(1'b0)` ⇒ 逻辑静默变常量。

**证据**：`out\evidence\synth_loop.md`（450 行）；最小复现件在 `D:\FPGA\易灵思\工作区\08_Efinix复现件\`。

**现状**：厂商 v7 工程用 `infer-clk-enable=3` 也能正常工作（写通路都是活的），所以**我们的 v7 路线不受影响**。我们自己的 `mmt` 工程受影响，但那条线已停在 `awready` 问题上。

### 7.5 🟡 JTAG 烧录是易失的

**`-m jtag` 是临时加载，断电/复位就丢配置**（屏幕变"无信号"或全红）。

**⇒ 不是坏了，重烧就好。**
**SPI 固化（`-m active`）在 hiftdi 后端不通，未解决。**

## 11. 重要纪律 / 踩过的坑

1. **"无法确认"是合法答案。** 不要凭记忆断言，每条结论要有实测证据。
2. **只由一个人跑 Efinity**（综合压力大、会互相抢 `work_syn`/`out` 目录）。并行代理必须用**独立目录**。
3. **`efx_pnr` 必须带 `--sync_file`**，否则约束全废（见 §4）。
4. **验证烧录结果不要看 exit code**，要看日志里是否同时出现 `Device ID read from JTAG: 0x10660A79` 和 `finished with JTAG programming`（脚本已实现）。
5. **烧之前确认板子枚举到 FTDI**：`VID_0403` 应该在位。
6. **JTAG 烧录易失**，断电要重烧。
7. **改参数前先确认"改的那个东西究竟作用在哪"** —— 今天有两次教训：
   - `v7_L` 改增益级行奇偶，但 A2 下三个增益都是 255 ⇒ 改了等于没改
   - WB1/WB2 假设"VIO 面板上 r_gain 就是红增益"，实际接反了
8. **不要用"位流大小差异"当作流程不一致的证据** —— `bitstream_compression=on`，大小随布局浮动。
9. **`mmt.xml` 里 `infer-clk-enable` 的注释可能和 value 不符**（踩过：注释写 3→0，value 实际还是 3）。
