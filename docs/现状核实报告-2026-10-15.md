## 3. 引脚覆盖

### 3.1 方法（可复现）

1. 从 `rtl\mmt\mmt_top.v` 的端口声明区（第 1–239 行，`);` 结束）解析出 128 个顶层端口名。
2. 在 `out\mmt.interface.csv` 全文按词边界查找每个端口名。

**结果：缺失 0 个。**

⚠️ 解析 `mmt.interface.csv` 有个坑：**端口名在最后一列，不是第一列**。
格式是 `<方向>[, 可选required], <x>, <y>, <z>, <clock 或 __bypass__>, <端口名>[bit]`：

```
output, 219, 4, 0, __bypass__, o_uart_txd
output, 219, 5, 2, __bypass__, led[0]
clkout, 18, 0, -1, CLK_25M
```

第一列是**方向属性**。按首列取会得到 3 个"端口名"并得出完全错误的结论（我第一遍就这么错了）。

### 3.2 关于 "Missing Interface Pins"（别读成错误）

## 6. 固件在片内 RAM 里（独立重建比对，不只是哈希互比）

交接说"`mmt_fw.bin` = 6752 B，与 `sw\build\soc_ram\*symbol*.bin` 及 `ip\sapphire_soc\`（两份副本）逐字节一致"。
这句话有歧义（.bin 是平铺二进制，symbol 文件是 ASCII `0/1` 文本，二者不可能"字节相同"）。我按**真实语义**重做了：

**方法**：按 `sw\hex2soc.ps1:98-114` 的约定（地址 `4*i+n` 的字节 → `symbolN` 第 `i` 行，每行 8 个 `0/1`，首位是 MSB，
解码用 `[Convert]::ToByte(line,2)`）从 4 个 symbol 文件**重建** 32 KB，再与 `mmt_fw.bin` 逐字节比。

| 检查 | 结果 |
|---|---|
| 容量 | 8192 行 × 4 = **32768 B (32 KB)**，与 `link.ld` 一致 |
| `mmt_fw.bin` 长度 | 6752 B |
| word0 | `0x00002117`（首 8 字节 `17 21 00 00 13 01 01 52`） |
| **6752 字节内差异** | **0** |
| **固件末尾之后的非零字节** | **0**（尾部干净，无旧固件残留） |
| `ip\sapphire_soc\` 副本 vs `sw\build\soc_ram\` | 逐行差异 **0** |
| `ip\sapphire_soc\source\hardware\netlist\` 副本 | 逐行差异 **0** |

⇒ **结论：位流里带的片内 RAM 初值 == 当前固件二进制，逐字节成立。**

### 附：核对过程中我自己的一个 bug（记下来免再踩）

第一遍比对得到"6046 个字节不一致"。原因不是工程问题，是 **PowerShell 的 `[int]` 转换用银行家舍入**：
`[int](3/4)` = **1**（不是 0），于是 `i%4 != 0` 的字节全部取到了下一行，凭空造出差异。
换成整数位移 `$i -shr 2` 后归零。
**教训：在 PowerShell 里做「整除」必须用 `-shr` 或 `[math]::Floor`，不能用 `[int](a/b)`。**
（另外第一遍我还把位序搞反了：`$readmemb` 的**首位是 MSB**，不是 LSB。）

## 11. 【下午更新】修掉一个会在上板时致命的 bug + 重出位流

### 11.1 发现的 bug：加速器完成中断没接进 CPU

**证据链（全部自己复现，非转述）**

1. 官方库 `D:\FPGA\tinyml\...\tinyml_lib.a`（md5 `6a6c9992…`，14 个成员）里抽出 `conv.o`，
   用 `D:\riscv\xpack-riscv-none-elf-gcc-15.2.0-1\bin\riscv-none-elf-objdump.exe -d -r -M numeric` 反汇编：

   ```
   conv_drv  : 670: lui x7, .LANCHOR0
               678: add x18, x16, x18
               67c: lw  x27, 0(x18)     ; .L28:
               680: beqz x27, 67c       ; ← 自旋！零则死循环
               684: sw  x0, 0(x18)
   conv_intr :  30: lui x28, .LANCHOR0
                44: sw  x31, 0(x30)     ; ← 唯一把该标志置 1 的地方
                48: .insn 0x500f        ; D-cache 刷新
   ```

   **⇒ ISR 是唯一唤醒源。** 我把 79 条 custom-0 指令的 `(func7,func3,rs1,rs2,rd)` 全部手工解出，
   与启动指令 `0x053e898b`（f7=2 f3=0 rs1=1）对得上。

2. 我们工程：`rtl\mmt\soc\mmt_soc_subsystem.v:433` 原本是 **`.userInterruptA (1'b0)`**；
   `rtl\mmt\mmt_top.v:425` 注释写着"加速器中断（暂未接进 SoC userInterruptA）"。
3. 官方 `D:\FPGA\tinyml\tinyml_hello_world\Ti60F225_tinyml_hello_world\tinyml_soc.v:473`：
   `assign userInterruptA = cpu_customInstruction_cmd_int;`

**结论**：不接中断 ⇒ ISR 永不执行 ⇒ `.LANCHOR0` 恒 0 ⇒ `conv_drv` 在 `0x680` 永久自旋。
这正好解释了固件为什么把 `MMT_TINYML_ISSUE_EN` 默认设 0（fail-closed）。
