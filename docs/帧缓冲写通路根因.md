- 工程：`D:\FPGA\mmt`（Efinity 2026.1.132，Ti60F225I3）
- 承接：task-10（已证明"写 FIFO 被整个删除、`wr_start` 恒 0、厂商同款工程该 FIFO 占 13 块 BRAM"）
- 时间：2026-10-11 21:4x–22:0x
- 纪律：**只写本文档**；未改动任何文件（含 `ip\`）；未跑 Efinity 流程；iverilog 未再使用
- 标注约定：**实测** = 直接读文件/报告得到的事实；**推断** = 由实测推出的机理；**无法确认** = 本轮证据不足

## 0. 结论摘要

### 0.1 根因判定：**几乎可以确定在 CSI RX IP 内部（5.15 版本）的视频输出门控上；但它不在明文里，无法静态读到驱动表达式**

- 我把 `pixel_data_valid` / `hsync_vc0` / `vsync_vc0` 在明文里能追的链路**全部追完了**，结论是：**这三个信号在明文代码里只出现"端口声明/端口连接"，一次赋值都没有**；真正的驱动表达式在 `efx_csi2_rx_top` 的 **AES 加密包（`pragma protect`）内部**。详见 §2。
- 也就是说：**Lead 设想的"在我们那份明文 508KB 里 grep 出最终驱动表达式"这条路是走不通的**——IP 的顶层包装是明文，视频通路的核心模块体是加密的。
- 但**实测差异非常明确、且方向一致**：mmt 的 CSI RX 比厂商的同一个 IP **少了 32 块 BRAM（4 vs 36）**、少了 262 个 FF、少了 620 个 LUT，并且 **`i_mipi_rx_pclk` 上的存储器端口从 45 个变成 0 个**。这说明 **5.15 这个配置下，像素侧的 FIFO/存储整段没有被实现**，与"视频输出被折叠成常量"完全吻合。详见 §3。

### 0.2 最可能的机理（**推断**，与全部实测自洽）

`mmt_top.v:583-584` 把 CSI RX 的 AXI 域**永久按住**（`.axi_clk(1'b0)`、`.axi_reset_n(1'b0)`）。
**综合器可以证明任何 AXI 域触发器恒等于它的复位值**（因为复位永远是 0）。
**推断**：5.15 版 IP 在 AXI 域里新增了一个"像素输出使能"类寄存器，且其复位值为"关闭"；于是综合器把 `pixel_data_valid`/`hsync_vc0`/`vsync_vc0` 证明为常量 0，进而把下游整条 `frame_buffer` 写通道（连同 128b×1024 写 FIFO 的 13 块 BRAM）全部折叠掉。
5.6 版没有这个寄存器（或复位值为"使能"），所以厂商顶层**同样把 AXI 绑 0 也能跑**。

这条推断可以**用一次 `efx_map` 直接判死**：把 AXI 域的时钟/复位放过（**不发起任何 AXI 事务**），如果 CSI RX 的 BRAM 从 4 跳回 ~36、`ddr_wr_buffer_inst` 的 mem 从 0 变 13，机理即证实。见 §6 判据 5 / §5 实验 E1。

### 0.3 推荐修法（按代价从低到高）

| 顺序 | 修法 | 依据强度 | 代价 |
|---|---|---|---|
| **E1（先做，零上板）** | 顶层让 CSI RX 的 AXI 域脱离常复位：`.axi_clk(core_clk)`、`.axi_reset_n(w_arstn)`，其余 AXI 信号保持绑 0 | 推断（机理一致）+ 一次 `efx_map` 即可判定 | 改 2 行顶层 |
| **E2（最稳，已验证过的配置）** | 用厂商 5.6 的 `ip\csi_rx_controller` 替换本工程的 5.15（同模块名/同端口，`mmt_top` 不用改） | 实测（厂商那份 build 里写 FIFO 是活的、13 块 BRAM） | 换 IP + 修 `settings.json` 路径 |
| **E3（对照实验）** | 用 2026.1 重新生成 5.15，仅把 `MIPI_CSI2_RX_DEBUG`/`MIPI_CSI2_RX_PIXEL_SIDEBAND` 在 0/1 之间做 A/B | **依据不足**（见 §1.3），只作对照 | 重生成 IP |

### 0.4 可直接排除的三个假设（我已逐条验证）

1. **不是顶层接线问题** —— 两侧 `csi_rx_controller`/`frame_buffer` 例化**逐行一致**（§1.1）。
2. **不是 `csi_rx_controller_define.vh` 陈旧的问题** —— 厂商的 `.vh` **同样陈旧**，而且**两侧 `.sv` 都不 include 任何 define 文件**（§1.2）。
3. **不是那两个新参数（`MIPI_CSI2_RX_DEBUG`/`MIPI_CSI2_RX_PIXEL_SIDEBAND`）在起作用** —— 它们只控制 `` `ifdef `` 下的**额外端口**，而这两个宏在**两个工程里都没有被定义**，所以全关；它们不会改变已有输出的驱动（§1.3）。

| 位置 | 作用 |
|---|---|
| `csi_rx_controller.sv:4452-4463` | `efx_csi2_rx_top` 的额外端口声明 |
| `csi_rx_controller.sv:5687-5695` | `efx_csi2_rx` 的额外端口声明 |
| `csi_rx_controller.sv:5950-5961` | `efx_csi2_rx` → `efx_csi2_rx_top` 的额外连接 |

## 4. 机理：为什么"AXI 常复位"能把整条视频通路折成常量

### 4.1 综合器的推理能力（这是理解本 bug 的关键）

`mmt_top.v:583-584`：
```verilog
.axi_clk       (1'b0),
.axi_reset_n   (1'b0),
```
`axi_reset_n` 是**常量 0**。于是 IP 内部**任何**形如
```verilog
always @(posedge axi_clk or negedge axi_reset_n)
    if (!axi_reset_n) q <= RESET_VAL;
```
的触发器，其 Q 都**可以被证明恒等于 `RESET_VAL`**（异步复位一直有效，D 端/CE 都不影响结果）。综合器随后做常量传播，把依赖它的一切逻辑折叠。

### 4.2 推断的因果链

```
IP 5.15 内部（推断）：AXI 域新增了一个"像素/视频输出使能"类寄存器，
                     复位值 = 0（关闭），且只能由 AXI 写来置 1
        │
        ├─ 但 mmt_top 把 axi_reset_n 常压 0  ⇒ 该寄存器被证明恒 0
        ├─ 于是 pixel_data_valid / hsync_vc0 / vsync_vc0 被证明恒 0
        │        │
        │        └─→ CSI RX 像素侧 FIFO 全被删（BRAM 36→4；i_mipi_rx_pclk 存储器端口 45→0）
        │             └─→ frame_buffer 的 i_vs/i_de 恒定 ⇒ frame_stable/frame_start 恒 0
        │                  └─→ wr_start 恒 0 ⇒ ddr_wr_buffer 写 FSM state 恒 0
        │                       └─→ U_wr_fifo 128b×1024 被整块删除（少 13 块 BRAM）
        │                            └─→ fb_awvalid/fb_wvalid/fb_wlast 恒 0（摄像头图像进不了 DDR3）
        │
        └─ 5.6 版没有这个寄存器（或复位值 = 1）
           ⇒ 厂商顶层同样把 AXI 绑 0，视频通路照样活（对照组实测）
```

### 4.3 这条机理能解释的现象清单（逐条对得上）

| 现象 | 是否被该机理解释 |
|---|---|
| CSI RX BRAM 36→4、像素时钟存储器端口 45→0 | ✅ 像素侧 FIFO 因输出恒 0 被删 |
| CSI RX FF 1191→929、LUT 2203→1583 | ✅ 依赖输出的逻辑被折叠 |
| lane aligner 的 4 块保留、下游全没 | ✅ 折叠从输出往上游传播，止于仍被字节域驱动/可观测的部分 |
| `frame_stable`/`wr_start` 恒 0 | ✅ 输入恒 0 |
| 写 FIFO 被整块删、CE 全无 | ✅ 写侧 `wr_fifo_wren` 与该 FIFO 的读侧都无来源 |
| 顶层 RTL 与厂商逐行一致却行为不同 | ✅ 差异在 IP 版本内部 |
| **综合/布局布线零报错** | ✅ 常量折叠是合法优化 |

> **无法确认**：这条链的**第一环**（"5.15 在 AXI 域里新增了使能寄存器"）我看不到源码，只能由"差异 + 机理"推出。**它必须由 §5 的 E1 实验来判定**。

## 5. 修法（按代价从低到高，含可行性与风险）

### E1【首选 · 零上板成本 · 改 2 行顶层】让 CSI RX 的 AXI 域脱离常复位

**改动**（`rtl\mmt\mmt_top.v:583-584`，**由 Lead 决定是否应用**）：
```verilog
.axi_clk        (core_clk),     // 原 1'b0
.axi_reset_n    (w_arstn),      // 原 1'b0
```
其余 AXI 信号**保持绑 0**（`axi_awvalid/axi_wvalid/axi_arvalid = 1'b0`）——**不发起任何事务**，只是不再把整个 AXI 域按住。

**预期**：若 §4.2 的机理成立，则**释放复位**本身就足以让"输出使能"寄存器的复位值不再被持续施加（若其复位值是 1）或让工具不再把它证明成常量；`efx_map` 后 `inst_efx_csi2_rx` 的 RAM 应从 **4 跳回 ~36**、`ddr_wr_buffer_inst` 的 mem 从 **0 变 13**。
**风险**：低（改两行、无功能事务）。若 AXI 域出现 X 或未初始化状态，也只影响 IP 内部的配置寄存器。
**代价**：一次 `efx_map`（约 3 分钟）。
**判据**：§6 的判据 1、4、5。

### E2【最稳 · 已被对照证明能跑】把 CSI RX IP 换回厂商 5.6

**依据**：厂商 `Ti60f225_sc431hai2hdmi_v1`（**同一颗 SC431HAI 摄像头 → HDMI**）用的就是 5.6，其 build 里 `u_wr_fifo` = 13 块 BRAM、CE 齐全（§3.3）。同模块名、同端口 ⇒ `mmt_top.v` 不用改。

**做法**：
1. 用厂商的这 7 个文件替换 `D:\FPGA\mmt\ip\csi_rx_controller\`：
   `csi_rx_controller.sv`、`csi_rx_controller_define.svh`、`csi_rx_controller_define.vh`、`csi_rx_controller_tmpl.sv`、`csi_rx_controller_tmpl.v`、`csi_rx_controller_tmpl.vhd`、`settings.json`。
2. **必须修厂商 `settings.json` 里的路径**（它指向本机不存在的绝对路径）：
   - `args[1].--base_path`：`"E:\\FPGA_Prj\\...\\ip"` → `"ip"`
   - `output.external_source_source`：删掉那 4 条 `E:\...` 绝对路径
   - `sw_version` 会变成 `2024.1.163`（**风险点**，见下）
3. 也可能需要同步 `ip\csi_rx_controller\Testbench\`、`Ti60F225_devkit\` 等子目录（若 mmt.xml 只引用 `csi_rx_controller.sv`，见 §5 风险说明）。

**可行性依据（实测）**：`mmt.xml:134-135` 把该 IP 登记为
```xml
<efx:ip instance_name="csi_rx_controller" path="ip/csi_rx_controller/settings.json" ooc="false">
  <efx:ip_src_file name="csi_rx_controller.sv"/>
```
`mmt.xml:178` 另有 `<efx:param name="include" value="ip/csi_rx_controller"/>`。
**风险（无法确认）**：因为它是带 `settings.json` 的"IP"条目，Efinity 可能会尝试**重新生成**这个 IP；若它按 `sw_version: 2024.1.163` 去找 2024.1 的 `efx_csi2_rx` 生成器（本机只有 2026.1），可能报错或强制升级。**规避办法（二选一，由 Lead 决定）**：
   - (a) **保留 mmt 自己的 `settings.json`（5.15）**，只替换生成的 RTL（`csi_rx_controller.sv` + `_define.svh`）为厂商 5.6 版；这样 `sw_version` 仍是 2026.1.132，Efinity 不会去找旧生成器；
   - (b) 把该 IP 从"IP 条目"降级为普通源文件：删掉 `mmt.xml:134-136` 的 `<efx:ip>` 块、把 `ip/csi_rx_controller/csi_rx_controller.sv` 作为普通 `.sv` 源文件加入（保留 `include` 目录），这样工具不会尝试重新生成。

### E3【对照实验 · 依据不足，不推荐作为首选】用 2026.1 重新生成 5.15 做参数 A/B

只把 `MIPI_CSI2_RX_DEBUG` / `MIPI_CSI2_RX_PIXEL_SIDEBAND` 在 `1'b0`/`1'b1` 之间切换后重新生成。
**为什么依据不足**：这两个参数只控制 §1.3 里的 `ifdef` 端口，而对应宏在生成物里**没有被定义**；它们不会改变已有输出的表达式。所以**大概率无效**。
**唯一价值**：如果 E1 证实了"AXI 域门控"，那么 E3 可以顺便测出"这两个新参数是否是 5.15 引入该门控的开关"（成本低，可作为附录实验）。

### 不推荐的路径

| 路径 | 为什么不推荐 |
|---|---|
| 改 `csi_rx_controller_define.vh` 的参数值 | 实测该文件不被 include（§1.2）。改了没用，还会误导后人 |
| 在顶层把 CSI RX 的 AXI 接一个真的 AXI-Lite 主机去写配置 | 目前**不知道要写哪个寄存器**（加密），属于盲调；E1 花 2 行就能先判死，不必先做这个 |
| 绕过 CSI RX，用测试图样喂 frame_buffer | 只能验证下游、不能修复摄像头通路；可作为"确认下游是好的"的辅助实验 |
