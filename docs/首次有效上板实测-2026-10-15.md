## 1. 串口实测（v2 位流，`sw\serial_daemon.ps1` 抓 449 行）

### 1.1 系统活着的证据

```
[CAM] SCL=11914(d=0) CK=410395(d=8333) PCLK=991737(d=19812) DE=277542377(d=5635213)
      HS=1302067(d=26438) VS=1205(d=24) pd=305172(d=6197) ack=644(d=0) nk=0(d=0)
      st=0x00007FFE wc=1769(d=36) wmx=2400 link=0x54B95804 pid=0x4D4D5450 rh=0x00000FFF
[LP] mode=ACTIVE idle_f=4 thr=500 enter=30 ctrl=0x01
[PP] A raw=0.0C flt=0.0C rej=0 B raw=0.0C flt=0.0C rej=0 win=4 thrA=500(x100) thrB=150(x10)
```

| 字段 | 读法 | 结论 |
|---|---|---|
| `pid=0x4D4D5450` | 探针魔数 | 位流里有探针，**v2 生效** |
| `ack=644(d=0)` | I2C 应答数 | **摄像头 I2C 配置序列跑完且有应答**（不再是"SCL 有总数但 ACK=0"） |
| `DE/HS/VS/pd/CK` 全在涨 | CSI RX 输出 | **CSI RX 在持续吐像素** |
| `FRM` 在涨（d=12） | 视频帧翻转计数 | 视频后端在出帧 |
| `[LP]` / `[PP]` / `[CMD]` 行 | 本会话新加的固件 | 固件与 UART RX **都正常** |
| `T=0.0C RH=0.0% IR=0.0C` | 传感器 | **传感器全 0**（未接或未上拉，今晚没插传感器） |

### 1.2 ★ 核心故障：DDR 写通路一个写都没有

**56 个采样点（约 3 分钟）全部是**：
```
[WR] AW=0(d=0) W=0(d=0) st=0x00 amax=0x00000000(d=0x00000000) asmp=0 ast=0x00 az=NOIMG
```

`st`(0x74) 按 `mmt_soc_regs.v:380-385` 解码：

| bit | 信号 | 实测 |
|---|---|---|
| 0 | `fb_awvalid` 电平 | **0** |
| 1 | `fb_awready` 电平 | **0** |
| 2 | `fb_wvalid` 电平 | **0** |
| 3 | `fb_wready` 电平 | **0** |
| 4 | 曾发生 AW 握手 | **0（从未）** |
| 5 | 曾发生 W 握手 | **0（从未）** |

### 1.3 决定性对照实验：测试图案也写不进去

通过串口发 `t`（开 8 色彩条+方块），固件回显 `[CMD] test pattern ON` 确认执行，
**测试图案期间 `AW/W` 依然全 0**。

**并且我把 `t` 的写通路整条追过**，确认命令真的生效：

| 环节 | 位置 | 状态 |
|---|---|---|
| 写 0xC8 | `mmt_soc_regs.v:514-516` | ✅ `test_pattern_en <= PWDATA[0]` |
| 透传 | `mmt_soc_subsystem.v:224-225, 523-524` | ✅ |
| 接进顶层 | `mmt_top.v:1717-1718` | ✅ |
| 被使用 | `mmt_top.v:699-702, 712` | ✅ mux 与 `i_en` |

⇒ **写通路死与视频源无关**（不是摄像头的问题）。

### 1.4 已排除的假设

| 假设 | 结论 | 依据 |
|---|---|---|
| DDR3 校准没完成 | **排除** | **LED0 在慢闪** ⇒ `cal_done=1`（`mmt_top.v:1928-1929`） |
| `vid_rst_n` 恒 0 | **排除** | `FRM` 在涨 ⇒ 整条视频后端在跑；而 `vid_rst_n=0` 时它不可能涨（Claude 独立梳理了完整依赖链） |
| 测试图案没生效 | **排除** | 见 §1.3 的写通路追查 |
| 写通路被综合折叠 | **guard PASS**，但见下 | `check_wr_path.ps1` 4/4 PASS；不过实测零写 ⇒ **guard 的判据不够** |

## 2. HDMI 侧：我们的接口与厂商 demo **逐项相同**

用 prebuilt 厂商位流 `ti60f225_oob.bit`（2024.1 综合）做对照实验。**结果同样是"无信号"。**
为排除"我们改坏了接口"，做了 5 个维度的逐项比对：

| 维度 | 我们的 `mmt.peri.xml` | 厂商 `ti60f225_oob.peri.xml` | 结论 |
|---|---|---|---|
| TMDS 引脚 | `GPIOR_PN_10/11/12/13` | 同 | **相同** |
| LVDS 块设置（`vod`/`pre_emphasis`/`serial_width=10`/`is_half_rate`/时钟名） | — | — | **逐字相同** |
| PLL 分频（USER_PLL、`vid_clk_dvi2` /40、`hdmi_tx_slow_clk` /20、`i_mipi_rx_pclk` /56、`hdmi_tx_fast_clk` /4） | — | — | **逐项相同** |
| 行/场时序常数（`MAX_HRES 1920`/`MAX_VRES 1080`/`HSP 2`/`HBP 88`/`HFP 120`/`VSP 2`/`VBP 20`/`VFP 20`） | `mmt_top.v:249-257` | `ti60f225_oob_top.v:224-231` | **相同** |
| 时序端口接法（含 `H_FRONT_PORCH(HFP/2)`、`H_SYNC(HSP)`） | `mmt_top.v:750-757` | `ti60f225_oob_top.v:519-526` | **相同** |
| 差分对极性 | 手册注："FPGA差分对P与N脚对调" | 同 pin | **相同** |

**⇒ 厂商位流也出不了画面这件事，不可能是"我们的 FPGA 设计差异"造成的。**

### 2.1 顺带算出的真实时序（未验证是否被显示器接受）

由 `mmt_top.v:750-757` + `hdmi_tx_slow_clk = 140 MHz`：
- 每行 = 1920(有效) + 120(前肩) + 4(同步) + 88(后肩) = **2132**（标准 1080p60 = 2200）
- 每帧 = 1080 + 20 + 2 + 20 = **1122**（标准 = 1125）
- ⇒ 帧率 = 140e6 / (2132 × 1122) = **58.5 Hz**（标准 60 Hz）
- ⇒ TMDS 码率 = 10 × 140 MHz = **1.4 Gbps**（标准 1080p60 = 1.485 Gbps）

⚠️ 这套**非标准时序**与厂商 demo 完全相同（因为 PLL 与时序常数都一样）。
**它对某些显示器可能不被接受（表现为"无信号"）** —— 但这条**未验证**，因为厂商 demo 也是同样时序。

## 3. ★★ 断点已锁定：在 `frame_buffer` 写侧内部

诊断固件（v3 位流 `2,923,146 B @ 20:06:12`）加了 `[VID]` 行，读 `0xCC/0xD0/0xD4`。
这三个寄存器的输入就是 **mux 之后、`frame_buffer` 入口的同几根线**
（`mmt_test_pattern` 的 `.i_vid_de/.i_vid_hs/.i_vid_vs` 接的是 `mipi_de_sel & mipi_hs_sel` / `mipi_hs_sel` / `mipi_vs_sel`，
与 `frame_buffer` 的 `.i_de/.i_vs` 完全相同，见 `mmt_top.v:715-718` vs `:740-741`）。

**实测（测试图案开启时）**：
```
[VID] lines=1080 pixels=480 frames=155(d=27) testpat=1
[VID] lines=1080 pixels=480 frames=181(d=26) testpat=1
...
[WR]  AW=0(d=0) W=0(d=0) st=0x00 ... az=NOIMG ... st8=0x00
```

| 字段 | 实测 | 期望 | 结论 |
|---|---|---|---|
| `lines` | **1080** | 1080 | ✅ 每帧行数正确 |
| `pixels` | **480** | H_ACTIVE/PPC = 480 | ✅ 每行 de 拍数正确 |
| `frames` | **持续增长**（d≈27） | 递增 | ✅ 帧在流 |
| `testpat` | **1** | 1 | ✅ 测试图案确实开着 |
| `AW/W` | **仍然全 0** | — | ❌ |

### ⇒ 结论

**frame_buffer 的输入视频信号（de/hs/vs/数据）在硬件上完全正常，而写通路一个 AW 都不发。**

这一刀把范围从"整条视频链"砍到 **`frame_buffer` 写侧内部**：
- 排除：CSI RX、mux/测试图案、`vid_rst_n`、DDR3 校准
- 仍在范围：`vid_rx_align_v1` → `ser2par` → 写 FIFO → `ddr_wr_buffer` 的 FSM → `awvalid`

### 静态追查结果（RTL 链看起来是通的，所以必须加观测）

```
wr_start = frame_start & frame_stable          (frame_buffer.v:204)
  → start_sync (2FF 到 axi_clk) → pos_sync → sync_r2
  → FSM state 0→1                              (ddr_wr_buffer.v:408-417)
  → wr_req = (wr_fifo_rdusedw > ddr_awlen)     (ddr_wr_buffer.v:318-326)
  → FSM state 1→2, awvalid<=1                  (ddr_wr_buffer.v:418-424)
```

顺带查到的三件事（都**不构成**根因，仅记录）：
- `ddr_awlen` 只有声明 `reg [7:0] ddr_awlen = 0;`（`ddr_wr_buffer.v:68`），**全文件没有任何赋值** ⇒ 恒 0。
- `frame_info_det.v:93` 是厂商 bug：`frame_len_d0 <= frame_end_r0;`（本该是 `frame_cnt`，被注释掉了）
  ⇒ `frame_len_d0[1..23]` 在折叠报告里全被优化成 0；后果是 `frame_stable` 在第 3 次 `frame_end` 后**永久为 1**。
- `frame_buffer` 没有 `i_hs` 端口，`vid_rx_align_v1` 的 `i_hs` 悬空；但 `frame_info_det` **从未使用** `i_hs`，无影响。

## 4. 诊断固件新增的 `r` 命令（DDR 读回自测，尚未使用）

- `r` 命令让 RISC-V 往 `0x03000000`（R7 区）写 8 个魔数再读回。
- ⚠️ 固件没有超时机制，读若挂死 CPU 就再也无输出 —— 所以做成**命令触发**而不是开机自动跑：
  触发前遥测已跑起来，即使挂死，**"串口停在哪个 `[DDRR] rd@` 之后"本身就是结论**（SoC 主口到 DDR 不通）。复位重烧即可恢复。
- 用途：区分「SoC→互联→DDR3 主口本身不通」与「只有 frame_buffer 写侧有问题」。
